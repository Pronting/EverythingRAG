# Everything RAG 知识组织与检索决策重构方案

设计日期：2026 年 10 月 13 日。文档状态：待实施设计。

## 1 用户操作与交付要求

用户导入资料后，系统生成跨文档主题、主题概览和原文导航。主题页面能够展示共同讨论的问题、适用条件、不同观点和全部成员。用户提问时，研究流程根据问题选择概览、关联或原文，并根据资料中的线索继续研究。

| 用户操作 | 系统行为 | 可以检查的结果 |
| --- | --- | --- |
| 导入讨论同一问题的多篇文章 | 将相关章节组织到共同主题 | 主题成员来自多个文档，归属理由指向对应内容 |
| 导入同时讨论多个问题的文章 | 为章节建立多主题成员关系 | 同一章节可以从不同主题访问，原文身份一致 |
| 查询定义、参数或步骤 | 直接检索正文，补充所属章节及条件 | 答案引用具体原文范围 |
| 比较方法或理解一个主题 | 阅读主题概览，取得各项观点的来源 | 主要方法、前提和不同观点都有对应资料 |
| 寻找方法之间的联系 | 访问关联并核查两端原文 | 结论区分资料陈述与根据资料形成的推论 |
| 概括知识库 | 枚举限定范围内的主题报告，分批分析 | 记录实际处理范围，统计使用去重后的成员 |
| 修改或删除资料 | 更新受影响的摘要、主题和关系 | 新查询取得一致版本，已撤销来源无法继续作为依据 |
| 中断导入或研究后恢复 | 从已完成的持久化步骤继续 | 已完成的生成结果与原文读取能够复用 |

本次交付包含知识构建、分层检索、研究决策、来源核查、更新机制、迁移、前端浏览和真实语料验收。功能之间按照数据依赖安排实现，整套验收完成后发布。

## 3 知识对象与阅读层级

### 3.1 对象及所属关系

对象类型使用 `document`、`section`、`chunk`、`topic`。关系通过独立记录保存。

这四种类型用于用户浏览。构建内部另有 `organization_unit`、`claim` 和 `entity`，同样登记对象身份和版本；成员关系及知识关联使用统一对象 ID。主题页面将组织单元汇集到对应章节，并保留具体原文范围。

| 对象 | 身份 | 内容与约束 |
| --- | --- | --- |
| `Document` | `document_id` | 一个来源文档，拥有多个内容版本 |
| `Section` | `section_id` | 文档中的完整章节；包括标题前正文和无标题文档的正文区域 |
| `Chunk` | `chunk_id` | 精确检索单元；保存一个或多个原文范围和所属章节 |
| `Topic` | `topic_id` | 由共同问题或概念组织的成员集合，允许跨文档和多主题归属 |

文档结构保存原有顺序。主题包含关系采用 DAG，同一子主题可以属于多个父主题。知识关联独立保存，可以连接主题、概念和观点。

章节的直接正文与子章节分别保存。聚类读取最小的完整内容单元，父章节的总览由直接正文和子章节归纳形成，防止同一正文因多个标题层级重复参与统计。

超长章节生成多个 `OrganizationUnit`，每个单元保留 `section_id` 和原文范围。它们属于构建数据，主题页面以章节为成员展示。单个章节内部讨论多个问题时，可通过这些单元进入不同主题。

文本块可以包含多个相邻短章节的内容，但必须显式记录全部来源范围。组织单元根据章节及正文范围生成。

### 3.2 对象身份

`DocumentRegistry` 统一分配和解析身份。文档身份在首次登记时生成，文档修改产生新的 `revision_id`。文件名和标题属于版本属性。

来源路径只保存在内部登记表。对外使用对象 ID、文档显示名称和章节标题。相同内容的不同来源保留各自文档身份，并通过 `content_hash` 共享正文存储与向量结果。

文件移动通过明确的移动事件，或同一同步批次内唯一且经过来源核查的路径映射延续身份。无法确认的新增与删除分别登记。内容相同本身不足以确定来源身份相同。

章节身份匹配按以下次序执行：显式来源锚点、原有结构位置与内容指纹、同文档中的唯一内容匹配。遇到多项匹配时生成新身份，并记录可确认的前后版本关系。章节显示名称不参与主键构造。

### 3.3 阅读表示

| 层级 | 内容 | 设计默认预算 |
| --- | --- | --- |
| L0 | 名称、范围、关键概念、可处理的问题 | 目标 150～300 tokens，最大 384 tokens |
| L1 | 观点、条件、限制、不同观点和阅读导航 | 目标 600～1600 tokens，正文最大 2048 tokens |
| L2 | 指定版本的原文 | 单次默认 1600 tokens，可按范围继续读取 |

L0、L1 是文档、章节和主题的阅读表示。文本块直接承载 L2 检索结果。主题的 L2 通过成员清单访问章节正文。

token 数量使用对应模型的 tokenizer。L0、L1 的正文预算与完整响应预算分别记录；来源 ID、结构字段、工具定义和消息格式仍计入完整请求。

OpenViking 使用 L0 和 L1 定位内容，再按需访问 L2；本项目将这种阅读方式应用于文档、章节和跨文档主题。[OpenViking Context Layers](https://docs.openviking.ai/en/concepts/03-context-layers)

### 3.4 L1 内容格式

| 字段 | 结构与要求 |
| --- | --- |
| `scope` | 主题对象、讨论范围、来源覆盖说明 |
| `key_points` | 观点列表，每条绑定 `claim_id` 和来源范围 |
| `conditions` | 前提、适用对象、版本、时间或环境限制 |
| `limitations` | 材料明确记载的限制、例外及未回答的问题 |
| `disagreements` | 双方观点、各自条件、是否已确认存在矛盾 |
| `navigation` | 阅读目的、目标对象、对应观点和建议读取范围 |
| `coverage` | 输入成员、成功处理成员和来源版本 |

模型通过 JSON Schema 输出结构，Pydantic 校验后保存。Markdown 展示由确定性渲染器生成。完整成员清单、观点记录和引用关系存入独立数据表。

L1 可以写明“了解更新条件，读取这些章节”，导航目标必须属于该版本的有效知识对象。OpenViking 的概览提示词包含这类按阅读目的组织的导航。[OpenViking Overview Generation](https://github.com/volcengine/OpenViking/blob/4c9a755bff4d31fd9bd9a3be1a19a6054ef3cea5/openviking/prompts/templates/semantic/overview_generation.yaml)

## 4 正文快照与来源位置

### 4.1 保存的正文视图

每个文档版本保存原始文件内容、解码后的 `raw_text`、用于检索的 `normalized_text` 和结构解析结果。文件字节哈希与各文本视图哈希分别记录。

`raw_text` 保留解码后的正文及换行形式。所有字符范围采用从零开始、结束位置不包含在内的 Unicode code point 区间。前端直接使用后端返回的引用摘录和位置，不用 JavaScript 字符长度重新推算后端范围。

| `SourceSpan` 字段 | 含义 |
| --- | --- |
| `document_id`、`revision_id` | 来源身份及内容版本 |
| `section_id` | 所属章节 |
| `content_view` | 范围所属正文视图，最终原文引用使用 `raw_text` |
| `start`、`end` | 字符范围 |
| `line_start`、`line_end` | 展示和原文定位使用的行范围 |
| `content_hash` | 所属正文视图哈希 |
| `span_hash` | 该范围实际文本的哈希 |

### 4.2 Markdown 与 HTML 来源映射

使用 `markdown-it-py` 解析原始 Markdown，保留 token 的来源行范围。每个原始结构单元先取得来源范围，再生成清洗后的检索文本。HTML 单元通过成熟 HTML 解析库处理，保存其原始容器范围。

一个规范文本单元可以映射到多个原文范围。表格行关联原始表头和对应数据行；代码保存原文范围；图片关联引用位置、图片身份和已有识图证据版本。

预处理造成字符数量变化时，引用依靠保存的映射访问原文。只能够确定表格或 HTML 容器范围时，引用完整容器，并如实标记范围精度。

### 4.3 正文读取

`read_document` 接收文档、章节或来源范围，直接读取版本快照。返回实际起止位置、相交章节、正文、下一读取位置、内容哈希及是否读完指定范围。

工具按文本段、列表、代码和表格边界安排窗口。单个表格或代码对象超过普通窗口预算时，返回对象信息和分页位置，后续按表格行或代码行读取。表头作为单独引用随相关行提供。

研究证据保存实际读取的原文。用于检索的清洗文本可以帮助选择位置；最终引用检查通过 `SourceSpan` 读取对应原文并确认摘录。

完整正文属于知识存储。模型上下文和工具结果只携带本次实际读取的窗口。

## 5 数据存储与索引

新增 `data_dir/knowledge.db`，使用 SQLite WAL 和外键检查。正文快照保存在 `data_dir/knowledge_content/`，以内容哈希寻址。大对象写入完成并验证哈希后，才能被数据库记录引用。

`state.db` 保存扫描指纹和来源根；`knowledge.db` 的已发布版本清单决定可检索内容。`app.db` 保存工作区与研究记录，通过 ID 关联共享知识版本。

为对象类型、来源版本、主题成员反查、依赖反查、构建状态建立索引。名称与摘要全文索引使用 SQLite FTS5，中文分词复用项目的 jieba 配置，并记录分词规则版本。

### 5.2 发布版本的向量 collection

每个知识版本使用独立的正文 collection 和导航 collection。正文 collection 保存文本块的检索表示；导航 collection 保存文档、章节、主题的 L0 和 L1 表示。

向量记录统一携带 `object_id`、`revision_id`、`object_kind`、`level`、`representation_version` 和 `generation_id`。成员清单、条件和来源数组保存在 SQLite。

向量复用键为 `embedding_fingerprint + embedding_input_hash`。复用前核对维度、模型身份和输入表示版本。正文未变化且输入相同的向量直接复制到待发布 collection。

已发布 collection 按只读方式打开，缺失时返回明确错误。待发布 collection 通过专用创建接口生成。所有写入和清理继续遵守 `.chroma-write.lock`。

### 5.3 一致性约束

1. `generation_objects` 中的每个对象版本必须存在。
2. 文档结构和主题包含关系分别检查环路。
3. 观点、摘要和关系的全部来源必须属于当前版本。
4. 向量对象、内容哈希和 SQLite 清单逐项一致。
5. 每个正文检索单元都能访问其原始来源范围。
6. 有内容的组织单元必须拥有主题成员关系或独立导航入口。
7. `active_generation_id` 只能指向通过完整性检查的版本。

## 6 章节分析与主题构建算法

### 6.1 章节分析输入

按照文档结构生成 `OrganizationUnit`。每个单元包含文档名称、完整标题路径、直接正文和相关来源范围。正文默认最多 2400 tokens，实际请求还要预留提示、输出及协议空间。

短小章节保留身份。相邻内容可以共同进入分析请求，但输出必须分别关联各自单元。代码、表格和图片描述附带所属章节信息；相应单元只提取资料能够支持的内容。

章节分析生成以下记录：

- 讨论的问题和概念。
- 主要观点及原文摘录。
- 方法成立的条件、限制和例外。
- 时间、版本、数值、单位和适用对象。
- 原文明示的概念关系。
- 章节 L1 和从中提取的 L0。

生成输入逐条携带 `span_id`。模型返回的 ID 必须出现在该次输入中。程序读取对应原文验证摘录；独立语义核查检查观点、条件和方向是否被引用内容支持。

结构错误、未知来源 ID、无效范围和引用文本不匹配使当前步骤失败。语义核查返回 `unsupported` 或 `uncertain` 时，该项记录保持相应状态，后续摘要只能使用确认有依据的观点。

### 6.2 章节表示

组织 embedding 的输入包含标题路径、章节范围、主要问题、关键观点和条件关键词。原文检索 embedding 继续使用正文表示。

单元内部存在多个明确问题时，分析结果为每个问题保存一个带来源范围的主题候选表示。它们共同指向原有章节。源内容、组织表示和正文检索表示各自记录哈希及版本。

### 6.3 聚类步骤

采用 UMAP 与 GMM 的递归主题构建。RAPTOR 官方实现使用 UMAP、GMM、BIC 和多群组成员关系，并将下层节点归纳为上层摘要节点。[RAPTOR Cluster Utils](https://github.com/parthsarthi03/raptor/blob/7da1d48a7e1d7dec61a63c9d9aae84e2dfaa5767/raptor/cluster_utils.py) [RAPTOR Cluster Tree Builder](https://github.com/parthsarthi03/raptor/blob/7da1d48a7e1d7dec61a63c9d9aae84e2dfaa5767/raptor/cluster_tree_builder.py)

项目中的完整规则如下：

1. 按组织表示哈希识别完全重复输入，并保存其全部来源身份。
2. 检查向量数量、维度和数值有效性，归一化向量。
3. 单个输入直接保留为独立导航节点。少于 12 个输入时，在原向量空间运行 diagonal GMM；其余输入通过 UMAP 降维后运行 GMM。
4. UMAP 默认维度为 10，邻居数量为 `min(15, N - 1)`，距离使用 cosine，随机种子固定并记录。
5. GMM 候选数量为 `1..min(50, max(1, floor(N / 2)))`。以 BIC 选择模型，设置协方差正则项，检查拟合收敛。
6. GMM 成员候选使用默认阈值 0.10。模型后验数值只表达聚类分配情况。
7. 语义核查读取成员的范围、观点和条件，确认共同问题并生成主题名称。成员归属理由必须引用自身内容。
8. 未取得有效归属的单元保留独立入口。相同成员集合合并为一个主题候选。
9. 保存主题成员、理由、来源、输入指纹和算法参数。
10. 根据主题 L1 生成上层组织表示，继续执行聚类和主题核查。

数值模型不收敛、向量出现无效值或生成结构无效时，构建步骤返回失败。算法根据小样本数量选择的正常分支直接记录在构建清单中。

### 6.4 递归终止

每轮主题构建要求上层有效节点数量严格小于输入节点数量。一个群组需要至少两个不同成员，而且需要确认能够描述共同范围。无法满足时，相应节点作为当前根主题保留。

数量检查包含新父主题和本轮未归入父主题的节点。所有输入节点必须仍然能从输出节点访问；存在多个主题归属时，按唯一节点计算。候选层级未满足数量减少与完整覆盖两个条件时，保留当前层级为根主题集合，结束递归。

单成员包装、重复成员集合和自我包含不会形成新的主题层级。由节点数量严格减少保证递归终止。知识库可以具有多个根主题。

摘要输入超过上下文时采用分批归纳；批次数量在每次汇集后减少。摘要批次与主题层级分别记录。

### 6.5 多主题归属与统计

主题直接成员记录唯一来源单元。读取全部后代时，使用 `topic_descendants` 按对象身份去重。统计原文数量时继续按文档版本及正文范围去重。

同一章节通过两个子主题访问时，主题覆盖统计只计算一次。内容完全相同的多份文档可以显示多个来源，观点支持数量同时给出内容去重后的数量。

### 6.6 主题身份延续

新旧主题在相同生成规则下，根据成员交集、内容范围和主要观点计算匹配候选。成员比较以来源单元身份为基础，使用加权 Jaccard；名称仅作为显示信息。

候选采用 `scipy.optimize.linear_sum_assignment` 进行一对一匹配。身份继承需要成员相似度达到配置阈值且语义范围核查通过。默认成员阈值为 0.60，该值在固定验证集上接受发布验收。

发生明确合并或分裂时创建相应新主题，并在 `topic_lineage` 保存前后关系。历史引用始终通过原 `generation_id` 访问原有主题。主题改名作为版本内容更新。

## 7 摘要生成与来源传递

### 7.1 输入清单

每次摘要生成创建 `SummaryInputManifest`，保存输入对象及版本、输入观点、来源范围、批次安排和生成规则。批次开始前检查 token 预算，完成后记录实际处理的输入 ID。

成员处理覆盖率按成功处理的唯一输入数量计算。它表示材料进入过归纳流程；摘要观点是否忠实以及是否遗漏重要条件，通过单独的语义验收检查。

### 7.2 生成过程

章节或主题摘要按照以下次序生成：

1. 收集该对象的全部有效成员及观点记录。
2. 按来源和内容去重，保留不同条件、例外和不同观点。
3. 根据上下文预算分批形成带来源的观点组。
4. 汇集观点组，生成结构化 L1 和阅读导航。
5. 从 L1 提取 L0，验证名称、条件和问题范围一致。
6. 检查全部导航目标、来源链、正文预算和覆盖清单。
7. 保存摘要及输入依赖。

上层摘要中的每条事实通过 `claim_id` 最终访问原文范围。引用链同时保存中间摘要和原文终点，读取证据时可以直接访问终点。

### 7.3 条件与不同观点

条件、例外和不同观点独立于简短摘要正文保存。上层 L1 至少给出存在这些内容的导航，完整记录可以分页访问。

概括“多份资料提出某方法”时，需要确认对应来源。概括“普遍采用”或“主要观点”时，需要明确样本范围和统计依据。语料中的重复转载按能够确认的原始来源关系合并统计；来源独立性未知时保留未知状态。

### 7.4 生成结果复用

摘要复用键包含输入对象与版本、输入观点、模板版本、JSON Schema 版本、模型配置指纹、tokenizer 版本、生成参数和语言。

同一有效复用键直接读取已保存结果。重新调用模型时保存新的生成记录；固定温度和随机种子不作为输出逐字相同的保证。

模型输出超过摘要正文上限时，当前步骤返回明确校验错误。恢复步骤时提供原输出和具体错误，通过正常生成流程重新形成完整结构。

## 8 概念与关联记录

### 8.1 概念身份

概念类型包含 `concept`、`method`、`system`、`metric`。每个概念保存规范名称、原文别名、含义范围和全部提及位置。

别名合并需要原文明示，或来自上下文充分的语义核查。具有相同名称但作用对象、版本或含义不同的概念分别保存。全局主题名称不决定概念身份。

### 8.2 关系分类

| 关系 | 记录内容 | 回答中的使用条件 |
| --- | --- | --- |
| `related_to` | 语义相近或共享概念 | 用于发现阅读对象 |
| `applies_under` | 方法成立的条件 | 核查方法与条件对应原文 |
| `depends_on` | 一项方法对其他条件或机制的依赖 | 核查方向及适用范围 |
| `supports` | 一项观点支持另一项观点 | 核查两端观点及资料中的联系 |
| `contrasts_with` | 对同一问题提出不同方法或观点 | 分别读取双方条件 |
| `contradicts` | 在一致对象、条件和时间下存在相互矛盾的陈述 | 读取双方原文并确认条件一致 |
| `example_of` | 具体案例与概念或方法的关系 | 核查案例适用范围 |

每条关系包含 `origin`、`validation_status`、两端对象、关系描述、条件、方向和来源。`origin` 区分 `source_explicit`、`cross_source_inference` 与 `computed_similarity`。

源文明示关系由原文支持。跨来源推论保留双方原文和推论说明，进入答案时使用相应表达。语义相似关系供导航使用。

### 8.3 候选生成与核查

章节分析直接提取源文明示关系。跨来源候选从共享概念、相同问题、主题重叠和组织向量邻居中产生，默认每个对象取得 12 个向量邻居，并按对象组合去重。

跨来源核查同时提供双方内容，检查对象、版本、时间、数值单位和条件。核查结果允许 `supported`、`uncertain`、`unsupported`，后两种状态不会被作为已确认关系描述。

源文发生变化时，依赖该版本的关系必须重新核查。GraphRAG 标准索引的实体提取、关系提取及描述归纳为这部分提供参考。[GraphRAG Indexing Methods](https://microsoft.github.io/graphrag/index/methods/)

## 9 分层检索与范围处理

### 9.1 检索请求

统一请求使用 `KnowledgeSearchRequest`，包含 `query`、`generation_id`、`object_kinds`、`levels`、`document_ids`、`topic_ids`、`scope_digest`、候选数量与输出 token 预算。

`scope_digest` 根据知识版本、文档范围、主题范围及其他有效过滤条件计算。分页游标绑定这些条件和稳定排序键，条件改变后旧游标失效。

检索结果分为 `NavigationHit` 和 `EvidenceCandidate`。两种结果都包含身份、版本、匹配方式及来源信息。`NavigationHit` 返回 L0 或导航片段；`EvidenceCandidate` 返回原文候选及对应 `SourceSpan`。

### 9.2 候选取得

| 通道 | 检索内容 | 设计默认候选窗口 |
| --- | --- | --- |
| 名称与别名 | 文档名、章节名、主题名、概念别名 | 20 |
| 导航 dense 与 FTS5 | L0、L1 和适用问题 | 各 24 |
| 正文 dense 与 BM25 | 文本块和原文相关表示 | 各 40 |
| 成员导航 | 已选择主题的章节、子主题 | 每页 30，可继续枚举 |
| 关系导航 | 符合范围的关系及两端对象 | 每页 20，可继续枚举 |

同类候选通过 RRF 合并，并保留每个通道的信号。L0 与 L1 命中同一对象时，合并为一个导航候选，保存命中层级。

导航候选和证据候选分别进行相关性判断。默认向决策模型提供最多 8 个导航候选；原文进入现有 `EvidenceView` 与 rerank 流程，数量还受上下文预算约束。

摘要评分使用单独的视图类型与校准档案。正文评分档案继续按原文视图校验。各层级的原始 dense、BM25 和 rerank 分数各自保存。

允许直接搜索全部层级。精确问题取得正文后可以完成证据核查；综合问题可以从主题或文档概览开始。RAPTOR 的 `collapse_tree` 路径允许从全部节点检索。[RAPTOR Tree Retriever](https://github.com/parthsarthi03/raptor/blob/7da1d48a7e1d7dec61a63c9d9aae84e2dfaa5767/raptor/tree_retriever.py)

### 9.3 主题范围

主题范围通过 SQLite 的去重成员集合解析成文档、章节和文本块集合。范围过滤在召回前应用。

正文 dense 查询根据 Chroma 适配器支持的过滤容量分批执行。每批取得同样数量的候选，按同一表示中的分数合并，再执行相关性筛选。BM25 或 FTS5 使用同一范围的成员集合。

来源范围无法解析时返回明确错误。查询没有相关结果时返回成功执行且候选为空，并记录搜索范围。

### 9.4 用户限定文档时的摘要

预生成主题可能包含范围外资料。范围限定请求取得主题成员交集后，仅使用交集成员生成对应 L0、L1，并以 `generation_id + scope_digest + topic_id + generator_fingerprint` 缓存。

全部成员都在指定范围内时，直接复用已有摘要。范围摘要只能引用范围内的观点、成员和关系。后台可以借助全库索引定位主题候选，进入研究模型上下文的内容必须符合当前范围。

### 9.5 上下文选择

读取 L1 时保留与当前要求相关的观点、条件和导航。已经转化为原文读取目标的导航条目可以从活动上下文移出，完整结果仍保存在工具记录中。

同一原文通过主题、关系和正文检索多次出现时，按文档版本与范围去重。模型上下文记录实际提供的范围。父主题与子主题同时相关时，按照覆盖的新问题选择读取对象，并保留未展示对象的可访问 ID。

## 10 检索决策与研究状态

### 10.1 研究方式

`RouteDecision` 增加 `knowledge_mode`，取值为 `fact`、`theme`、`relationship`、`global`。同时保存来源范围、候选主题与用户要求。复合问题在每个研究任务中选择相应方式。

| 方式 | 初始动作 | 必要核查 |
| --- | --- | --- |
| `fact` | 名称定位或正文搜索 | 具体事实、所属对象、条件和原文范围 |
| `theme` | 主题搜索与 L1 阅读 | 主要观点、方法覆盖和各自来源 |
| `relationship` | 主题搜索、概览阅读、关系探索 | 两端对象、关系方向和适用前提 |
| `global` | 解析范围、枚举主题、分批分析 | 成员覆盖、统计依据和结论来源 |

模型根据完整问题和相关目录决定方式。主题名称命中作为资料线索，实际能否回答由原文支持检查决定。

### 10.2 持久化研究记录

新增 `KnowledgeResearchState`，由 `RagResearcher` 持有并写入现有 run 持久化体系。

| 记录 | 关键字段 |
| --- | --- |
| `ResearchQuestion` | `question_id`、`requirement_ids`、问题、来源线索、是否必要、状态 |
| `ResearchAction` | `action_id`、动作、目标、前置条件、对应问题、预算、状态 |
| `TopicVisit` | 主题、版本、读取层级、范围摘要、已枚举游标 |
| `SourceRead` | 文档版本、正文范围、实际提供的 tokens、证据 ID |
| `ClaimAssessment` | 观点、支持证据、条件核查、冲突处理结果 |
| `CoverageRecord` | 要求、已支持内容、缺少内容、相关证据、判断理由 |
| `ScopeCoverage` | 合格主题和成员、已处理集合、来源读取集合 |
| `ActionOutcome` | 新来源、新条件、新观点、重复内容及失败原因 |

`RunResearchState` 负责同一 run 内的工具执行复用。复用键包含 `generation_id`、`revocation_epoch`、`scope_digest`、工具及规范参数。原文读取再包含正文版本和实际范围。

### 10.3 决策模型输出

每轮决策输出有明确 JSON Schema 的 `ResearchDecision`：

- `action`：允许的动作枚举。
- `question_id` 与 `requirement_ids`：对应研究问题和用户要求。
- `target_ids` 或 `query`：工具输入目标。
- `origin_refs`：触发本次动作的概览、观点、关系或用户原话。
- `expected_gain`：预计取得新来源、条件、不同观点或范围覆盖。
- `budget_request`：本次读取及模型调用预算。
- `reason_summary`：可展示的简短选择理由。

模型仅能选择当前服务支持的动作。程序检查目标存在性、来源范围、依赖是否完成、是否重复和预算。无效输出使当前决策步骤失败，保存具体错误供恢复处理。

### 10.4 动作及前置条件

| 动作 | 前置条件 | 输出与进展 |
| --- | --- | --- |
| `search_topics` | 问题和来源范围明确 | 新导航候选 |
| `read_overview` | 对象有效且范围允许 | 观点、条件、导航目标 |
| `list_members` | 主题有效 | 可继续分页的完整成员 |
| `search_evidence` | 完整查询及有效范围 | 原文候选 |
| `read_source` | 原文位置已确定 | 实际正文窗口和证据 |
| `explore_relation` | 两端至少一端已定位 | 关系记录与核查位置 |
| `map_topics` | 已取得范围清单及批次 | 每个批次的观点和未回答问题 |
| `assess_coverage` | 新资料已登记 | 每项要求的覆盖判断 |
| `finalize` | 达到完成条件 | 交给现有答案生成与核对流程 |

同一轮中互不依赖的检索可以并行执行，读取结果之后的判断按依赖顺序执行。访问下一层关系时，每次都需要说明它与当前用户要求的联系。

### 10.5 从概览生成研究问题

研究问题可以来自 L1 的未核查观点、适用条件、不同观点和阅读导航。每个新增问题必须关联至少一项用户要求，并保存触发它的来源记录。

例如，用户询问改善长期记忆的方法，概览中包含“写入选择”和“更新条件”时，后续问题可以分别核查选择依据及更新触发条件。问题中的研究对象、文档范围和用户限制继续传入检索。

GraphRAG DRIFT 从相关群组报告形成后续问题，再通过局部检索继续研究；本项目使用这一决策思路，并将问题和动作写入现有研究状态。[GraphRAG DRIFT Search](https://microsoft.github.io/graphrag/query/drift_search/)

### 10.6 覆盖判定

`CoverageRecord` 使用 `missing`、`partial`、`supported`、`conflict`。已有 `RequirementState` 的 `answered` 由完成核查的 `supported` 映射产生。

一项要求达到 `supported` 需要同时满足：

1. 有直接回答该要求的结论。
2. 结论引用的原文已经进入研究证据。
3. 对象、数值、单位、条件与版本通过现有程序检查和语义核查。
4. 比较问题取得每个被比较对象的必要资料。
5. 存在不同观点时，已表达各自条件或记录无法确认的部分。
6. 限定来源范围得到遵守。

目录统计类要求可以由指定版本的完整数据库查询结果支持。正文事实类要求使用对应原文证据。

### 10.7 终止与恢复

正常完成需要所有必要要求已有支持，且影响结论的条件、矛盾和歧义已经处理。相关资料耗尽时，以具体缺口结束。用户取消、预算耗尽或服务失败分别保存对应状态。

研究进展包括新原文范围、新的有效导航目标、新条件和新的覆盖结果。重复读取同一摘要、仅改写同义问题或取得重复材料不会增加进展。

默认连续三个已完成动作没有新增有效资料时，执行一次范围与待处理动作检查；仍无可执行的新目标则停止并记录缺口。已经取得新导航但尚未读取原文时，目标读取属于待处理动作。

恢复时重新核对知识版本、来源撤销状态和模型配置。有效的已完成步骤直接复用，失败步骤使用相同身份继续执行。发生来源撤销时，撤销相关证据与结论，并清理其活动上下文后重新判断待处理要求。

## 11 全库问题的研究流程

`global` 模式首先生成固定范围的 `ScopeManifest`，包含全部合格文档、组织单元、根主题和独立导航节点。范围清单使用当前知识版本和过滤条件计算。

系统从根主题开始构造需要处理的主题集合。当某主题内容跨度超过当前问题所需范围或报告容量时，使用其子主题与直接成员继续组织批次。每个原始单元至少被一个批次覆盖；多重归属通过唯一来源集合处理。

每个批次输出与问题有关的观点、原文引用、条件、不同观点及无法回答的内容。汇集过程按观点和来源去重，再读取将进入最终答案的关键原文。

统计类问题直接查询完整成员清单。主题报告数量、来源数量和独立观点数量分别计算。摘要中出现某个词语的次数不作为观点频率。

覆盖记录分别保存：

- `eligible_source_units`：限定范围内的全部来源单元。
- `summarized_source_units`：被有效主题报告覆盖的来源单元。
- `processed_source_units`：本次问题对应批次已经处理的来源单元。
- `read_source_spans`：本次实际读取的原文范围。

全库批次全部处理完成时，可以报告范围分析完成。预算不足时记录已处理数量及未处理集合，并按实际范围生成答案。

GraphRAG Global Search 使用指定层级的群组报告执行 map-reduce，本项目将其批次方式用于主题报告，并增加来源集合与覆盖记录。[GraphRAG Global Search](https://microsoft.github.io/graphrag/query/global_search/)

## 12 构建任务与版本发布

### 12.1 构建任务状态

`BuildJob` 使用 `queued`、`running`、`interrupted`、`failed`、`cancelled`、`completed`。每项任务包含基础版本、输入快照清单、生成配置及当前步骤。

步骤按以下依赖执行：

`capture_sources → parse_sources → analyze_sections → build_topics → build_relations → materialize_indexes → validate_generation → publish_generation`

步骤记录输入哈希、成功产物、实际模型用量、执行时间和错误类型。独立章节可以并行分析，默认模型并发数为 2，并服从现有 provider 的共享并发管理。

同一数据目录同时只允许一个任务进入知识版本写入流程。新变更进入队列。SQLite 事务只处理本地记录，模型请求在事务之外执行。

单个文件读取或分析失败时立即记录该步骤失败；其他独立文件可以继续完成。当前批次全部必需输入成功后才能发布，失败批次保持完整错误清单和已完成产物。

### 12.2 增量构建

文件扫描使用 mtime、size 和内容哈希识别变化。构建时保存实际读取的内容及其哈希；扫描后又变化的文件以本次实际快照为准，后续同步继续处理新变化。

新版本从基础版本清单生成。未变化的正文、章节分析和 embedding 复用已保存产物。组织表示变化时，对当前有效组织表示重新执行主题聚类，随后计算成员差异和依赖变化。

摘要与关系根据输入指纹复用。主题归属变化可能影响多个祖先，依赖反查必须处理全部相关祖先。生成模型、模板、tokenizer、解析规则和 embedding 变更分别通过各自指纹触发重建。

一次同步内的资料变更合并为一个构建批次。重新聚类的 CPU 时间、向量复制时间、变化摘要数量和模型调用数量均进入构建报告。

### 12.3 图片证据

文档版本记录图片的 `pending`、`ready` 或 `failed` 状态。包含图片但正文可用的版本可以按实际可用证据完成构建；摘要明确记录尚未取得图片信息的位置。

图片分析完成后生成变更任务，更新相应章节及依赖摘要，通过新知识版本发布。每项图片结果核对其来源文档版本。来源已经撤销或替换的图片任务不能写入当前版本。

### 12.4 发布步骤

1. 将知识版本标记为 `building`，保存 `base_generation_id`。
2. 完成正文、分析、主题和关系记录。
3. 写入待发布正文与导航 collection，并建立相同版本的词法索引。
4. 执行结构、引用、数量、哈希和 ANN 可达性检查。
5. 将版本标记为 `validated`，保存检查报告和全部产物指纹。
6. 开启 SQLite 事务，核对当前活动版本等于 `base_generation_id`，且撤销状态符合构建清单。
7. 更新 `active_generation_id`，标记新版本为 `published`，提交事务。
8. 更新扫描状态投影、工作区公开版本信息和界面事件。

Chroma 写入完成后才能提交 SQLite 发布指针。查询通过指针读取清单中指定的 collection。发布后的状态投影如果未完成，启动时依据共享发布清单恢复。

构建期间的新查询读取当前已发布版本，界面同时显示待发布任务状态。运行中的研究持有其 `generation_id`，在正常资料更新时继续读取相同版本。

### 12.5 崩溃恢复与产物清理

启动时将失去执行进程的 `running` 任务标记为 `interrupted`。恢复检查已完成步骤的输入和产物哈希，仅重新执行缺少有效结果的步骤。

模型请求已发送但结果未保存时，记录 `unknown_outcome`。恢复重新发起请求，实际模型调用与费用按照 provider 可取得的记录报告。

已完成 collection 写入但尚未发布的版本继续执行校验。已经发布而尚未完成界面状态更新的版本补充状态投影。

活动版本、运行中研究和可恢复任务所引用的版本保持可读。默认额外保留最近两个已发布版本。清理任务检查引用计数后删除未引用产物；正文内容按全部有效来源和历史保留引用共同计算使用情况。

### 12.6 删除与来源撤销

删除操作在 `knowledge.db` 事务中登记来源撤销并增加 `revocation_epoch`。新检索和读取立即检查撤销记录，相关摘要、观点及关系通过依赖反查标记为不可用。

正在运行的研究在工具返回前、上下文组装前和答案发布前核对撤销状态。发现受影响来源时，移除相关活动证据、上下文和结论，重新执行必要的覆盖检查。

历史答案保持会话记录，其来源标记为已撤销，后续研究不会复用这些来源作为有效知识证据。后台构建排除已撤销资料的新版本，并根据保留引用完成内容清理。

完全相同内容的其他有效来源保留自身身份。撤销依据来源身份执行。

## 14 配置与模型预算

新增 `KnowledgeOrganizationConfig`。索引模型选择复用现有 provider 注册表，以明确的 `ModelSelection` 保存；设置迁移时复制当前有效选择作为索引模型选择，之后分别管理。

只有旧 `chat` 配置时，配置迁移按其有效地址和模型建立等价索引模型配置。创建构建任务时固定模型、能力和 tokenizer 信息，运行过程中设置变化不改变该任务的配置。

| 参数 | 设计默认值或规则 |
| --- | --- |
| `organization_unit_max_tokens` | 2400 |
| `l0_target_tokens`、`l0_max_tokens` | 256、384 |
| `l1_target_tokens`、`l1_max_tokens` | 1200、2048 |
| `source_read_target_tokens` | 1600 |
| `cluster_reduction_dimension` | 10 |
| `cluster_max_components` | 50，受样本数量规则限制 |
| `cluster_membership_threshold` | 0.10 |
| `cluster_random_state` | 42 |
| `topic_identity_min_overlap` | 0.60 |
| `relation_neighbor_candidates` | 12 |
| `index_model_concurrency` | 2，服从共享 provider 限额 |
| `navigation_result_limit` | 8，服从实际 token 预算 |
| `overview_reads_per_decision` | 最多 3 个，服从实际 token 预算 |
| `stalled_action_limit` | 3，之后执行待处理目标检查 |
| `retained_published_generations` | 最近 2 个，额外保留运行或恢复所需版本 |

这些数值属于设计默认值，固定语料验收负责核查其质量和资源使用。发布配置与评测结果共同记录，语义阈值不会被解释为事实正确率。

每次模型请求沿用现有预算条件：

`local_prompt_tokens + reserved_output_tokens + protocol_margin <= provider_context_limit`

新增构建与研究总预算记录实际输入、输出、embedding 数量、provider 费用和执行时间。费用只有在配置了对应计价信息时计算，否则显示实际 tokens 与调用数量。

单次上下文预算由模型能力限制。整次研究的累计调用与时间预算通过显式运行配置控制；未配置累计上限时，由完成条件、资料耗尽、无新增资料和用户取消控制终止。

预算不足时，分批读取尚未处理的完整内容，或结束当前研究并记录缺口。tokenizer 缺失、模型能力未知或配置无效时，调用前返回错误。

## 15 知识浏览与研究过程展示

### 15.1 主题浏览

知识浏览入口提供主题目录与文档目录。主题卡片显示名称、L0、来源文档数量和更新时间。打开主题后读取 L1，展示主要观点、条件、不同观点及阅读导航。

主题页面提供子主题、直接成员、全部来源和关联内容。全部来源通过分页访问完整成员清单。成员显示文档名称、章节路径、归属理由和原文入口；数量根据去重来源计算。

选择一个观点能够查看对应原文与适用条件。选择关联能够查看关联描述及双方来源。用户从一个主题访问另一个主题时，页面保留访问路径；同一主题可以有多个访问路径。

### 15.2 构建状态

导入界面分别显示来源读取、章节分析、主题构建、关系核查、索引校验和发布进度。进度分母来自实际任务清单。运行中的知识版本和待发布任务分别显示，用户能够看到本次导入何时可用于问答。

失败任务展示失败阶段、受影响文件数量、可执行的恢复操作和已有模型用量。后台保留脱敏错误代码，界面按现有来源权限显示用户可访问的文档名称。

### 15.3 研究过程

`ProcessArea` 展示可理解的动作，例如“阅读长期记忆主题概览”“核查两种更新方法的适用条件”“读取三份来源”。动作名称和简短理由来自持久化事件。

来源面板展示进入答案的原文依据。主题概览可以作为阅读路径显示，引用入口直接定位原文。全库问题展示已分析范围、尚未处理范围和实际读取的来源数量。

HTTP 响应、SSE 事件与 `frontend/src/types.ts` 使用相同字段定义。重连后从持久化研究状态恢复动作与覆盖信息。

## 16 数据迁移与发布条件

### 16.1 迁移清单

迁移命令创建 `MigrationManifest`，记录旧 schema、collection、embedding fingerprint、文档清单、来源读取结果、新身份映射和目标 `generation_id`。旧数据保持可读，迁移在独立目标数据库和 collection 中完成。

1. 核查配置、真实来源文件、旧块清单和 embedding 配置，登记可用来源。
2. 保存文件快照，从原始来源建立章节、组织单元和原文范围。
3. 建立旧 `document_id`、块 ID 与新对象的映射。对应原文无法确认时登记未映射状态，历史引用保留原有展示信息。
4. 根据完整 embedding 输入哈希复用向量。标题、表示规则或正文发生变化时重新计算相应向量。
5. 完成章节分析、主题构建、关系核查和两个 collection 的生成。
6. 执行第 18 节的结构、版本、检索和问答验收，保存结果。
7. 通过第 12 节的发布事务启用新知识版本。

读取不到来源文件的文档列入迁移阻塞清单。操作界面提供重新关联来源和明确移出本次迁移范围的操作；用户确定的范围形成新的迁移清单。任何未完成的必需输入都会阻止本批次发布。

### 16.2 运行兼容

研究 run 保存执行协议版本和知识版本。迁移前已经开始的 run 继续读取其原有版本；发布后的新 run 使用新的知识服务。各版本的工具缓存与研究记录分别校验，恢复请求使用对应的执行协议。

现有 `S1` 等答案引用继续由原文证据分配。主题、观点和来源范围具有各自内部身份，最终生成过程通过证据登记器取得答案引用 ID。

旧版本清理需要同时满足保留策略、无活动读取者及无可恢复任务引用。迁移清单、结构校验和聚合评测结果保留，用于定位运行问题。

## 18 真实语料验证与验收

### 18.1 评测输入

使用实际知识库的固定快照，记录语料 SHA-256、来源文件与章节范围、模型及 embedding fingerprint、schema、配置和知识版本。私人正文和逐题产物保存到已被 Git 忽略的 `.tmp_probe/knowledge-refactor/`；仓库保存评测代码和经过检查的聚合结果。

保留现有 `scripts/rag_eval_cases.json` 的完整用例，并补充真实提问，覆盖事实、跨文档主题、关系、全库概括、限定来源、不同观点、资料不足和来源更新。新增用例逐题标注所需观点、可接受原文范围、适用条件及应说明的未知内容。

标注来源直接核查原文。语义评测使用独立评分流程并抽查判定依据；关键引用、数字、否定和条件需要逐项检查。评测调用真实 embedding、生成模型、SQLite 和 Chroma。

### 18.2 结构与更新验收

| 检查项 | 验收条件 |
| --- | --- |
| 原文映射 | 每个有效文本块均可读取对应版本原文，范围和哈希全部匹配 |
| 主题成员 | 每个有效组织单元有主题归属或独立导航入口，完整清单可以分页枚举 |
| 层级结构 | 无环路、无自我包含、无重复成员集合造成的递归 |
| 摘要依赖 | 所有导航目标和观点引用存在，必需成员全部进入归纳流程 |
| 多主题统计 | 同一原文经多条路径访问后，覆盖数量与去重原文集合一致 |
| 范围限定 | 工具正文、范围摘要、关系与答案引用全部符合限定来源 |
| 更新发布 | 每次查询绑定一个完整版本，正文、导航和词法索引清单一致 |
| 删除撤销 | 新检索、已有工具缓存、活动证据和答案发布检查均识别撤销来源 |
| 中断恢复 | 在实际构建进程终止并重启后，复用已有有效产物并完成发布 |

实际文件新增、修改、移动、删除在隔离的真实语料副本中执行。复制后的文件内容、模型服务、数据库和索引均使用真实实现。通过终止实际子进程检查模型结果保存前后、collection 完成前后以及发布事务前后的恢复行为。

### 18.3 检索与答案验收

同一批问题分别运行当前系统、启用主题组织的检索，以及完整研究流程。三种运行使用相同模型和累计 token 上限，重复执行三次，记录逐题结果与差异。

| 指标 | 计算方式与发布条件 |
| --- | --- |
| 精确证据命中 | 按文档、章节和正文范围核查；原有已通过用例继续通过 |
| 主题归属准确性 | 抽取真实成员归属，检查其是否讨论主题范围及所述条件 |
| 观点覆盖 | 已被正确回答且有原文支持的必要观点数除以标注观点数 |
| 条件保留 | 标注的版本、前提、限制及不同观点在答案中的正确保留比例 |
| 引用准确性 | 引用摘录存在且支持对应陈述；检查到的无依据事实必须修正 |
| 导航效率 | 达到相同必要观点覆盖时，累计输入 tokens、原文读取量和调用次数 |
| 全库覆盖 | 实际处理的唯一来源单元与范围清单逐项核对 |
| 运行资源 | 构建与查询耗时、模型 tokens、向量计算量、collection 大小及峰值内存 |

完整流程在主题和关系问题上的平均必要观点覆盖必须高于当前系统；对精确问题、限定来源与未知问题的已通过用例逐题检查，新增失败全部处理。相同覆盖水平下，分层导航的累计输入 tokens 应低于逐次读取完整相关章节的基准。

质量指标和资源指标分别报告。聚类阈值与摘要长度在独立验证集上确定，最终评测集固定后不用于选择参数。以上条件属于发布目标，实际改善幅度以真实运行结果记录。

### 18.4 执行检查

实施完成后运行后端测试、Ruff、现有检索与问答评测、前端构建和实际服务上的 E2E。新增 E2E 覆盖主题浏览、成员分页、原文引用、构建恢复和全库覆盖显示。测试失败需要定位原因、修改实现并重新执行受影响检查。

所有新增集成与验收测试使用真实组件。数据与服务条件不足时明确报告尚未完成的检查，功能交付以完整验收记录为依据。

## 19 实施顺序与完成条件

依赖顺序为正文与身份、章节分析、主题与关系、分层检索、研究决策、界面与迁移、整体验收。每项完成后执行对应真实组件检查；发布要求全部交付项通过。

| 顺序 | 交付内容 | 完成条件 |
| --- | --- | --- |

## 20 研究过程示例

用户提问：“我保存的资料中，哪些方法可以改善 Agent 长期记忆？”

1. `RagResearcher` 选择 `theme`，绑定本轮知识版本与来源范围。
2. `search_knowledge` 返回涉及长期记忆、写入选择、更新与遗忘的导航候选。
3. `read_knowledge` 读取相关 L1，从资料中的条件和导航形成待核查问题。
4. 问题队列记录“选择哪些信息写入”“何时更新已有记忆”“哪些方法需要时间信息”等问题，每项关联用户要求与触发来源。
5. `list_members` 与主题范围搜索定位章节，`read_document` 读取方法、前提和限制的实际原文。
6. `explore_relations` 返回与当前问题有关的方法联系；需要形成跨来源推论时核查双方依据，并在结论中表达推论性质。
7. 覆盖检查核对每种建议的目标、条件与来源，继续处理影响结论的缺口。
8. 生成过程根据已核查的研究结果回答，引用具体原文，说明资料未能确定的适用条件。

若实际知识库只支持其中部分研究方向，研究记录保留其对应范围与缺口。示例中的方向由资料内容决定，研究动作通过结构化结果执行。
