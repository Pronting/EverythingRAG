# T4 向量库（Chroma）与本地嵌入（bge-m3）技术选型落地

## 1. Chroma 集成

**推荐**

- Python 客户端 `chromadb`，入口为 `PersistentClient(path=...)`，进程内嵌、持久化到目录。
- 持久化目录：`<用户数据目录>/vectorstore/`（如 `~/.everything-rag/vectorstore/`，Windows 为 `%USERPROFILE%\.everything-rag\vectorstore\`），与 `state.db`、`config.json` 同级，全部位于用户数据目录，满足「纯本地」。
- Collection 设计：**单一 collection**。名称含嵌入模型指纹与 schema 版本，如 `chunks__bge-m3__v1`（详见 §3 重建索引）。创建时在 collection metadata 里显式指定距离度量：`metadata={"hnsw:space": "cosine"}`（该参数只在创建时生效）。
- 距离度量：**余弦（cosine）**。bge-m3 / gte 均输出归一化向量，余弦与内积等价，但语义上余弦更直观、且不要求调用方自行归一化。
- HNSW 参数：**个人规模（≤100 万块）不做调优**，用 Chroma 默认；仅当实测 top-K 召回率不达标时才调整 `ef_search / M / construction_ef` 等（具体键名以官方 configuration 文档为准）。不要为了「看起来专业」预调参数，个人库的规模不值得。
- 隐私：关闭 Chroma 匿名遥测（`Settings(anonymized_telemetry=False)`，或环境变量 `ANONYMIZED_TELEMETRY=FALSE`，以官方文档为准）——遥测只含环境信息不含内容，但按「不出机」口径一律关闭，杜绝任何意外外呼。

**理由**

进程内 API 最简，`upsert/delete/query + where` 恰好覆盖 MVP 全部需求（来源标注要过滤、增量要按 ID 增删、重建要可切换）。Python 生态最顺，配合 §5 的幂等写入天然适配增量同步。个人库规模下其性能（§7）与 HNSW 默认参数绰绰有余，把调优成本省给功能本身。

**备选**

- **LanceDB**：进程内单文件、列存，可处理更大数据、开源分发更干净；API 表达力略弱。开源阶段（v1.0）经 `VectorStore` 接口评估切换。
- **Qdrant 本地模式**：过滤与性能最强，但需单独进程，违背 MVP 简单优先。远期评估。
- **SQLite-vec**：极端可嵌入单文件，但 HNSW 与增量维护需自研，MVP 不划算。

**边界**

- 锁定 Chroma 大版本（0.5.x 或 1.x 之一，以官方文档为准）。持久化目录格式跨大版本不保证兼容；升级走「重建索引」流程而非原地迁移。
- Chroma 是进程内库，**禁止多进程同时打开同一持久化目录**。后端 FastAPI 单进程 + 入库/问答共用同一 client 实例即可满足（MVP 单用户）。
- 所有访问收敛在 `VectorStore` 接口内，业务层禁止直接 import `chromadb`——切换 LanceDB/Qdrant 的成本被隔离在单点。

## 2. 元数据与 schema

**推荐字段集**（写入 `collection.upsert` 的 `metadatas`）：

| 字段 | 类型 | 必填 | 语义 / 示例 |
|---|---|---|---|
| `source_type` | str | 是 | `file`（普通 MD）或 `conversation`（对话导出） |
| `source_file` | str | 是 | 原始文件绝对路径（不拷贝文件，就地引用），溯源与级联删除用 |
| `platform` | str | 是 | `chatgpt / kimi / deepseek / local / unknown`；本地文档一律 `local`，**不用空值** |
| `conversation_id` | str | 否 | 对话去重键或会话标题，支撑「只看某对话」 |
| `role` | str | 否 | 对话块角色 `user / assistant / system / tool` |
| `time` | int | 是 | epoch 毫秒时间戳（对话块取消息/会话时间，普通块取文档 mtime），支撑时间范围过滤 |
| `heading_path` | str | 否 | 标题路径，如 `项目笔记>架构决策>技术选型` |
| `anchor` | str | 是 | 块锚点（block_id 的来源），增量同步判稳用 |
| `chunk_type` | str | 是 | `text / code / image_description` |
| `image_path` | str | 否 | 仅 `image_description` 块携带，原图路径只用于展示 |
| `doc_index` | int | 否 | 文档内块序号，排序 / 调试用 |
| `content_hash` | str | 否 | 块内容哈希，与状态库清单交叉校验（冗余） |

块的唯一 id = **block_id**（见 §3），放 Chroma 的 `id` 字段、不进 metadata。块原文放 `documents`（重嵌、Prompt 组装、展示复用）。

**Chroma 约束与设计要点**

- 元数据值仅支持 `str / int / float / bool`，**不支持 None / 空值**：可空字段要么省略该键、要么用字符串 sentinel（如 platform 缺失 → `unknown`）。这是「为什么本地文档 platform 一律写 `local`」的直接原因——过滤语义才能可预测。
- 来源标注（PRD §4.6）与「只看某平台」的检索支撑全部用 `where` 表达：
  - 只看某平台：`where={"platform": "chatgpt"}`
  - 平台 + 时间段：`where={"$and": [{"platform": {"$eq": "chatgpt"}}, {"time": {"$gte": t0}}]}`
  - 只看图片描述块：`where={"chunk_type": "image_description"}`
  - Chroma 支持的比较算子：`$eq / $ne / $gt / $gte / $lt / $lte / $in`，逻辑组合：`$and / $or`（以官方文档为准）。
- Chroma 元数据过滤是 HNSW **预过滤**：当过滤条件命中集很小而 `n_results` 固定时，可能返回**不足 K 条**。Prompt 组装必须容忍返回 `<K`（这正是「无结果/低置信」处理的输入之一，对齐 PRD §4.6）。
- 时间过滤依赖 `time` 为 int；不要存字符串时间（无法 `$gte/$lte` 比较）。

**理由**

一套字段同时服务三个诉求：来源标注（source_file/source_type/platform）、级联删除（source_file）、平台/时间过滤（platform/time）。`anchor` 与 `block_id` 分离：`block_id` 是 Chroma 唯一键（含文件指纹防跨文件冲突），`anchor` 是文档内稳定的语义锚点，两者配合实现 §3 的防漂移增量维护。

**备选 / 边界**

- 备选：把 platform/conversation 拆成多 collection（每平台一个）。**否决**：跨平台统一检索需多查多合、排序无法统一，与「一个统一向量空间」的产品内核冲突。
- 边界：metadata 字段若未来要加，需同步改 schema 版本号（collection 名中的 `vN`），避免新旧块字段不一致导致过滤漏匹配。

## 3. 按 ID 增量维护

**推荐**

- **block_id 生成**：`hash(归一化(doc_path))::anchor#相对序号`，对齐技术架构 §4.3 的 `hash(doc)::/H1/笔记方法/H2/检索#3`。anchor 由标题层级链 + 相对序号构成：
  - 内容变了 → 该块 `block_id` 不变、`content_hash` 变 → 只需 upsert 该块（局部修改只重嵌受影响块）；
  - 锚点被删除 → 删除该锚点下全部块；
  - 对话块 anchor 用 `dedup_key + 消息序号`（锚定对话而非文件，对齐 §4.5 对话级去重）。
- **upsert**：`collection.upsert(ids=[block_id], embeddings=[...], documents=[...], metadatas=[...])`。稳定 block_id 使 upsert **天然幂等**，重跑/重试安全。
- **delete（文件删除 → 级联删块）**：从 SQLite 切块清单取该文件全部 block_id → `collection.delete(ids=[...])` 分批删；再兜底 `collection.delete(where={"source_file": path})` 清掉清单外的孤儿，双重保险不留幽灵向量。
- **重建索引**（换嵌入模型或向量库异常，PRD §4.4）：
  1. 新建 collection `chunks__<new_embed_model>__v<schema>`；
  2. 从 SQLite 切块清单读出全部块的**块文本**（清单里存了文本，§6），批量重嵌入 → upsert 到新 collection（块与模型无关，**只重嵌、不重新切块解析**）；
  3. 全部成功后，更新 `state.db` 中的 `active_collection` 指针 → 应用只读新库 → 删除旧 collection。
  4. 效果：**重建期间旧索引全程可读**，满足 PRD §4.4 验收 #5「重建期间旧索引保持可读」。

**理由**

把「换模型」与「重嵌」解耦：切块结果与嵌入模型无关，所以重建不需要回到源文件重解析，只需把清单里的块文本重新嵌入。这既快又稳，且天然给出「旧索引可读」的方案——因为新旧是两个独立 collection，切换是指针级的。

**备选 / 边界**

- 备选：重建时直接删除旧 collection 再全量重灌。**否决**：不可读窗口长、失败无回退。
- 边界：`active_collection` 指针是唯一权威；任何检索/写入必须先解析指针再取 collection，禁止硬编码 collection 名。
- 边界：block_id 的 doc_path 哈希在「文件被移动后重新导入」场景下会生成新块（对齐 PRD §4.5 验收 #13「原路径移除 + 新路径新增」），这是预期行为，不是漂移。

## 4. 嵌入模型加载与性能

**推荐**

- **加载方式：fastembed（qdrant/fastembed，ONNX Runtime 后端，无 torch 依赖）** 加载 `BAAI/bge-m3`，1024 维。理由：安装体量小（不拖 ~2GB 的 torch）、惰性加载、原生批处理，与 Chroma 同属轻量进程内方案，最契合本地个人工具。
- **维度 / 量化**：默认 1024 维；推荐默认档为 int8 量化（fastembed `quantize=True`，ONNX 模型约 600MB），质量优先档为 fp32（约 2.2GB），做成配置项 `embed.quantize`。检索质量上 int8 损失对个人语料可忽略，v0.1 实测校准后定默认值。
- **批处理吞吐**：入库批量 `embed(文本列表)`（建议 32–128/批，CPU 上数百短文本/秒量级）；问答单条查询 `query_embed(问题)`（约 50–200ms，CPU，以官方/实测为准）。具体方法名以 fastembed 官方文档为准。
- **惰性加载**：`EmbeddingProvider` 为应用级单例，**首次实际调用**（首次入库或首次检索）才实例化并加载模型；冷启动不加载 → 满足启动 <5s（技术架构 §7）。模型驻留内存后不释放，避免问答抖动。
- **内存**：int8 约 600MB 常驻、fp32 约 2.2GB。8GB 机器默认 int8 档；4GB 机器切 `gte-multilingual-base`（768 维，约 1GB）兜底。
- **并发**：入库批嵌入与问答嵌入走同一 `EmbeddingProvider`，用线程池隔离（onnxruntime CPU 原生多线程），MVP 单用户无需多进程。

**理由**

与 PRD §3.3 的「运行层用 ONNX Runtime（sentence-transformers 或 fastembed）」一致，fastembed 是其中依赖最轻、加载最惰性的一条路，能同时兑现「安装轻」「冷启动快」「嵌入吞吐够」三个非功能目标。

**备选**

- **sentence-transformers**：功能全、任意 HF 模型、API 最简，但拖入 torch 重依赖（安装与内存成本高）。作为 `EmbeddingProvider` 的配置后端保留，给对模型自由度要求高的用户。
- **onnxruntime 直连**：最大控制（可同时取 bge-m3 的**稀疏向量分支**，为 v0.2 混合检索做一条模型两用），但需自写 tokenize + session + 归一化，工作量最大。v0.2 引入混合检索时再评估。
- 三者收敛在 `EmbeddingProvider` 接口后切换，默认 fastembed 不锁定架构。

**边界**

- 隐私澄清：模型权重**首次下载需联网一次**（从 HuggingFace 拉取，属模型安装，非用户数据出网）；下载后本地缓存，运行时零外呼。此网络面与「文本不出机」不冲突，但需在配置 UI 说明清楚。
- bge-m3 稀疏分支：fastembed 不直接暴露稀疏输出；若 v0.2 要走「一条模型两用」，需换 onnxruntime 直连或另备稀疏模型——记入 v0.2 决策点，不阻塞 MVP。
- 问题嵌入只整段嵌入，不切块（对齐技术架构 §6.1），MVP 不做长句拆分/改写。

## 5. 嵌入与向量库协作

**推荐**

- **同空间约束（问题嵌入必须与入库同一模型）三重保险**：
  1. 入库与问答都调用**同一个 `EmbeddingProvider` 单例**（同模型、同参数、同归一化开关），从根上杜绝「两条代码路径用了不同模型」；
  2. collection 创建时在 metadata 记录模型指纹：`{"embed_model": "BAAI/bge-m3", "dim": 1024, "space": "cosine"}`；
  3. 问答启动时校验 `config.embed_model == collection.metadata.embed_model`，不一致直接拒绝检索并提示重建索引（对齐 PRD §4.4 验收 #4）。
- **原子写入**：「向量 + 块文本 + 元数据 + 来源映射」在一次 `collection.upsert(ids=, embeddings=, documents=, metadatas=)` 调用内提交——Chroma 单调用为原子单元，四者要么一起进库要么一起不进。块数多时分批（如 ≤1000/批）多次 upsert，每批各自原子；不要跨调用散落同一块的四件套。
- **失败重试**：
  - 嵌入失败 → 记录失败块、不中断批次（对齐 PRD §4.2/§4.4），完成后可「仅重试失败块」；
  - upsert 失败 → 退避重试 ≤2 次，仍失败则该批块标记 `pending`、不提交清单，下次启动由对账补写；
  - 幂等 upsert 保证任意次重试结果一致。
- **跨库一致性顺序**：Chroma 与 SQLite 无法处于同一事务，固定顺序「**先 upsert 向量库 → 再提交 SQLite 清单**」。若第二步崩溃，残留由启动对账修复（§6）；不可反向（先提交清单后写向量，否则检索命中「清单里有但向量没了」的死块）。

**理由**

「同空间」是 RAG 正确性的地基，靠人工约束必翻车，所以做成「单例 + 指纹 + 启动校验」三道硬闸。原子性以 Chroma 单次调用为边界、幂等性以稳定 block_id 为基座，两者叠加让入库管线在个人场景下不需要分布式一致性机制。

**备选 / 边界**

- 备选：把块文本也落一份 SQLite 而不依赖 Chroma `documents`。不冲突——§6 正是这么设计的（清单冗余存文本），Chroma 的 documents 与清单文本互为备份。
- 边界：不做跨数据库分布式事务；一致性靠「顺序 + 幂等 + 启动对账」，这是个人本地工具的正确复杂度。

## 6. 与状态库（SQLite）协作

**分工边界**（哪些放 SQLite、哪些放 Chroma、哪些冗余）：

| 数据 | 权威位置 | 用途 |
|---|---|---|
| `files` 指纹表（path / mtime_ns / size / content_hash / status） | **SQLite** | 增量同步快慢路径（对齐技术架构 §4.1） |
| `conversations` 去重键表（dedup_key / file_path / last_seen / status） | **SQLite** | 对话级去重、`last_seen` 过期判定级联删（对齐 §4.2） |
| `chunks` 切块清单（block_id / anchor / content_hash / **块文本** / 所属文件 / 向量状态 / pending 标记） | **SQLite** | 增量决策中枢（哪些块该重嵌/删）、级联删、重建索引数据源、失败重试依据 |
| `task_logs` 任务日志 | **SQLite** | 进度 / 审计（脱敏） |
| `config`（含 `active_collection` 指针、嵌入模型指纹） | **SQLite** | 重建索引切换、同空间校验 |
| 向量 + 块文本/元数据副本 | **Chroma** | 检索执行体；块文本与元数据是清单的冗余副本，供 where 过滤、Prompt 组装、展示 |
| 块原始来源映射（block_id → 文件/对话/平台） | **两端冗余** | 溯源（PRD §4.4 验收 #6）；SQLite 侧为权威，Chroma 侧为副本 |

**要点**

- **决策中枢在 SQLite，执行体在 Chroma**：增量同步只读 SQLite（指纹、去重键、锚点判稳），判定出「要 upsert 哪些 block_id / 要删哪些」后，对 Chroma 发对应批操作。Chroma 本身不承载任何「决策」逻辑。
- **冗余的目的**：① 块文本两端各存一份，Chroma 挂了可以靠清单重灌，清单丢了可以靠 Chroma get 恢复（对账能双向修复）；② 用于一致性校验（对账比对 id + content_hash）。
- **对账规则（启动或同步结束时必经，不可跳过）**：枚举 Chroma 全部 id（`get(include=[])` 分批取）与清单 id 比对——
  - Chroma 有而清单无 → 删除（孤儿，通常是崩溃残留或外部修改）；
  - 清单有而 Chroma 无 → 用清单存的块文本重嵌入补写（修复 §5 的「先写库后提交」崩溃窗口）；
  - 相同 id 但 content_hash 不一致 → 以清单为准重嵌入。
- 去重键 / 指纹 **只写在 SQLite，不产生向量**：Chroma 只认最终落定的 block_id，天然幂等，与去重逻辑零耦合。

**理由**

指纹/去重/切块清单本质是「关系型决策数据」，SQLite 的事务与 SQL 表达力（`WHERE last_seen`、join 文件→块）远强于 Chroma metadata；向量检索是 Chroma 唯一擅长的。按「谁擅长谁权威 + 必要的双向冗余 + 启动对账」划分，复杂度与单机数据规模匹配。

**备选 / 边界**

- 备选：把清单也搬进 Chroma（靠 metadata 存全部字段）。**否决**：Chroma 不是关系库，缺 SQL、事务与一致性保证，增量决策会退化。
- 边界：对账必须是启动必经路径（可异步后台执行、不阻塞 UI，但不可配置为跳过），否则跨库不一致会静默积累。
- 边界：`chunks` 清单存块文本的磁盘成本 ≈ 语料文本量级，与向量体积（§7）相比可接受，换来的是「重建索引不重解析、对账可自动修复」。

## 7. 性能目标与边界

**可行性结论**

- 个人规模（1 万–100 万块）下 **检索 P95 <1s 完全可行**，实际远优于该值：Chroma 进程内 HNSW 在 ≤100 万向量上典型 top-K 查询为几十毫秒量级。落地目标对齐技术架构 §7：
  - 单次向量检索 P95 **<100ms**（≤100 万块）；
  - 完整问答链路「问题嵌入 → 上下文就绪」**<300ms**（主要开销是本地嵌入 50–200ms，向量检索毫秒级）。
- 内存边界：100 万块 × 1024 维 × fp32 ≈ **4GB 原始向量** + HNSW 索引开销，Chroma 需常驻内存。8GB 机器建议块规模控制在约 30–50 万以内，或切 768 维模型（gte，约 3GB）；超出评估向量量化（v0.2）或切换 LanceDB。
- 吞吐：入库以「批量化嵌入（32–128/批）+ 每批一次 upsert」为主手段，对齐 PRD §7 的 1 万字符/秒级目标。
- 同步快路径：只 stat 不读内容（对齐技术架构 §4.1），10 万文件 <3s；对账与指纹均为本地操作，不涉及网络。

**MVP 明确不做（边界）**

- **混合检索**（BM25 + 向量、RRF 融合）→ v0.2；届时 bge-m3 稀疏向量分支需单独评估（fastembed 不直接暴露，§4 已记）。
- **交叉编码器重排**（bge-reranker）→ v1.0。
- **L3 图像向量**（CLIP / ColPali）→ 远期调研项（技术架构 §2.4 已否决进入 MVP）。
- **PDF / 实时监听 / 跨源融合排序** → 见 PRD 范围，不属本期。
- 阶段一检索参数（对齐技术架构 §6.1）：默认 top-K=20 候选 / 取 8 入上下文；元数据过滤走 `where`；低于相似度下限明确告知「未检索到相关内容」，不硬凑答案。

**验收口径**

以上指标均为假设值（对齐技术架构 §7），需在 v0.1 用作者真实语料（≥100 篇 MD + ≥100 张图 + 若干导出对话）实测：检索 P95、内存峰值、导入吞吐、int8 vs fp32 召回差异。超界项决定降档模型 / 量化 / 切向量库。

## 8. 风险与待验证

| 风险 | 缓解 |
|---|---|
| Chroma 大版本升级导致持久化目录格式不兼容 | 锁定版本；升级走重建索引流程而非原地迁移 |
| fastembed 对 bge-m3 的 ONNX 导出/量化版本召回质量未验证 | v0.1 实测 int8 vs fp32 召回差异；保留 `embed.quantize` 开关 |
| int8 量化在专有名词/代码等重召回场景退化 | 保留 fp32 档；v0.2 引入混合检索补字面命中 |
| Chroma HNSW 预过滤在极小命中集下返回不足 K 条 | Prompt 组装容忍 `<K`；对「无结果/低置信」显式处理 |
| 跨库（Chroma + SQLite）崩溃残留 | 固定写序（先库后清单）+ 幂等 upsert + **启动必经对账** |
| 换模型后误用旧向量 | collection 指纹 + 启动强校验 + 一键重建（§5 三道闸） |
