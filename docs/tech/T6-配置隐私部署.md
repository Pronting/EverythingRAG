## 1. 配置中心设计

### 1.1 存储格式与 schema

**推荐：`config.json`（JSON），配合 pydantic v2 `BaseModel` 单源校验 + `schema_version` 字段 + 原子写。**

理由：
- 既有技术方向已定 `config.json`（04-架构 §1.4），不推翻，只细化。
- pydantic v2 对 JSON 有原生往返（`model_validate_json` / `model_dump_json`），TOML 无原生支持；JSON 解析比 TOML 宽容（TOML 对非法字符/重复键严格），配置由 UI 生成而非手写，宽容性更抗坏数据。
- JSON 零第三方依赖（`json` 在 stdlib）；`tomllib` 虽在 3.11+ stdlib，但 pydantic 侧无原生桥接。

备选：
- **TOML**：可读性/注释更好，适合「用户手改」型配置。本项目配置 95% 由向导/设置页生成，不手改，收益用不上；留作 `schema_version=2` 的迁移备选。

边界与落地细节：
1. **原子写**：写入先写 `<config>.tmp` 再 `os.replace` 原子替换，防中途崩溃产生半截 JSON。
2. **schema_version**：`schema_version: 1` 置于顶层；加载时低于当前版本走迁移函数链（`migrate_0_to_1(...)`），未知更高版本拒绝加载并给出「配置文件来自更新版本」提示，避免回滚损坏。
3. **配置导出/导入**：设置页提供「导出配置」——导出前**脱敏**（key 一律替换为 `api_key_ref` 引用文本，不导出实际密钥）；导入时校验 schema + 回填缺省。
4. **目录可移植性**：config.json 内路径一律**相对 data_dir**（`~/.everything-rag/`）存储，不存绝对路径，移动数据目录即整体搬迁。

### 1.2 配置校验（pydantic）

**推荐：两层校验 —— ① 结构校验（每次加载/保存，必过）② 可达性校验（保存时，失败阻止保存）。**

- 结构校验：`AppConfig`（顶层）+ `ModelConfig`（嵌入/对话/识图共用基类）+ `FeatureConfig`；用 `Field` 约束（枚举 provider、`model` 非空、`base_url` 为 http/https 等）。加载时 `model_validate`，失败 → 落到默认配置 + 标记「配置不完整」，引导进向导，绝不崩启动。
- 可达性校验（对应 4.7#8「校验配置可达性；失败阻止保存无效配置」）：
  - 本地 ollama/llama.cpp：`GET {base_url}/api/tags` 确认端点活 + 模型在列。
  - 云端 OpenAI 兼容：对 `{base_url}` 发最小探测（`/models` 或一次 0-token 请求），校验 base_url 可达 + key 有效。
  - 失败 → 返回可读错误（区分「网络不可达」「认证失败」「模型不存在」），阻止保存。
  - **边界/例外**：用户离线场景（如只读备份机）无法连通云端也应能保存配置 → 提供显式「跳过连通性校验直接保存」次级按钮，勾选后允许保存但标记 `pending_reachable_check`。此为对 PRD「阻止保存」的受控例外，需在产品评审确认。

### 1.3 三模型配置字段设计

**推荐：每个模型统一五件套 `provider / base_url / model / api_key_ref / api_key_hint`，云本地共用一套 schema，靠 `provider` 分支。**

```json
{
  "schema_version": 1,
  "data_dir": "~/.everything-rag",
  "embedding": {
    "provider": "local",                      // "local" | "cloud"（嵌入 MVP 只允许 local）
    "local": { "engine": "onnx|ollama", "model": "bge-m3", "dimensions": 1024 },
    "cloud": { "base_url": "", "model": "", "api_key_ref": "", "api_key_hint": "" }
  },
  "chat": {
    "provider": "local",                      // 默认 local
    "local": { "engine": "ollama|llamacpp", "model": "qwen2.5:7b", "base_url": "http://127.0.0.1:11434" },
    "cloud": { "base_url": "", "model": "", "api_key_ref": "", "api_key_hint": "" }
  },
  "vision": {
    "enabled": false,                         // 识图=功能开关
    "provider": "local",
    "local": { "engine": "ollama|llamacpp", "model": "qwen2.5vl:7b", "base_url": "http://127.0.0.1:11434" },
    "cloud": { "base_url": "", "model": "", "api_key_ref": "", "api_key_hint": "", "cloud_consent": false }
  },
  "features": { "image_processing": false, "cloud_qa_image_enhance": false },
  "privacy": { "audit_enabled": true, "log_level": "INFO", "collect_usage_stats": false }
}
```

字段说明：
- `provider`：切换位（见 §3）。
- `base_url`：OpenAI 兼容端点；本地 ollama 即 `http://127.0.0.1:11434`，云端即厂商端点。本地/云端同一 Provider 代码，仅改 base_url（对齐 04-架构 §2.1/§3.4）。
- `model`：模型名（本地为 ollama 标签/GGUF 路径，云端为 API model id）。
- `api_key_ref`：**密钥引用**（见 1.4），绝不存密钥值本身。
- `api_key_hint`：脱敏展示用提示串（如 `…abcd`），非密钥。
- `cloud_consent`（vision/chat 专属）：云端启用确认标志，见 §3.3。

边界：
- **嵌入模型 MVP 仅允许 `local`**（04-架构 §3.3：云端嵌入会破「文本不出机」，仅作为将来隐私要求低用户的显式可选，且默认关）。schema 仍预留 `cloud` 分支便于未来加，但 UI 不展示、保存时校验强制 `local`。
- **嵌入模型全局唯一必配**（04-架构 §3.3：问答问题嵌入必须与入库同模型）。`embedding` 是单一对象而非数组，从 schema 层杜绝双嵌入模型。

### 1.4 key 引用与来源

**推荐：三层来源，`api_key_ref` 用前缀标记来源，运行时经 `SecretStore` 解析。**

| 来源 | `api_key_ref` 值 | 持存位置 | 生命周期 | 使用场景 |
|---|---|---|---|---|
| 环境变量（首选） | `env:EVERYTHING_RAG_CHAT_KEY` | 进程环境 | 由用户在自己的启动器/系统环境设置 | 命令行启动、CI、脚本化 |
| 内存（次选） | `memory:set` | `SecretStore`（仅内存） | 本次进程；重启后失效 → UI 引导重填 | 设置页录入、掩码展示 |
| 系统钥匙串（v0.2 可选） | `keyring:everything-rag/chat` | OS Keychain/DPAPI | 持久但系统托管 | 有系统钥匙串偏好用户 |

- `SecretStore`：进程内单例，`ref -> value` 映射；config.json 只存 ref + hint。解析失败（如 env 未设、memory 重启丢失）抛 `KeyMissingError` → Provider 层返回「缺少 key」可读错误，UI 引导补录。
- 环境变量命名规范（对齐 04-架构 §5.3 的 `EVERYTHING_RAG_OPENAI_KEY` 示例，落定为按角色）：`EVERYTHING_RAG_CHAT_KEY`、`EVERYTHING_RAG_VISION_KEY`、`EVERYTHING_RAG_EMBED_KEY`（预留），另设通用兜底 `EVERYTHING_RAG_API_KEY`（缺角色变量时回退给 chat）。
- **写入安全**：config.json 权限收紧（POSIX `0600`）；因不含密钥，即使读漏也不泄露 key——密钥只在内存/环境/钥匙串，落盘零密钥是本设计的核心。

备选：
- 单一 `env:` 来源最简，但「设置页手填」被排除，不符合非技术用户；`keyring` 上 MVP 会引入平台依赖，故后置。

### 1.5 配置变更的连带影响处理

**核心规则：只有「嵌入模型」变更会触及向量空间，其余模型变更不影响既有向量。**

| 变更 | 对既有数据影响 | 处理 |
|---|---|---|
| 嵌入模型（provider/engine/model/dimensions 任一变化） | **向量空间不兼容**（04-架构 §3.3 硬约束） | 触发重建索引闸门（见下） |
| 对话模型 | 无向量影响 | 仅清空会话上下文缓存，防历史轮次上下文与新模型不一致 |
| 识图模型 / 识图开关 | 无向量影响；关闭后既有 `image_description` 块保留（4.7#5） | 仅影响后续入库；关闭时不清库 |
| 对话/识图 provider 本地↔云端 | 无向量影响 | 触发隐私 consent 流程（§3.3） |

**重建索引闸门设计（推荐）：**
1. 计算 `embedding_identity = sha256(provider|engine|model|dimensions|模型文件版本)`，存 state.db。
2. 保存嵌入配置时比对新旧 identity；不同 → 返回「需重建索引」响应，UI 弹窗：说明「换嵌入模型后向量空间不兼容，需全量重嵌，预估耗时 X」。
3. 用户选择「立即重建」→ 后台任务全量重嵌 + 进度条（复用 4.4 重建索引能力）；完成前**阻塞检索与入库**并给出明确「正在重建索引」提示（对齐 4.4#5 二选一中的「给出明确的不可用提示」）。
4. 用户选择「暂不重建」→ 同样处于阻塞态（无可用向量空间），直至重建完成。

备选：重建期间**旧索引保持可读**（需进程内同时保留新旧两个嵌入模型，检索走旧模型直到重建完成）——内存/显存成本高、逻辑复杂，MVP 不取；留作 v1.0 优化项。

## 2. 配置向导流程

### 2.1 分步与状态机

**推荐：5 步向导，状态机常驻后端，进度落 `state.db`，前端仅渲染。**

```
WIZARD_NOT_STARTED
   │  启动时 config_is_ready_for('core')==false
   ▼
STEP1_SELECT_DIR ──► STEP2_EMBEDDING ──► STEP3_CHAT ──► STEP4_VISION ──► STEP5_PREVIEW ──► WIZARD_DONE
                        （必配）           （必配）        （条件性）         （确认）
```

- 每步一个后端接口：`GET /api/wizard/state`（恢复进度）、`POST /api/wizard/step`（提交单步，后端校验后持久化并返回下一步）。前端无状态，刷新/关页不丢进度。
- 每步完成后写 `state.db` 的 `wizard` 表（`step_no, payload, status`）；**config.json 只在向导整体完成后写入完整合法配置**——这样 config.json 永远是「完整配置」的单一事实源，向导中间态不进 config.json，避免半配置污染。
- 步骤互锁：未完成 step1 不能进入 step2；后端按状态机顺序校验 `current_step`，非法跳步返回 409。

### 2.2 跳过逻辑

- **识图步跳过**：进入 STEP4 时，先展示「是否启用图片识别功能？」开关（对应 4.7#3）。
  - 关 → 直接标记 STEP4 完成（`vision.enabled=false`），纯文本闭环，**跳过识图模型配置**。
  - 开 → 才展开识图模型配置（含 provider / 模型），并在此处注入云端隐私提示（见 §3.3）。
- **二次进入向导**：已完成的步骤跳过、直接落在第一个未完成步骤（断点续传）。

### 2.3 配置完整性校验与半配置状态

**推荐：双档就绪判定 `config_is_ready_for(scope)`，任何非核心功能都不得进入「核心不可用」状态。**

```python
scope = "core"   # 搜索 + 同步入库：要求 embedding 完整 + chat 完整
scope = "image"  # 图片入库：要求 vision.enabled==False 或 vision 完整
```

| 状态 | 行为 |
|---|---|
| core 未就绪（启动检测） | 阻塞整个应用 → 强制进入向导（从断点恢复）；**不提供「跳过」逃逸**（4.7#10） |
| core 就绪、image 未就绪 | 应用正常使用；图片入库入口显示缺失提示并阻塞（4.7#4）；问答与文本同步不受影响 |
| 保存配置时校验失败 | 阻止保存 + 可读错误（见 §1.2 结构/可达性两层） |

边界：
- 「半配置状态不可用」的落点是**启动时**而非运行时：运行中把对话模型配置改坏（如 key 失效）不应强杀应用，而是「问答功能降级为不可用 + 引导修复」，同步/检索仍可用；只有嵌入模型缺失才全局阻塞（因为检索依赖嵌入）。

### 2.4 配置完整性校验的字段级判定

- embedding 完整 = `provider` 合法 + `local.model` 非空（或 `cloud` 分支完整 + key 可解析）。
- 每个字段的「是否必填」跟随 `provider` 分支联动：`provider=local` 时不要求 `api_key_ref`；`provider=cloud` 时必填。
- 后端统一用 pydantic 的 `model_validator(mode="after")` 做跨字段校验（如「cloud 必带 key_ref」），单点实现，前端同步显示由 API 错误回传驱动，不重复实现。

## 3. 本地/云端 provider 切换

### 3.1 切换位实现

- 数据模型：每个模型配置的 `provider: "local" | "cloud"` 字段（§1.3），UI 为卡片内「本地 / 云端」分段控件。
- 切换只改配置 + 触达性校验 + consent 流程，不改 Provider 代码——本地与云端共享同一 `ChatModel`/`VisionModel` 抽象，差异只是 base_url + 是否走 `OutboundClient`（04-架构 §3.4）。
- **切换即校验**：切到云端立刻跑一次连通性探测（§1.2），失败当场报错，不落到 config。
- 后端路由规则：`provider=cloud` 的模型必须满足「key 可解析 + cloud_consent=true」才可调用（§3.3）；否则返回 409 类错误，绝不静默降级到本地（防「以为在本地其实出网」的错觉）。

### 3.2 云端 key 管理（不落明文）

设计同 §1.4：环境变量注入（首选）/ 内存持有（掩码展示）/ 钥匙串（v0.2）。

- **掩码展示**：设置页与审计面板一律显示 `sk-…abcd`（取尾 4 位）；`api_key_hint` 由后端在保存时从明文计算尾 4 位，config 不存明文。
- **重启恢复**：`memory:` 来源重启丢失后，config 中 `api_key_ref` 保持 `memory:set`，前端显示「密钥已清除（内存持有）」，引导重新填写；环境变量来源则每次启动自动解析。
- **永不回显**：`GET /api/config` 与任何导出均不含明文 key；写盘只在 `SecretStore` 初始化时接收一次明文，之后所有层只传 ref。

### 3.3 隐私影响提示与二次确认的实现位置

**推荐：两层机制 —— ① UI 前置提示（inform）② 后端强制 consent（enforce）。二次确认是后端强制而非 UI 建议。**

1. **提示层（设置页 + 向导 STEP4）**：
   - 切换 `provider` 到云端时，卡片内联展示隐私卡：「使用云端 {对话/识图} 模型时，{用户问题+检索上下文 / 图片} 将发送至 {base_url 域名}」。
   - 识图（图片出网）必须**显著**提示（4.7#7），用高对比警示色 + 「图片将离开本机」字样。
2. **确认层（模态二次确认）**：
   - 弹窗要求用户勾选「我已了解：{具体外发数据} 将发送至 {域名}」复选框 + 点「确认启用」。
   - 确认成功后后端写 `cloud_consent=true`（chat/vision 各自独立标志）。
3. **强制层（后端）**：
   - `ChatModel`/`VisionModel` 路由前校验：`provider=cloud 且 cloud_consent!=true` → 拒绝调用返回 409「需先完成云端启用确认」。此校验在后端，任何绕过 UI 的请求都被拦——这是「显式 opt-in」的落地强制点。
   - 即便用户已设置环境变量（§1.4），只要 consent 未给，后端也拒绝出网路由 → **杜绝「配了 env 就意外出网」**。
   - 已 consent 后若再次切回本地再切云端，**重置 consent** 要求重新确认（防止「记不清自己开过」）。

边界：
- 嵌入模型无云端分支，无 consent 流程。
- v0.2「问答时喂原图」增强默认关闭，开启时同样走 vision 的 consent 路径并单独显著提示（04-架构 §2.3）。

## 4. 网络审计面板

### 4.1 审计实现层次（统一出口收敛）

**推荐：出网收敛在唯一 `OutboundClient`（httpx 自定义 Transport + 审计记录），代码审计 + 测试期 lint 双保险。**

- 唯一出口：所有非回环出网请求必须经由 `OutboundClient`（`app/net/outbound.py`），内部用 httpx 自定义 `Transport` 在每次请求发出前/收到后写审计事件。`ChatModel`/`VisionModel` 通过依赖注入拿到该 client，除此之外**禁止任何模块** import `requests`/`urllib`/`aiohttp`/裸 httpx。
- 强制方式：
  - 运行时：Provider 构造强制注入 audited client；未注入即抛错（fail-fast）。
  - 测试期：CI 加一个静态检查（ruff/grep），扫描 `import requests|urllib|aiohttp` 出现在 `net/` 之外即失败。
  - 该收敛与 04-架构 §5.2「出网流量只可能来自 ChatModel/VisionModel 两个 Provider」一致，且比文档更进一步：把「两个 Provider」落实为「一个 OutboundClient」。
- **模型下载也是出网**：首次跑本地嵌入需下载 bge-m3（~2GB），这是用户显式发起的一次性外发，同样走 OutboundClient 并记入审计（`data_type=model_download`），保证「默认零外发」的断言真实而非掩盖。

### 4.2 记录 schema 与事件类型

审计表 `outbound_events`（放 state.db 或独立 `audit.db`，推荐独立库避免与状态库职责混杂）：

```sql
outbound_events(
  id INTEGER PK,
  ts TEXT,                -- ISO 时间戳
  provider_role TEXT,     -- chat | vision | embed | model_download
  provider_name TEXT,     -- 配置中的模型名（非密钥）
  url_host TEXT,          -- 出网域名（记录域名即可，不记录完整含参 URL）
  data_type TEXT,         -- question_context | image | chat_answer | model_download
  item_count INTEGER,     -- 发送的切块/图片数
  bytes_out INTEGER, bytes_in INTEGER,
  status TEXT,            -- ok | error
  error_code TEXT         -- 非敏感错误码
)
```

- 触发点：在 Transport 层记录**每次**非回环请求（成功与失败都记）。
- 边界：不记录请求/响应正文（防审计日志本身变敏感面）；只记「类型 + 数量 + 字节 + 目标域名 + 时间」。

### 4.3 展示与默认零外发断言

- **聚合视图**：按 provider 汇总（总调用次数、总出站字节、最近使用时间）。
- **时间线视图**：「何时 → 去了哪（域名）→ 发了什么类型 → 多少数据量 → 结果」，列表倒序。
- **默认零外发断言（非装饰，是计算）**：
  - 后端提供 `GET /api/privacy/status`：扫描当前 config，若全模型 `provider=local` 且无待下载模型 → 断言 `outbound_calls_total==0`（结合审计表核对），返回「本机零外发」。
  - 前端面板据此渲染绿色徽章「本机零外发」；一旦有任何云端配置或出网事件，徽章切换为「有数据外发：N 次」并高亮时间线。
  - 同时面板展示「系统自身无遥测 / 无自动更新检查 / 无外部依赖调用」的静态承诺（MVP 不内置任何遥测 SDK；依赖升级由用户手动 pip，模型下载由用户显式触发）——与审计数据共同构成可核验的「数据流向视图」（4.8#8）。

边界：
- 回环流量（127.0.0.1）不记入审计（本地 ollama/前端静态资源），避免噪声。
- 审计表提供「清空」操作并入「删除知识库」的二次确认流程（4.8#4 删除时一并清除）。

## 5. 日志脱敏

### 5.1 日志分级与格式

**推荐：stdlib `logging`，四级（ERROR/WARNING/INFO/DEBUG），默认 INFO；自定义 `RedactingFormatter` 在日志边界统一脱敏。**

- 零第三方依赖（`loguru` 为可选备选，MVP 不需要其额外能力）。
- 格式建议 `key=value` 或 JSON（DEBUG 用 JSON 便于机器解析），字段仅结构化事件（事件名、数量、耗时、错误码、模型名），对齐 04-架构 §5.3「仅记录结构化事件」。
- 日志落盘 `~/.everything-rag/logs/` + 控制台双写；`log_level` 走配置（隐私设置内），DEBUG 也经过同一脱敏管线。

### 5.2 脱敏规则

**推荐：脱敏在 Formatter 边界强制生效，任何日志消息都不可绕过。**

`RedactingFormatter` 对每条消息执行：
1. **密钥模式**：`sk-`、`Bearer `、`api_key=`、`Authorization:` 头值 → `<redacted-key>`。
2. **路径脱敏**：用户数据目录 / 导入目录下的任何绝对路径 → `<redacted-path>`；**文件名也不输出**（对齐 4.8#6，见 §5.5 冲突消解）。
3. **URL 参数**：query 中含疑似密钥参数名（`key`/`token`/`secret`）的值 → `<redacted>`。
4. **超长正文**：疑似 base64/长文本片段截断到 ≤64 字符（debug 输出文本时截断，对齐 04-架构 §5.3）。
5. 用非敏感 **`file_id`**（state.db `files` 表行 id）替代路径/文件名：可本地反查、不可外泄敏感信息。

### 5.3 错误信息边界

- **后端 API 错误响应**：返回 `error_code + 简短人类可读信息`，**不回显 provider 响应体 / 请求 payload / base64 图片**（04-架构 §5.3）。完整细节只进日志，且日志已脱敏。
- 云端调用失败时：只回传「服务商返回 401 认证失败 / 429 限流」级别的归类，不打印原始响应 JSON。
- UI 层：错误 toast 展示与 API 响应一致，不含敏感字段。

### 5.4 一键清除日志

- `DELETE /api/logs`：截断/删除当前日志文件；设置页「清除日志」按钮触发，无二次确认（日志本已脱敏，误删无碍），但并入「删除知识库」二次确认流程以清除审计与任务日志相关内容（4.8#4）。
- 可选增强（v0.2）：设置「退出时自动清空本次会话日志」。

### 5.5 文档冲突消解（必须显式记录）

- **冲突**：04-架构 §5.3 允许日志含「块/文件路径」；03-功能需求 §4.8#6 **禁止**「源文件路径、文件名」。二者矛盾。
- **裁决**：以更严格的 03-功能需求为准（用户可见承诺，且是 4.8 验收标准原文）。默认级别（INFO）不输出任何路径/文件名；DEBUG 下若要输出**目录名/文件名（basename）**，须用户在隐私设置显式开启「debug 日志包含文件名」，且仍不输出完整绝对路径。此冲突与裁决写入验收清单，供实现阶段对账。

## 6. 本地 Web 服务部署

### 6.1 启动入口与随机端口

**推荐：`run.py`（或 `python -m everything_rag`）单入口；端口用「先占 0 取号、后传给 uvicorn」的方式随机分配；记录上次端口以便复用。**

- 随机端口分配：
  1. `socket.socket(); bind(('127.0.0.1', 0)); port = sock.getsockname()[1]; close()` 取一个空闲端口（单用户本地场景竞争窗口可忽略）。
  2. 以该 port 启动 uvicorn；若端口恰被占用（极端竞态），捕获启动失败并重试一次（重取号）。
  3. 将端口写入 `~/.everything-rag/run.port`：下次启动优先复用该端口（若仍空闲），用户浏览器书签/快捷方式地址稳定；被占用则换新随机号并更新文件。
- 绑定地址**仅 `127.0.0.1`**，绝不 `0.0.0.0`（04-架构 §3.5/§5.4）；MVP 不做局域网访问。
- 启动输出打印 `http://127.0.0.1:{port}` 大字号提示。

备选：
- uvicorn `port=0` 原生随机 + 解析启动日志取端口：可行但需解析日志，不如预取号直接。不做端口持久化文件则用户每次地址都变，体验差，故加 `run.port`。

边界：
- Windows 首次监听：python.exe 可能触发防火墙弹窗/杀软扫描。回环绑定一般无需放行规则，但杀软对监听进程的提示无法完全避免——作为已知 UX 瑕疵记录，PyInstaller 打包为正式 exe 后（§7）此问题显著缓解。

### 6.2 静态前端托管与浏览器自启

- **托管**：FastAPI 挂 `StaticFiles(directory="static", html=True)`，API 路由在静态之前注册。SPA 路由用 **hash 路由**（前端 HashRouter）→ 免去服务端 history fallback，MVP 最简；若未来改 history 路由，再加 catch-all `GET /{path:path}` 回 `index.html`。
- **自动开浏览器**：服务 ready 后用 stdlib `webbrowser.open(f"http://127.0.0.1:{port}")`；提供 `--no-browser` 参数（无头/脚本场景）。启动动画期间先开浏览器属正常，首页加载即完成。
- **优雅退出**：`Ctrl+C` 捕获 → uvicorn shutdown → 关闭线程池 → 落盘未决状态（幂等设计保证中断可重入，04-架构 §7）。

### 6.3 Windows 首发脚本

**推荐：`install.ps1`（venv + 依赖安装）+ `start.bat`（启动器），双保险。**

- `install.ps1`：
  1. `py -3 -m venv .venv`（用 `py` launcher 规避 PATH 缺 python 的问题）；
  2. `.venv\Scripts\python -m pip install --upgrade pip`；
  3. `.venv\Scripts\pip install -r requirements.txt`（锁 lockfile，04-架构 §5.4）；
  4. 打印「安装完成，双击 start.bat 启动」。
- `start.bat`：`.venv\Scripts\python run.py` + 暂停提示。
- 补充 `start.sh`/`install.sh`（bash）作为 macOS/Linux 目标的最小配套（后续发布目标）。
- 边界：PowerShell 执行策略可能阻止 `.ps1` → `start.bat` 提供 `powershell -ExecutionPolicy Bypass -File install.ps1` 的提示或直接以 bat 完成安装（bat 版更稳，二者都给）。

### 6.4 进程模型

**推荐：MVP 单前台进程（控制台常驻），不做守护/托盘。**

- 理由：单用户、单进程（FastAPI + asyncio + 线程池）满足全部 MVP 负载（04-架构 §3.1/§7）；前台控制台可见日志、Ctrl+C 即停，调试直观。
- 未来演进（不做于 MVP）：`--daemon`/开机自启/托盘最小化均属桌面壳能力，交给 Tauri（§7）。
- 边界：关闭控制台即停服务——MVP 可接受，文档明示「关闭本窗口即停止」。

### 6.5 开机自启（MVP 不做）

- 明确**不做**：本形态（Web 服务 + 控制台）做自启需注册 Windows Startup 快捷方式/注册表 + 无托盘意味着用户无法在后台管理，收益低、风险面大。
- 归属：Tauri 壳（v1.0+）以原生 `autostart` 插件实现；届时默认关闭、设置内开启。
- 替代：MVP 提供「生成桌面快捷方式」一次（可选），不自启。

## 7. 开源打包评估

### 7.1 打包路径对比与推荐

| 路径 | 包体/资源 | 复杂度 | 原生能力 | MVP 后顺序 |
|---|---|---|---|---|
| **脚本启动（现状）** | 零包体 | 最低 | 无 | 立即（MVP 就是它） |
| **PyInstaller onedir** | ~40–80MB（含 Python+FastAPI+静态资产） | 低 | 无托盘/自启 | **v1.0 短程**：Windows「下载即双击」 |
| **Tauri + Python sidecar** | 安装包 ~10–30MB（不含 Python 运行时则更小） | 高（Rust 工具链 + Python 侧车打包） | 原生窗口/托盘/自启/自动更新 | **v1.1+ 中程**：三平台正式分发 |
| Electron | ~100MB+，高内存 | 中高 | 同 Tauri | 不推荐 |

**推荐：MVP 用脚本 → v1.0 短程用 PyInstaller（onedir）桥接 Windows → v1.1+ 迁移 Tauri + Python sidecar。**

理由：
- 短程选 PyInstaller onedir（非 onefile）：onedir 启动快（免解压）、杀软误报率低于 onefile；加一个 NSIS/innosetup 简单安装包即可「下载→安装→双击」。
- 中程选 Tauri 的原因：① 包体与内存显著优于 Electron；② 原生托盘/开机自启/自动更新（`tauri-plugin-autoupdater`）正好补齐 MVP 缺失的桌面体验；③ 前端可 100% 复用 Web 版（04-架构 §3.5 已保证前端不被锁死）。
- **关键复杂度 = Python 后端的侧车打包**：推荐用 `python-build-standalone`（astral）运行时 + PyInstaller 把 FastAPI 后端打成单文件 sidecar，经 Tauri `externalBin` 内嵌；或直接以 PyInstaller exe 作为 sidecar。此为本路径最大的技术风险点，需在 v1.0 末尾做 spike 验证。
- Electron 的 Node 生态对 Python RAG 栈无增益，纯为壳，成本高于 Tauri，排除。

边界：
- **模型权重绝不打进安装包**（见 7.2）：安装包体积与许可双受益；bge-m3 等由「模型下载助手」在用户显式触发下从官方源拉取（记入审计面板）。
- PyInstaller 已知坑位（需 spike）：chromadb（含 onnxruntime、sqlite）、FastAPI/uvicorn 的 hidden-import；`--collect-all` 处理静态资产与 `data_dir` 默认值。
- 自动更新属出网行为：上线时必须在审计面板登记、默认关闭或显式 opt-in（守护「零外发」承诺）。

### 7.2 模型权重与产物边界

- 产品代码（Python + 前端 + 安装器脚本）→ Apache-2.0。
- **模型权重是独立资产**，各按其 License 分发，与产品 Apache-2.0 无必然关联（04-架构 §3.5）。本产品定位「个人工具」，**不主张对模型权重的再许可**——只是「引用/帮助下载」。
- 落地规则：
  1. **默认推荐/内置下载的模型必须宽松许可**（Apache-2.0 / MIT）。如 bge-m3、Qwen2.5-Instruct、Qwen2-VL、gte-multilingual 等；具体许可以各官方仓库为准（个别版本存在 CC-BY-NC 历史，如部分 Qwen-VL 早期版本、MiniCPM-V 早期版本 → 严禁默认捆绑）。
  2. 模型配置面板**逐项展示每个模型的 License**（拉取自本地模型清单），用户下载前确认。
  3. 「模型下载助手」只列出宽松许可模型；非商用模型一律不提供一键下载入口，仅在高级区显示名称+许可证供知情自取。
  4. 安装包不捆绑任何权重（体积 + 许可双重原因）。

### 7.3 Apache-2.0 合规注意

- 产品包根目录放 `LICENSE`（Apache-2.0）与 `NOTICE`（保留第三方声明）。
- 依赖许可审计：`pip-licenses` 生成依赖许可清单并入库（CI 检查）。重点规避 **AGPL/GPL 传染性依赖**混入主程序；Apache 许可本身允许兼容 GPL 依赖单独使用，但分发捆绑时需清晰区分。
- 已知生态对照（04-架构 §3.5）：chromadb/sentence-transformers/fastembed 等 RAG 主流依赖为宽松许可，风险低；仍以 lockfile + `pip-licenses` 实测为准。
- 修改他人代码的 Apache 文件需保留其 `NOTICE`/版权声明（Apache-2.0 §4 义务），在项目 NOTICE 中集中列出。
- 社区化义务：开源后接受 PR 需在合并前跑依赖/许可扫描，防止贡献者引入传染性依赖。
