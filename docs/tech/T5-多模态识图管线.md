# T5 多模态识图管线 —— 技术选型决策文档（方案 B）

> 定位：确定「Everything RAG」图片识图管线（方案 B）的技术选型细节与边界。
> 生成日期：2026-08-11 ｜ 状态：v0.1 待评审 ｜ 责任角色：多模态工程师（T5）
> 前置约束（**本文档无权推翻，只细化落地细节与边界**）：
> - 方案 B 为检索主干：图片 → 多模态识图模型 → 文字描述 → 与文本**同一嵌入模型、同一向量空间**；原图路径进元数据（仅展示，不复制图片）。
> - 识图模型：本地 VLM 为默认（Qwen2-VL / MiniCPM-V 方向，经 Ollama / llama.cpp 的 OpenAI 兼容端点）；云端 OpenAI 兼容 VLM 为**显式可选**；识图是**功能开关**（不开图片功能就不用配）。
> - 识图只在入库时发生一次；问答默认不调识图；v0.2「喂图增强」是叠加增强，不替代 B。
> - 纯本地数据不出机（本地识图不出机；云端识图图片出网需显式 opt-in + 二次确认）。
> - MVP 不做 L3 图像向量（CLIP）、不做 ColPali。
> - 型号/量化/许可/价格的具体数值**以官方文档为准**，本文件给出的推荐基于架构权衡。
>
> 关联文档：PRD §04 技术架构（§2 多模态、§3.4 对话模型、§3.5 开源许可、§5 隐私安全）、§03 功能需求（§4.3 图片处理、§4.7 模型配置、§4.8 隐私安全）。

## 0. 背景与既定约束（回顾）

- 识图发生在**入库阶段**，是「入库一次、检索多次」原则下唯一的重型计算节点之一：一次性、可异步、无延迟敏感。
- 检索要的是「能搜到」（召回），不是「描述完美」；本地 4–8B 级 VLM 生成的文字描述对检索召回质量足够。
- 识图模型与对话模型在 §3.4 已定为统一「OpenAI 兼容」抽象，本地（Ollama/llama.cpp）与云端只是不同 `base_url`。
- 图片描述块继承所在文档/对话的元数据（平台/来源/时间），保证来源标注一致。
- 本文七项决策彼此耦合：Provider 抽象（§3）决定接入方式（§2）与隐私模型（§7）；Prompt 模板（§4）决定入库产出质量（§5）；元数据（§6）决定展示闭环。

## 1. 决策速览

| # | 决策点 | 推荐 | 一句话理由 |
|---|---|---|---|
| 1 | 本地 VLM 接入 | 对接用户已装的 Ollama / llama.cpp / LM Studio（OpenAI 兼容端点），产品只当 HTTP 客户端；默认 Qwen2-VL-7B Q4_K_M 档 | 不打包模型、不重复下载，分发最轻；一条客户端代码同吃本地/云端 |

| 6 | 隐私模型 | 默认本地（仅 loopback base_url 才算本地）；云端显式 opt-in + 二次确认 + 只出网「降采样后图片字节」、默认不携带文档上下文文本；网络审计覆盖识图路径 | 出网面收敛到两个 Provider 出口，可审计、可证伪 |
| 7 | 性能与边界 | 本地吞吐按 0.2–1 张/分钟保守设计，全异步 + 队列可续跑；喂图增强留 v0.2，给出触发信号与接口预留 | 导入体验不被识图拖垮；增强有明确回看时机 |

## 2. 决策一：本地 VLM 接入

### 2.1 推荐：对接用户已装的本地理性服务，产品只当「OpenAI 兼容 HTTP 客户端」

```
用户侧（安装由用户完成，产品给引导）         产品侧（零模型分发）
──────────────────────────────            ─────────────────────
Ollama (默认, 127.0.0.1:11434/v1)   ──►    识别 provider（HTTP 客户端）
  ollama pull qwen2-vl:7b                    base_url + model 配置
llama.cpp server (备选, 自定义端口)   ──►      不做模型下载、不打包权重
  llama-server -m ...-q4_k_m.gguf \
    --mmproj ...-mmproj-f16.gguf --port 8080
LM Studio (备选, 127.0.0.1:1234/v1) ──►      启动时探测 /v1/models 判可用
```

理由：
1. **与既定决策一致**：PRD §3.5 / §9.1-R8 已定「默认对接已有本地推理服务（Ollama / LM Studio / llama.cpp），避免重复下载与打包模型」。产品内置模型分发既增加包体（数 GB）又背上模型许可合规负担（§3.5 明示模型权重许可与产品 Apache-2.0 无必然关联，必须逐项审计）。
2. **统一一条客户端**：Ollama / llama.cpp / LM Studio 都暴露 OpenAI 兼容 `/v1/chat/completions`，与云端 OpenAI 兼容 VLM 是同一请求协议——「本地 Ollama」与「云端 API」之间切换只是改配置，不产生两套代码。
3. **Windows 首发友好**：Ollama 与 LM Studio 都有官方 Windows 安装包，LM Studio 更是图形化一键拉起本地 VLM，适合无命令行经验的用户。

### 2.2 接入方式（OpenAI 兼容 chat/completions 带图片输入）

统一请求体（Ollama、llama.cpp、LM Studio、OpenAI 兼容云端一致）：

```json
POST {base_url}/chat/completions
{
  "model": "qwen2-vl:7b",
  "messages": [{
    "role": "user",
    "content": [
      {"type": "text",      "text": "<§4 描述模板>"},
      {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,<B64>"}}
    ]
  }],
  "temperature": 0.2,
  "max_tokens": 1024
}
```

- 图片以 **base64 data URI** 内联传输（`data:image/jpeg;base64,...`），本地请求无外网；base64 使体积膨胀约 1/3，配合 §5 的降采样控制在可接受范围（约 1280px 边长 JPEG ≈ 200–600KB → base64 ≈ 0.3–0.8MB）。
- 关键参数：`temperature` 压低（0.2 左右）保确定性；`max_tokens` 给足（描述模板最坏场景约 600–1000 token）。
- **本地 provider 校验**：base_url 的 host 必须是 loopback（`127.0.0.1` / `localhost` / `::1`），否则产品**拒绝将其标记为「本地」**并提示（防止用户误填远程地址而不知出网，见 §7）。

### 2.3 模型量化档位与硬件门槛（近似，以官方模型卡/量化社区为准）

| 模型方向 | 档位 | 权重体积（近似） | 显存/内存门槛 | 适用场景 |
|---|---|---|---|---|
| Qwen2-VL-2B | GGUF Q4_K_M | ~1.6GB | ~4GB 显存 / 8GB 内存（CPU 可跑） | 无独显兜底；中文识图尚可 |
| **Qwen2-VL-7B** | **GGUF Q4_K_M** | **~4.8GB** | **~8GB 显存** / 16GB 统一内存（Apple Silicon） | **默认推荐**：质量/资源平衡 |
| Qwen2-VL-7B | fp16/bf16 | ~16GB | 16GB+ 显存 | 高质量、但个人机器少见 |
| MiniCPM-V-2.6 (8B) | GGUF Q4 | ~5.5GB | ~8–10GB 显存/内存 | 中文强、视觉定位强、体积友好备选 |
| Qwen2.5-VL-3B | GGUF Q4 | ~2.2GB | ~5GB 显存 | 更新换代候选（以官方为准） |

- 门槛底线：**CPU-only（无独显、≤16GB RAM）可跑 Q4 7B 档，但单图 10–30 秒级**，正好落在「0.2–1 张/分钟」的保守吞吐假设内；**≤8GB RAM 或极致低配**则走 Qwen2-VL-2B 档，或干脆关闭图片功能 / 用云端——三条路径都在产品内闭环，不强迫所有人配 GPU。
- 视觉投影（mmproj）：llama.cpp 需单独指定 `--mmproj` 文件；Ollama 内部自动携带。产品侧无需感知，只需在模型配置处提示「llama.cpp 模式需同时配置 mmproj」。

### 2.4 安装方式：依赖用户已装（MVP） vs 内置下载

- **推荐（MVP）：依赖用户已装 Ollama / LM Studio / llama.cpp**。
  - 首次启用图片功能时，配置向导内给出引导：检测本机是否存在 OpenAI 兼容端点（探测 `/v1/models`），未装则展示「安装 Ollama」指引 + 推荐 `ollama pull qwen2-vl:7b` 命令，用户确认后返回继续。
  - 产品只在「模型配置」页展示该模型的**许可证**（凡推荐型号必须宽松许可，如 Qwen2-VL 系列为 Apache-2.0 带 1 亿 MAU 阈值条款、MiniCPM-V 系列许可证须逐版核对——**以官方文档为准**，违规型号禁止进入默认推荐/内置下载清单）。
- **备选（v0.2 起）：「模型下载助手」**：产品调用本地 Ollama CLI（`ollama pull <tag>`）或 Ollama 模型管理 API 引导下载，仍是操作「用户已装的 Ollama」，**不内置推理二进制、不打包权重**。
- **边界**：MVP 绝不做「内嵌 llama.cpp 二进制 / 内嵌权重」的分发形态（跨平台打包负担 + 许可合规风险，违背 §3.5 与 §9.1-R8）；本决策不改变「识图是开关、纯文本用户零配置」的约束。

## 3. 决策二：识图 provider 抽象

### 3.1 推荐：底层共用「OpenAI 兼容 client」，上层分 `VisionModel` / `ChatModel` 两个薄接口

- **共用层（复用不合并）**：一个 OpenAI 兼容 HTTP 客户端内核，负责请求装配（messages/content 编码、base64 图片装配）、重试与退避、超时、流式解析、**网络审计打点**（见 §7）、key 注入（环境变量优先）。本地 Ollama / llama.cpp 与云端 API 共用这一个内核。
- **接口层（语义隔离）**：识图与对话是两种调用语义，拆成两个薄接口，但共享同一个配置模型（base_url / model / api_key / 超时）：

```python
# providers/vision.py —— 识图接口（单图 → 描述，非流式、确定性）
@dataclass
class VisionConfig:
    enabled: bool
    provider: Literal["local", "cloud"]
    base_url: str
    model: str
    api_key: str = ""            # 云端用；环境变量优先，不落盘明文
    max_retries: int = 2
    timeout_s: float = 120.0
    max_pixels: int = 1_300_000  # 降采样上限，见 §5

class VisionModel(Protocol):
    def describe(self, image: bytes, mime: str, prompt: str) -> str: ...

class OpenAICompatibleVision:    # 本地 Ollama/llama.cpp 与云端共用，仅 config 不同
    def __init__(self, cfg: VisionConfig, audit: NetworkAudit): ...
    def describe(self, image, mime, prompt) -> str: ...   # 内部打审计点
```

```python
# providers/chat.py —— 对话接口（多轮、流式）
class ChatModel(Protocol):
    def stream_chat(self, messages: list[dict]) -> Iterator[str]: ...
```

理由：
1. **只维护一条模型调用代码路径**（PRD §3.4 明示），本地/云端切换零代码改动；
2. **接口语义各司其职**：识图是「单张图 → 确定性描述」（非流式、单一输入、无角色），对话是「多轮 → 流式生成」；强行合并成一个接口会让调用方被迫处理无关语义，测试与 mock 也变重；
3. **为 v0.2 喂图增强留缝**：喂图增强 = 「对话模型接收图片消息」，那是在 `ChatModel` 上叠加**可选能力位**（`supports_image_input`），而不是把识图塞进对话接口。底层 client 已支持图片消息装配，届时只是新开一个调用方。

### 3.2 与 ChatModel 的关系（最终结论）

- 共用：OpenAI 兼容 client 内核、配置项 schema、重试/审计/脱敏策略。
- 不共用：接口定义、调用方、错误类型语义。
- 一句话：**「同内核、双接口」**，既满足「一条代码路径」的既有决策，又不把两种职责糊在一个类里。

### 3.3 备选与边界

- 备选 a：`VisionModel` 直接是 `ChatModel` 的别名（完全共用）——不推荐，语义混淆、流式/非流式混用。
- 备选 b：独立重写第二套 HTTP 客户端——不推荐，重复出网面、审计难统一。
- 边界：MVP 只实现 `OpenAICompatibleVision` 一个默认实现；第三方 provider（如直接走某 SDK）留到开源阶段按插件接口扩展，MVP 不预设。

## 4. 决策三：描述 Prompt 模板

### 4.1 推荐：固定 7 段模板 + 反幻觉约束 + 确定性参数

```text
你是个人知识库的图片描述器。请根据给定图片与上下文，按下面的固定结构输出中文描述。
只描述图中客观可见的内容，看不清/不存在的内容如实写"无/看不清"，严禁编造。

【画面主体】图的主要类型（架构图/流程图/表格截图/聊天记录截图/界面截图/文档截图/代码截图/照片…）
            与一句话概括。
【关键实体与场景】图中的对象、人物、场景、组织、系统组件、命名实体。
【图中文字(OCR)】逐条列出图中可见的文字：标题、按钮、标签、聊天消息要点、数据值、注释。
            保持原文语言与拼写，不要翻译、不要改数字。
【图表与数据】(若为图表/表格) 图表类型、坐标轴含义、趋势、关键数值；表格的行列主题与关键条目。
【关系与结构】(若为结构图) 节点与连线、流程步骤、层级包含关系。
【与上下文的关系】(若给定上下文) 本图在所属文档/对话中起什么作用、呼应什么主题。
【可检索标签】5-10 个逗号分隔的检索词，含专有名词、缩写、数字、主题词。
```

调用参数：`temperature=0.2`、`max_tokens≈1024`（保守给足）、单轮（不加对话历史）。

### 4.2 设计理由（跨模型稳定 + 可检索）

1. **格式由「段标题」驱动而非自由文段**：固定 `【】` 段标题让不同模型（Qwen2-VL / MiniCPM-V / 云端 GPT-4o 级）输出的结构对齐，后续若做「按字段解析」或字段级比较都可行。
2. **字段密度与检索目标对齐**：方案 B 的检索单元是「文字描述」整体嵌入（同一嵌入模型），**OCR 字段（原样文字/数字/专有名词）与标签字段贡献了向量检索最需要的专有名词与数字**——正好补向量检索对精确词弱的问题（与 §6.2 BM25 阶段的目标一致）。
3. **反幻觉约束降低污染**：识图一次落库、长期检索，一次幻觉描述会污染知识库；「看不清/无，严禁编造」是对检索质量的直接保护。
4. **OCR 原文不翻译**：多语言图内文字保留原文，避免「翻译失真 + 丢失可检索字面」。描述正文用中文（产品中文优先），与文档主语言一致便于同空间检索。

### 4.3 上下文字段的策略（隐私相关，见 §7）

- 本地 provider：可注入「与上下文的关系」（把所在文档标题锚点路径 + 邻近文本块摘要给模型），描述更贴上下文。
- 云端 provider：**默认不注入上下文文本**（避免文档内容随图出网），「与上下文的关系」输出「未提供上下文」；仅当用户额外开启「上下文随图发送」且二次确认后才注入（见 §7.3）。

### 4.4 边界

- 模板是**全局常量**，MVP 不提供用户编辑；v1.0 可开放「自定义描述模板」作为高级配置。
- 描述结果最大长度截断（如 1200 字）防止个别模型失控长文；超长截断不阻塞。
- 若模型输出违反结构（未按段标题），**不做重试、原样入库**（可检索性仍成立），只记一条 debug 日志。

## 5. 决策四：入库管线实现

### 5.1 推荐流程

```
MD 解析出图片引用（![alt](path)）
   │
   ▼  ① 图片预处理（本地、同步、快）
   Pillow 打开 → Image.verify()（损坏校验）→ ImageOps.exif_transpose()（EXIF 方向）
   → convert("RGB")（剥离 alpha/CMYK）→ 降采样到最长边 ≤1280px 且总像素 ≤ 130 万
   → JPEG 编码 quality=85 → bytes
   │
   ▼  ② 去重判定（按图片内容）
   image_content_hash = xxh64(降采样后 JPEG bytes)   ← 不依赖路径
   state.db: image_descriptions(content_hash, description, embedding?, status, created_at)
   ── 命中已存在 → 复用描述与嵌入，不再调模型 ──────────┐
   │                                                  │
   ▼  ③ 异步任务（后台队列，见 5.3）                    │
   调 VisionModel.describe() → 描述文本                 │
   → 与文本同一嵌入模型出向量 ──────────────────────────┘
   │
   ▼  ④ 确定性 upsert（幂等）
   每个引用位置各建一个描述块：block_id = 锚点路径 + 图引用序号（确定性）
   元数据：type=image_description / image_path(绝对+相对) / image_content_hash /
           source_file / source_platform / created_time（继承所在文档/对话）
   同图多处引用：共享描述文本 + 共享向量（嵌入只算一次），block_id 各自独立
```

### 5.2 图片预处理细节

- **解码**：Pillow（`Image.open` + `Image.verify()` 校验完整性；`verify()` 后需重新 `open` 才能正常加载）。解码失败 → 标记「图片不可读」，跳过该图不中断批次（对齐 §4.3 验收 7）。
- **EXIF 方向**：`ImageOps.exif_transpose()` 将拍摄方向转正——手机截图/照片横竖颠倒若不处理会导致描述「颠倒画面」。
- **降采样**：最长边 ≤ 1280px（Qwen2-VL 推荐）到 1344px（MiniCPM-V 支持上限）区间取一个全局常量（建议 **1280px**，兼顾两种模型）；总像素上限 ~130 万。理由：VLM 视觉 token 随分辨率超线性增长，超大图（如 4K 截图）直接喂会拖慢/超上下文；切片由运行层（Ollama/llama.cpp）内部处理，产品只需限制分辨率与总像素。
- **编码**：统一 JPEG（RGB, q85）后送 base64，控制体积与格式一致性。

### 5.3 异步批量处理（文本先入库、描述后台补全）

- **快慢分离**：文本块走主管线立即切块、嵌入、入库（毫秒级/张的只有 decode+downsample，也在此同步做）；「调识图模型」是慢路径，放后台。
- **任务队列**：内存 `asyncio.Queue` + 持久化任务表 `image_tasks(task_id, content_hash, image_path, status, retries, error, created_at)`，支持**应用重启后续跑**（未完成任务下次启动重新入队）。并发控制：本地 provider 并发 **1**（LLM 推理不并行收益，且 Ollama 内部排队）；云端 provider 并发 2–4 + 限流感知（收到 429 就退避，见 5.4）。
- **占位与补全**：图片描述未就绪时，该引用位置**不产生向量块**（避免「空描述块」污染检索），但同步状态表记录该图的待处理标记；后台完成后按确定性 block_id 做 upsert，幂等、可重入。用户在此窗口检索：命中其所在文档的文本块即可，图片描述就绪后自然进库。
- **进度与续跑**：批量页展示「图片描述后台生成中 X/Y（成功/失败）」；失败清单提供「仅重试失败图片」。

### 5.4 同图多处引用只算一次 + 失败重试与降级

- **去重键**：**图片内容哈希（降采样后 JPEG 的 xxh64）**，而非路径——同名文件、不同路径、复制粘贴的同一张图都能命中；路径变化不影响（防路径漂移）。描述与**嵌入**都只算一次并缓存到 `image_descriptions` 表；各引用位置仅新增一条元数据不同的块。
- **重试（默认 2 次）**：对瞬时错误（超时 / 网络 / 429 限流）做指数退避重试（如 2s → 8s）；对永久错误（图片损坏、400/模型拒绝、无效请求）**不重试**直接失败。重试次数做成配置项（`vision.retry`，默认 2，0=不重试）。
- **降级（不阻塞整批）**：单图失败仅标记 `status=failed + 可读原因`，批次继续；**批量熔断**：失败率超阈值（如连续 10 张或 >50% 失败）→ 暂停队列并提示「识图服务不可用，请检查模型/网络」，避免对云端 API 盲目打费。图片功能开关关闭时：图片仅存元数据占位，不建描述块、不调模型（§4.3 验收 2）。

### 5.5 边界

- 预处理与嵌入仍是「本地必做」；`image_descriptions` 表本地落盘。
- 描述完成后的 upsert 必须**幂等**：block_id 由「文件 + 锚点路径 + 图引用序号」确定性推导，重跑/续跑不会产生重复块（对齐增量同步「局部更新」约束）。
- MVP 不做图内局部区域检索/裁剪放大重识（CLIP 场景，明确不在范围）。

## 6. 决策五：原图路径元数据与前端展示

### 6.1 推荐：存「绝对路径 + 相对知识库根路径」双值

```json
"image_path":        "D:/kb/notes/架构笔记.md 同级/arch.png",   // 相对知识库根目录
"image_abs_path":    "D:\\kb\\notes\\assets\\arch.png",          // 规范化绝对路径
"image_content_hash":"d41d8cd98f00b204..."
```

- **绝对路径**（`os.path.abspath` 规范化，统一分隔符）用于直接定位与展示路由。
- **相对根目录路径**用于「知识库目录迁移/换机」后的 **rebase**：相对路径 + 新根 = 新绝对路径，避免整库失效。
- 二者同时落库，展示与溯源用绝对路径，迁移重建用相对路径。

### 6.2 命中后前端渲染缩略图的边界

- 浏览器沙箱**无法直接读本地文件**（`file://` 跨源被禁），因此需要**后端只读路由**：

```python
# 后端（FastAPI）
@app.get("/files/image")          # 仅服务知识库根目录内文件
def image(path: str, thumb: int = 0):
    p = Path(path).resolve()
    root = Path(config.knowledge_root).resolve()
    if not p.is_relative_to(root):          # realpath 白名单，防路径遍历
        raise HTTPException(403)
    if thumb: return serve_thumbnail(p, size=256)   # Pillow 生成，内存 LRU 缓存
    return FileResponse(p)
```

- 前端 `<img src="/files/image?path=...&thumb=1">` 渲染缩略图，点击放大用 `thumb=0` 出原图。
- **边界**：
  1. **只服务知识库根目录内的图片**（`is_relative_to` + `resolve()` 双重防穿越），超界 403；不服务任意本地路径（防恶意构造）。
  2. 仅本地回环（`127.0.0.1`）访问，无鉴权（单用户）；开放局域网时必须加鉴权（与 §5.4 一致）。
  3. **不复制图片进产品目录**：读取按需、只读、加内存/磁盘 LRU 缩略图缓存，原始文件永不写入产品数据目录（守住「原图只存路径」既定决策）。
  4. 图片文件缺失/损坏 → 前端显示占位「图片不可用」，不阻塞来源卡片其余部分。

### 6.3 备选

- 纯展示路径文本（最保守，无图片服务）——不推荐：来源卡片「点击看原图」是 4.6 验收要求，纯文本体验断崖。
- 导入时拷贝缩略图进产品目录——不推荐：违背「不复制图片」决策，且产生清理/一致性负担。

## 7. 决策六：本地 vs 云端的隐私模型

### 7.1 推荐：默认本地（不出机）的实现保障

1. **出网面收敛**：所有 HTTP 外呼只允许来自两个 Provider（`ChatModel` / `VisionModel`）；其余模块**禁止发起外呼**（架构约束 + 代码评审/测试断言）。识图路径的出网唯一入口是 `VisionModel.describe()` 内部的审计打点。
2. **本地 ≠ 任意 base_url**：本地 provider 校验 base_url host 必须为 loopback（`127.0.0.1/localhost/::1`），否则产品**拒绝标记为本地**并在配置处提示「该地址为远程主机，将产生出网」。这从机制上防止「误把远程 Ollama（如局域网或公网实例）当成本地」而不知情出网。
3. **图片预处理先于发送、只发送处理产物**：解码/EXIF/降采样/JPEG 编码全部本地完成，仅把**降采样后的图片字节**作为请求体；不出网源文件名、不出网路径、默认不出网文档上下文。
4. **默认配置即安全**：识图开关默认关；provider 默认 local；云端 provider 必须显式选择并保存 key 才激活。纯文本路径（不开图片功能）**零外发**不变。
5. **配置脱敏**：云端 key 走环境变量（如 `EVERYTHING_RAG_VISION_API_KEY`）或内存，不落盘明文（PRD §5.3）。

### 7.2 云端时的出网面收敛 + 显式 opt-in + 二次确认

- **出网面**（云端识图时）：仅「降采样后图片字节」；**默认不携带任何文本**（描述 Prompt 使用固定模板、上下文字段置「未提供」，见 §4.3）→ 文档内容不出网。请求目标 = 用户填写的 `base_url` 所指向服务商。
- **opt-in 三要素（全部在设置页可见）**：
  1. 图片功能总开关（默认关）；
  2. provider = 云端（默认本地）；
  3. 保存云端配置前的**二次确认**：弹窗明确「启用后将把知识库中的**图片**发送至 **{host}** 进行识别，识别得到的文字描述保存在本机。文档文本不会随图发送。确认？」——对齐 PRD §4.7 验收 7、§4.8 验收 3。
- **常驻警示**：provider=云端期间，设置页与图片入库页展示常驻警示条「图片识别正在外发图片至 {host}」，避免「配过一次就忘」。

### 7.3 网络审计如何覆盖识图路径

- `NetworkAudit.record(kind, provider, host, data_class, bytes)` 在 `VisionModel.describe()` 与 `ChatModel.stream_chat()` 内部打点；审计数据存内存 + 状态库（`network_events` 表，脱敏，不含图片/路径/文件名）。
- 审计面板展示：每次外呼的**时间、目标 host、数据类别（文本/图片/问题）、字节量、关联模块（识图/对话）**；「数据流向」视图据此渲染。
- **识图专用审计断言**（验收用）：纯本地配置 → 识图路径零外呼；云端识图 → 仅图片字节外呼、无文本随行、记录出现在审计面板。
- **日志文件脱敏**（PRD §4.8 验收 6）：日志文件只记结构化事件（成功/失败/耗时/错误码），不记录图片路径、文件名、描述正文。

### 7.4 隐私模型汇总

| 场景 | 是否出网 | 出网内容 | 前提 |
|---|---|---|---|
| 图片功能关闭（默认） | 否 | — | — |
| 本地识图 | **否**（loopback 校验保证） | — | 用户已装 Ollama/llama.cpp |
| 云端识图 | 是 | 仅降采样后图片字节（无文件名/路径/上下文文本） | opt-in + 二次确认 + 常驻警示 |
| 云端识图 + 上下文随图（可选扩展） | 是 | 图片字节 + 文档上下文片段 | 额外开关 + 二次确认（v0.2 评估） |
| 云端喂图问答（v0.2） | 是 | 原图 + 问题 + 上下文 | 默认关 + 开启提示 |

## 8. 决策七：性能与边界

### 8.1 吞吐假设与导入体验策略

- **假设**：本地识图 0.2–1 张/分钟（CPU 或低配独显跑 Q4 7B 档，保守值；独显 7B Q4 可到 5–10 张/分钟，**以验收实测为准**）。100 张图 ≈ 1.5–8 小时后台，因此**异步化是刚需而非优化**。
- **策略**：
  1. **文本先行**：切块/嵌入/入库不等待识图；导入完成提示「图片描述后台生成中 X/Y」，用户可立即问答。
  2. **队列可续跑**：`image_tasks` 表持久化，重启后未完成图片续跑（幂等 upsert）。
  3. **感知引导**：批量页展示进度/失败清单/重试入口；图片命中但描述未就绪时前端显示「该图片描述仍在生成中」占位。
  4. **不阻塞问答**：识图后台队列与问答线程池互不阻塞（PRD §7 并发约束）。
- **结论**：识图吞吐只影响「描述就绪时间」，**不影响导入完成时间与首次问答**，这是方案 B 对「识图慢」的根本化解。

### 8.2 MVP 不做喂图增强的判定策略（留 v0.2）

- **为什么不做进 MVP**：方案 B 已让「图片内容可被文字检索」，MVP 检索主链（向量检索 → 文字描述 → 答案）闭环成立；喂图增强只提升「答案需看图内细节」场景的生成质量，属于体验增强而非检索闭环，故归 v0.2（与 PRD §7.2 一致）。
- **v0.2 做它的触发信号**（满足其一即可立项）：
  1. 评测集/反馈显示「图片内容类问题」命中描述但答案需看原图细节（如「架构图第三层是什么」「表格第 5 行数值」）；
  2. 描述对细节召回不足（描述丢失的细节无法从文本还原——即方案 B 的天花板出现）；
  3. 对话模型已支持多模态输入（前置能力）。
- **技术预留（不实现 UI/判定，仅留接口）**：`VisionModel` 已具备「接收图片 + 文本」能力；`ChatModel` 增加可选能力位 `supports_image_input`；届时「喂图」= 复用同一多模态 Provider，把原图 + 问题 + 检索上下文喂给对话模型，流式输出 + 来源标注（PRD §2.3）。出网语义按 §7.4 表格处理（云端喂图默认关 + 开启提示）。
- **MVP 内不做的明确清单**：不做 CLIP 图像向量、不做 ColPali、不做图内局部检索、不做图搜图、不做图片相似度检索。

## 9. 待确认项（以官方文档为准）与验收要点

### 9.1 待确认项

1. 推荐型号的精确 Tag、量化体积、官方许可文本（Qwen2-VL / Qwen2.5-VL / MiniCPM-V 各版）——实现阶段拉取官方模型卡核对。
2. llama.cpp 对所选型号的最新支持状态（mmproj 文件与 GGUF 匹配）；Ollama library 中该型号的可用 Tag。
3. 云端候选端点的限流/价格/图片尺寸上限——以服务商文档为准。
4. 本地吞吐假设（0.2–1 张/分钟）需用作者真实硬件跑出基线，回填 §8.1。

### 9.2 与 §4.3 验收标准的对齐（实现后逐条核验）

- 开关关闭：无识图调用、仅元数据占位、所在文本块不失败（验收 2）。
- 成功返回：描述走与文本同一嵌入、与图片引用关联入块（验收 3）。
- 原图路径绝对+相对入元数据（验收 4）。
- 失败重试 2 次后标记失败、继续批次（验收 5）；进度/失败清单/重试入口（验收 6）。
- 不可读图片跳过并标注（验收 7）。
- 同图多处引用只算一次、各引用独立元数据（验收 8）。
- 问答默认不调用识图（验收 10）。
- 隐私回归：纯本地零外呼、云端仅图片字节 + 审计面板可查（§7.3）。

### 9.3 主要风险与缓解

| 风险 | 缓解 |
|---|---|
| 用户没装本地推理服务 → 图片功能不可用 | 引导安装 + `ollama pull` 指引 + 云端可选 + 关闭降级，三路闭环 |
| 本地模型描述质量不稳（幻觉） | 反幻觉 Prompt + 低 temperature + 模板化字段 |
| 云端误配导致不知情出网 | loopback 校验 + 二次确认 + 常驻警示 + 审计面板 |
| 识图慢拖垮导入 | 异步队列 + 文本先行 + 可续跑 |
| 模型许可合规 | 配置页展示许可；违规型号禁止进入推荐/内置下载清单 |
