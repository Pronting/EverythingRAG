## 4.1 数据接入

### 功能概述

用户通过**拖拽**或**选择目录**两种方式导入 Markdown 文件。导入器是系统的唯一数据入口，承担两项核心职责：

1. **类型识别**：自动区分「对话文档」与「普通文档」。对话文档来源于第三方 AI 平台（如 ChatGPT / Kimi / DeepSeek 等）的对话导出；普通文档为本地知识类 Markdown。
2. **归一化**：将对话导出内容归一化为标准 Markdown 纯文本输入，并识别**对话边界**（user / assistant 消息轮次），为每条对话打上元数据：来源平台、时间、对话标题、角色序列。普通文档不打对话类元数据。

架构原则（继承框架决策）：产品**只认 Markdown**，不绑定任何具体工具、token、API 或浏览器抓取。多来源的价值集中在元数据上。对话边界识别采用**通用对话结构特征识别**（消息轮次标记、角色标签等）+ 可插拔的格式适配器机制（开源后社区可扩展），而非逐平台写死。

对外链 URL：仅将 URL 与链接文本存入元数据，**不发起任何网络请求抓取链接内容**。

导入全流程提供**反馈与错误处理**：实时进度、成功/失败/跳过统计、可读失败原因、失败项重试入口。

**非目标（MVP）**：不支持 PDF / DOCX / 结构化数据；不支持通过 token 或浏览器抓取对话；不做实时监听（见 4.5）。

### 用户故事

1. 作为重度 AI 用户，我希望把 ChatGPT / Kimi / DeepSeek 等平台导出的对话文件直接拖进应用，以便不用手动整理就能在统一知识库里检索。
2. 作为用户，我希望按目录一次导入多份文件，以便批量建立知识库而不用逐个操作。
3. 作为用户，我希望导入时看到进度和结果，以便知道哪些文件成功、哪些失败及失败原因。
4. 作为用户，我希望系统能自动判断一份文件是"对话"还是"普通文档"，以便对话能带上平台/时间信息、文档按文档处理。
5. 作为用户，我希望导入器不要求我提供任何平台账号或 token，以便我的数据来源完全由我自己掌控。
6. 作为用户，我希望文档里的外链只是被记录，以便系统不会去抓取网页内容、也不因此引入额外风险。

### 关键验收标准

1. WHEN 用户将一个或多个 `.md` 文件拖拽到导入区 THEN 系统立即开始解析并显示实时进度。
2. WHEN 用户选择"选择目录"导入一个文件夹 THEN 系统递归扫描该目录下（含子目录）所有 `.md` 文件；对不可读文件或非 MD 文件给出跳过说明，不中断整体导入。
3. IF 文件内容呈现对话结构特征（存在连续的多轮消息标记、角色标签等）THEN 系统将其识别为「对话文档」并解析消息边界（user / assistant / system / tool 等角色轮次）。
4. IF 文件不呈现对话结构特征 THEN 系统将其识别为「普通文档」，不解析对话边界、不设置平台/对话类元数据。
5. WHEN 对话文档解析成功 THEN 系统保存以下元数据：来源平台、时间（导出时间或对话开始时间，取可用者）、对话标题、消息角色序列。
6. IF 对话文档的来源平台无法自动识别（文件名/目录名/格式特征均无法推断）THEN 系统按「未知平台」处理，并在导入完成后允许用户手动补充来源平台元数据。
7. WHEN 文档中出现 Markdown 外链（URL）THEN 系统仅将 URL 与链接文本存入该块的元数据，不发起任何网络请求。
8. WHEN 导入过程中部分文件失败（编码不支持、格式损坏等）THEN 系统继续处理其余文件，并在完成报告中列出每个失败项及可读原因（如"文件编码无法识别"）。
9. WHEN 导入完成 THEN 系统展示成功 / 失败 / 跳过数量统计，并提供「重试失败项」入口（仅对失败项重跑管线）。
10. WHEN 用户重复导入已存在的文件 THEN 系统按 4.5 的去重键规则处理：不产生重复块，并在反馈中提示"已存在，跳过"。
11. WHEN 用户导入不支持的文件类型（如 `.pdf`、`.docx`）THEN 系统明确提示"当前版本仅支持 Markdown 文本"，并继续处理批次内其他受支持的文件。
12. IF 导入批次中某一文件的读取编码非 UTF-8 但可自动检测 THEN 系统按检测结果读取并标注编码来源；若检测失败则将该文件标记为失败项（遵循第 8 条）。

## 4.2 文档处理管线（文本）

### 功能概述

对导入的 Markdown 执行「解析 → 语义切块 → 元数据保留」三步，产出供向量化的**块**。核心约束（继承框架决策）：**按语义结构切块（标题 / 段落），明确不用固定窗口切分**。

- **MD 解析**：将 Markdown 解析为结构化文档树，正确识别标题、段落、列表、表格、代码块、图片引用、引用块等元素。
- **语义切块**：以标题层级为一级边界（每个标题及其下内容构成块），以段落（空行分隔）为最小单元；代码块整体成块；超过最大长度阈值的语义块按段落/句子拆分并继承标题路径。不按固定字符窗口硬切。
- **上下文保留**：每个块携带**标题路径**（如「项目笔记 > 架构决策 > 技术选型」）作为上下文元数据。
- **元数据保留**：来源文件路径、来源平台（对话）、时间（对话）、角色（对话）、标题路径。
- **对话文档**：每条消息（或其内的语义段）作为带角色的块处理。

切块结果直接决定 4.5 增量同步"局部修改只更新局部块（防边界漂移）"的可行性：由于块边界由语义结构决定而非固定位置，局部编辑后各块边界保持稳定，只有被修改的块需要重新嵌入。

**非目标（MVP）**：不做 PDF / 结构化数据的解析；不做跨源融合重排（见 4.6 范围）。

### 用户故事

1. 作为用户，我希望长文档被按主题切开，以便问答时只检索相关内容，而不是把整篇塞给模型。
2. 作为用户，我希望检索结果能保留文档层级上下文，以便答案能指到具体章节、我也能理解上下文。
3. 作为用户，我希望代码块不被拆散，以便检索到整段代码而非碎块。
4. 作为用户，我希望我改一个段落只影响那一段，以便增量同步既快又不会让附近内容的检索边界漂移。

### 关键验收标准

1. WHEN 系统处理一个 Markdown 文档 THEN 先将 MD 解析为结构化文档树（标题、段落、列表、表格、代码块、图片引用等元素均被正确识别）。
2. IF 文档包含多级标题（H1~H6）THEN 切块以标题为语义边界：每个标题及其下内容构成一个独立块，子标题内容优先归属最近一级父标题。
3. WHEN 文档存在无标题的长段落 THEN 系统以段落（空行分隔）为最小切分单元生成块，不按固定字符窗口硬切。
4. IF 单个语义块的内容超过系统设定的最大长度阈值（常量，默认约 2000 字符）THEN 系统在该块内进一步按段落 / 句子拆分为子块，子块继承相同的标题路径上下文。
5. WHEN 系统生成每个文本块 THEN 保存块元数据：来源文件路径、标题路径（如「项目笔记 > 架构决策 > 技术选型」）、块内序号。
6. WHEN 对话文档进入管线 THEN 每条消息（或其内语义段）作为带角色的块处理，块元数据额外包含：来源平台、消息角色、对话时间。
7. IF 文档中存在代码块 THEN 系统将整个代码块作为独立语义块处理，不拆散代码内容。
8. IF 文档中存在图片引用（`![...](路径)`）THEN 系统保留该引用，并将图片交由图片处理管线（4.3）；文本块中保留图片引用的占位/链接信息。
9. IF 文档损坏或无法解析为有效 Markdown THEN 系统跳过该文档并在导入报告中标注原因，不中断整体管线（与 4.1 失败处理衔接）。
10. WHEN 同一文档被再次处理（增量更新场景，见 4.5）THEN 系统尽量复用未被修改的块的向量与元数据，仅对内容变化的块重新切分与嵌入。

## 4.3 图片处理（方案 B）

### 功能概述

对文档中的图片引用执行「多模态识图 → 文字描述 → 文本嵌入」，即**方案 B**（检索主干）。关键决策（继承框架决策）：

- **方案 B 为检索主干**：图片经多模态识图模型转为文字描述，描述作为文本被嵌入进向量库，使图片内容可被文字检索。
- **原图路径进元数据**：原图路径（绝对路径或相对知识库根目录路径）存入图片块的元数据，用于展示与溯源。
- **识图功能是开关**：默认可关闭。关闭后图片仅作为文本元数据占位，不产生向量块、不调用识图模型。
- **批量与失败处理**：批量处理并发受控、进度可见、失败重试与降级（单图失败不阻塞整批）。
- **可选增强（v0.2+）**：「问答时把相关原图喂给多模态模型看图作答」是叠加增强，**不替代方案 B**；且仅当用户开启该增强开关时，问答流程才调用识图模型。

管线流程约束（继承框架决策）：识图**只在入库时发生一次**；默认问答流程**不调用识图模型**。

**性能/成本优化**：同一图片在多个文档中被引用时，识图描述只计算一次（按图片内容 / 路径去重），避免重复计算成本。

**非目标（MVP）**：不做 L3 多模态图像向量（CLIP）；不做图片生成类任务。

### 用户故事

1. 作为用户，我希望图片里的内容也能被搜到，以便我问"那天的架构图里写了什么"时能命中。
2. 作为用户，我希望通过开关控制是否启用识图，以便在不愿图片出网或想省资源时仅索引文本。
3. 作为用户，我希望看到图片处理进度和失败清单，以便知道哪些图没进库、为什么。
4. 作为用户，我希望一张图在多处被引用时只处理一次，以便导入不会因重复识图而变慢变贵。
5. 作为用户，我希望问答时默认不调用识图模型，以便纯文本流程完全可控、可预测。

### 关键验收标准

1. IF 识图功能开关为开启 THEN 管线中发现图片引用时调用配置的识图模型生成文字描述。
2. IF 识图功能开关为关闭 THEN 系统跳过识图，图片引用仅以元数据形式保留（不产生向量块），且所在文本块不因缺图而失败。
3. WHEN 识图模型成功返回描述 THEN 系统将描述文本走文本嵌入流程（与 4.2 产出块一致），并把描述与图片引用关联保存在同一图片块中。
4. WHEN 系统处理图片 THEN 原图路径（绝对路径或相对知识库根目录的路径）存入该图片块的元数据。
5. IF 识图失败（网络错误、模型拒绝、图片损坏等）THEN 系统自动重试设定次数（默认 2 次）；重试仍失败则将该图标记为失败并继续处理后续图片，不阻塞整体任务。
6. WHEN 批量图片处理进行中 THEN 系统显示进度（已处理 / 总数、成功 / 失败数），并在完成后提供「仅重试失败图片」入口。
7. IF 图片文件缺失或无法解码 THEN 系统将该图标记为不可读并跳过，在报告中标明原因，不中断批次。
8. WHEN 同一图片在多个文档中被引用 THEN 识图描述只计算一次（按图片内容 / 路径去重），各引用位置保留独立的元数据链接。
9. WHEN 用户启用「看图作答」增强且检索命中原图 THEN 系统可在答案展示时调用识图模型看图辅助作答；该增强仅作用于展示环节。
10. IF 用户未启用「看图作答」增强 THEN 问答流程完全不调用识图模型（与"入库时只发生一次、问答时不调用识图模型"一致）。

## 4.4 向量化与向量库

### 功能概述

将 4.2 的文本块与 4.3 的图片描述块**统一走同一嵌入模型**生成向量，写入**本地向量库**。核心约束（继承框架决策）：

- 文本与图片描述统一嵌入，检索时**同一模型**对问题做嵌入，保证向量同空间可比。
- **向量库本地化**：向量、块文本、元数据、来源映射均存储于本机数据目录，不出本机。
- 支持**重跑 / 重建索引**：更换嵌入模型或向量库异常时，一键全量重建。

向量与块元数据、原始文本、来源映射（块 ID → 文件 / 对话 / 平台）原子存储，保证任一向量的来源可回溯。

**非目标（MVP）**：不做混合检索 + 重排（v0.2+）、不做跨源融合排序（v1.0+）。

### 用户故事

1. 作为用户，我希望文本和图片描述用同一套向量，以便统一检索、无差别命中。
2. 作为用户，我希望向量和原始内容都保存在我本机，以便数据不出本机。
3. 作为用户，我希望在更换嵌入模型或向量库异常后能重建索引，以便恢复可检索状态。

### 关键验收标准

1. WHEN 文本块或图片描述块通过管线 THEN 系统调用配置的嵌入模型生成向量，并将「向量 + 块文本 + 块元数据 + 来源映射」原子写入本地向量库。
2. IF 嵌入调用失败 THEN 系统记录失败块，不中断批量任务，并在完成后允许针对失败块重试。
3. WHEN 问答检索时 THEN 用户问题经与库内块相同的嵌入模型生成查询向量（保证同空间可比）。
4. IF 用户更换嵌入模型 THEN 系统提示需重建索引（不同模型向量空间不兼容），并提供一键重建入口。
5. WHEN 用户触发「重建索引」THEN 系统全量重新向量化知识库；重建期间旧索引保持可读，或给出明确的不可用提示（二选一，实现期定）。
6. WHEN 向量库写入成功 THEN 系统持久化块 ID 与来源映射，确保任一向量的来源可回溯到具体文件 / 对话 / 平台。
7. IF 向量库本地存储目录空间不足 THEN 系统给出可读告警并阻止写入，避免静默失败。
8. WHEN 系统启动时检测到向量库与数据目录不一致（如缺少索引或元数据文件）THEN 系统提示用户执行同步（4.5）或重建索引（本条），不静默降级。

## 4.5 增量同步

### 功能概述

让知识库与本地源文件保持一致的增量更新机制。核心约束（继承框架决策）：

- **触发方式**：手动「同步」按钮 + 启动时自动检查；**不做实时文件监听（MVP）**。
- **指纹比对**：扫描所有已知文件，未变化跳过（毫秒级），变化才重新处理，删除则移除。
- **对话级去重**：去重键 = **来源平台 + 对话内容（规范化后）**，不是文件 hash——防止用户手动编辑导出文件（文件名、导出时间戳变化等）导致 hash 失效而重复入库。
- **防边界漂移**：局部修改只更新局部块。得益于 4.2 的语义切块，块边界由语义结构决定而非固定位置，单处编辑只影响对应块。

**指纹（fingerprint）定义**：文件级指纹 = 内容哈希 + 已知元数据（用于快速判断"是否变化"）；对话去重键 = 平台 + 规范化后的对话内容（用于判断"是否同源对话"）。两者职责不同、独立使用：指纹判断变更，去重键判断同源。

### 用户故事

1. 作为用户，我希望修改了文档或新增导出对话后点一下「同步」，以便知识库跟得上我的更新，又不用重复处理所有文件。
2. 作为用户，我希望启动应用时它会自动检查一遍，以便我不必记得每次手动同步。
3. 作为用户，我希望改一行只更新那一块，以便增量同步快且不会让附近内容的检索结果边界漂移。
4. 作为用户，我希望删掉源文件后知识库也移除对应内容，以便不留"幽灵数据"。
5. 作为用户，我希望同一段对话换了个文件名重新导出，不会被当成两份，以便知识库不重复不膨胀。

### 关键验收标准

1. WHEN 应用启动 THEN 系统自动触发一次增量同步检查（后台执行，不阻塞用户操作），并在 UI 提示同步状态与结果。
2. WHEN 用户点击「同步」按钮 THEN 系统立即执行增量同步并展示进度与结果（新增 / 更新 / 删除 / 跳过计数）。
3. WHEN 同步扫描到某个已知文件且其指纹（内容哈希 + 已知元数据）未变化 THEN 系统跳过该文件的重新处理，单文件跳过耗时保持在毫秒级。
4. WHEN 已知文件的指纹发生变化 THEN 系统仅对该文件重新走文档处理管线，不处理库中其他文件。
5. WHEN 已知文件的指纹变化属于局部编辑（仅某一段被修改）THEN 基于语义切块，仅重新嵌入受影响的块，其余块复用旧向量与元数据（防边界漂移）。
6. IF 某文件曾被导入但同步时已不存在（被删除 / 移出导入目录）THEN 系统移除该文件对应的所有向量、块与元数据记录，库中不残留孤儿数据。
7. WHEN 同步导入对话文档 THEN 去重键按「来源平台 + 对话内容（规范化后）」计算，而非文件哈希。
8. IF 同一对话以不同文件名 / 不同导出格式重复出现 THEN 规范化后去重键相同，系统判定为同一对话，不产生重复块；若内容有增量变化则按更新处理。
9. WHEN 对话被用户手动编辑（如清理冗余消息、调整排版）THEN 规范化去重键不受文件元数据变化影响，仍能识别为同一对话并按增量更新处理。
10. WHEN 两个不同来源（不同平台）存在相似对话 THEN 因去重键包含平台维度，系统不将其合并去重，各自独立入库。
11. IF 同步过程中某文件处理失败 THEN 系统在同步报告中单独列出失败项并允许重试，不影响其他文件的同步结果。
12. WHEN 同步完成 THEN 系统展示本次同步汇总，并给出与上次同步的差异摘要（新增 X / 更新 Y / 删除 Z）。
13. IF 已知文件的路径发生变化（被移动后重新导入）THEN 系统按「原路径记录移除 + 新路径记录新增」处理，并在报告中提示该情况，避免路径漂移造成静默重复。

## 4.6 问答 Dashboard

### 功能概述

面向自然语言问答的检索增强生成（RAG）界面，是用户与知识库交互的主入口。核心约束（继承框架决策）：

- **检索增强生成**：问题嵌入 → 本地向量检索 → 取 top-k 相关块 → 组装上下文 → 对话模型生成答案。
- **答案强制标注来源**：每个答案必须标注来源（哪个文件 / 哪段对话 / 哪个平台），支持点击跳转原文核验。
- **流式输出**：答案逐字流式返回，UI 持续渲染增量。
- **多轮对话**：支持基于历史上下文的追问。
- **无结果 / 低置信处理**：检索结果不足或相关度低于阈值时，明确告知"未检索到足够相关内容"，不编造看似确定实则无依据的答案。

**检索策略范围（MVP）**：仅向量检索。混合检索 + 重排为 v0.2、跨源融合排序为 v1.0，均不在本期。

### 用户故事

1. 作为用户，我希望用自然语言问"我上次关于迁移数据库说了什么"，以便不用翻聊天记录就能找回记忆。
2. 作为用户，我希望每个答案都标注来源，以便点过去核验并信任答案。
3. 作为用户，我希望答案像聊天一样流式出来，以便等待不焦虑、可提前判断方向。
4. 作为用户，我希望在问不到时知道"为什么没答上"，以便决定是否补数据，而不是被模型瞎编骗到。
5. 作为用户，我希望支持多轮追问，以便在一条脉络上深入而不是每次重新起头。

### 关键验收标准

1. WHEN 用户在 Dashboard 输入问题并提交 THEN 系统将问题经嵌入模型向量化后，在本地向量库检索 top-k 相关块（k 为可配置常量，默认 5）。
2. WHEN 生成答案 THEN 系统以流式方式逐字返回内容，UI 持续渲染增量（首字延迟与稳定输出速率满足非功能指标，见第 8 章）。
3. WHEN 生成答案 THEN 答案中每个事实性论断均附带来源标注：来源文件路径 / 对话标题 / 来源平台。
4. WHEN 用户点击答案中的来源标注 THEN 系统跳转展示对应原文块及上下文（含原图引用时展示缩略图或图片路径）。
5. IF 检索到的 top-k 块相关度低于系统设定的置信阈值 THEN 系统明确告知「未检索到足够相关的知识」，并附上最相关片段供用户判断，不生成看似确定实则无依据的答案。
6. WHEN 知识库为空或检索结果为空 THEN 系统提示用户先导入 / 同步数据，不执行生成。
7. WHEN 用户发起多轮对话 THEN 系统将历史轮次的问答摘要或相关上下文带入检索与生成，支持追问（如"那迁移后出了什么问题"）。
8. IF 对话历史超出上下文长度限制 THEN 系统仅保留相关历史或最近 N 轮（N 可配置），保证生成不超限，并提示用户。
9. WHEN 答案生成过程中模型或服务异常 THEN 系统保留已流出的部分，提示错误并允许重试，不静默截断。
10. IF 用户未启用「看图作答」增强 THEN 问答过程中不调用识图模型，图片相关命中仅以文字描述参与检索（与 4.3 约束一致）。

## 4.7 模型配置

### 功能概述

管理三模型分工与相关开关。核心约束（继承框架决策）：

- **三模型分工**：嵌入模型（必配）、对话模型（必配）、识图模型（条件性配置——仅开启图片功能时才需要）。
- **配置向导**：首次使用分步引导，让不熟悉配置的用户也能完成。
- **功能开关联动**：识图模型 = 功能开关。不开图片功能就不用配识图模型，保证「纯文本用户数据 100% 不出机」。
- **本地 / 云端切换位**：每个模型提供 provider 切换（本地运行 vs 云端 API），并在切换处展示对应隐私影响（详见 4.8）。

### 用户故事

1. 作为用户，我希望只配嵌入 + 对话就能用起来，以便最快上手、不被迫为用不上的功能付费或冒隐私风险。
2. 作为纯文本用户，我希望不配识图模型也能完整使用，以便我的数据 100% 不出机。
3. 作为用户，我希望按向导一步步配置，以便不熟悉模型配置也能完成。
4. 作为用户，我希望每个模型都能在本地与云端之间切换，以便我按隐私 / 性能 / 成本权衡。

### 关键验收标准

1. WHEN 首次启动配置向导 THEN 系统分步引导：① 数据接入 → ② 嵌入模型 → ③ 对话模型 → ④（可选）识图模型 → ⑤ 完成预览。
2. WHEN 用户未配置嵌入模型或对话模型 THEN 系统阻塞问答与同步入库的核心流程，并给出明确的「去配置」引导。
3. IF 用户未开启图片功能 THEN 系统不要求配置识图模型，配置向导跳过该步，纯文本流程可完整闭环。
4. WHEN 用户开启图片功能 THEN 系统提示需配置识图模型；未配置时阻塞图片入库，并在相关入口显示缺失提示。
5. WHEN 用户开启图片功能后又关闭 THEN 系统不再要求识图模型；已入库的图片描述块保留，后续图片不再调用识图（降级为元数据，见 4.3）。
6. WHEN 配置每个模型时 THEN 系统提供本地 / 云端 provider 切换位，并展示所选 provider 的隐私影响（本地不出网；云端需外发对应数据）。
7. IF 用户选择云端 provider 且该模型涉及图片处理 THEN 系统显著提示图片将离开本机，需用户显式确认后方可继续。
8. WHEN 用户保存模型配置 THEN 系统校验配置可达性（如嵌入模型可正常调用）；失败则给出可读错误并阻止保存无效配置。
9. WHEN 用户修改模型配置 THEN 系统提示该项变更的连带影响：嵌入模型变更需重建索引（4.4），对话 / 识图模型变更不影响既有向量。
10. IF 系统启动时检测到配置不完整（如对话模型缺失）THEN 系统引导用户进入配置向导补齐，不进入不可用的半配置状态。

## 4.8 隐私与安全

### 功能概述

保障「数据不出本机」的核心承诺，覆盖数据流控制、知识库管理、日志与提示四方面：

- **纯本地**：所有数据处理（解析、切块、嵌入、检索、生成）与存储（源文件索引、向量库、元数据、缓存）均在本地完成。唯一的例外是用户显式将模型配置为云端 provider 的场景。
- **知识库导出 / 删除**：支持一键导出备份、一键删除全部派生数据（含向量、元数据、缓存、日志相关内容），删除前二次确认。
- **日志脱敏**：日志不记录对话正文、文件路径、文件名等敏感信息，仅保留脱敏的操作事件、耗时、错误类型与错误码。
- **隐私影响提示**：识图模型本地 / 云端选择直接影响"图片是否出网"，必须在配置处显著提示并需显式确认（见 4.7 第 7 条）。

**待拍板衔接**：基础框架第 9 章列出的「识图模型本地 vs 云端」作为开放问题，本节将提示机制定为必做，具体默认值与默认 provider 由第 9 章决议后回填。

### 用户故事

1. 作为用户，我希望确认我的数据从没离开过我的电脑，以便放心导入私密对话。
2. 作为用户，我希望一键删除知识库（含向量与缓存），以便不再需要时彻底清除、不留残余。
3. 作为用户，我希望一键导出知识库，以便备份或迁移到其他设备。
4. 作为用户，我希望在选云端识图模型前被明确提醒，以便我知情决定图片是否出网。

### 关键验收标准

1. WHEN 系统运行 THEN 所有数据处理、嵌入、检索、生成均在本地完成，知识库文件与向量库仅存储于本机数据目录。
2. IF 用户全程使用本地模型 / 本地嵌入 THEN 系统可保证文本与图片数据 100% 不出机。
3. IF 用户将任一模型配置为云端 provider THEN 系统在该场景执行前（尤其是图片入库、问答调用时）展示隐私提示，明确该操作会将相应数据发送至所选服务商。
4. WHEN 用户执行「删除知识库」THEN 系统清除源文件索引、向量库、元数据、缓存与日志中的相关内容，并二次确认后执行。
5. WHEN 用户执行「导出知识库」THEN 系统生成可移植的导出包（原始文档、元数据、向量 / 索引备份），供备份或迁移。
6. WHEN 系统写日志 THEN 日志中不得包含：对话正文内容、源文件路径、文件名、文档摘要等敏感信息；仅保留脱敏的操作事件、耗时、错误类型与错误码。
7. IF 错误信息需记录上下文用于排障 THEN 系统仅记录非敏感的结构信息（块数、文件类型、错误码），并提供一键清除日志的入口。
8. WHEN 系统展示隐私 / 安全相关设置 THEN 提供直观的「数据流向」视图：本地数据路径、各模型配置（本地 / 云端）、是否有数据外发，便于用户一眼确认。
9. IF 知识库数据目录权限异常或被外部访问 THEN 系统在启动时检测并提示，避免数据被意外读写。
10. WHEN 应用首次启动 THEN 系统向用户展示隐私承诺说明（数据本地化原则、例外场景、删除能力），供用户知情使用。
