## 2. 产品定位

### 2.1 一句话定位

**个人知识第二大脑——把本地文档与各 AI 平台的对话记录统一向量化，用自然语言问答即可快速找回"我说过的、查过的一切"，纯本地运行、答案永远带来源。**

对外传达的口径（诚实版）：

> **"AI 能快速找回我的一切。"**
> —— 不是"AI 知道我的一切"。

- **"找回"** 是我们承诺的全部：检索增强（RAG）——用户提问，系统从用户自己的语料中检索并作答。这是检索、是定位，不是生成记忆。
- **"知道"** 是过度承诺：任何宣称"AI 懂你"的产品都需要长期记忆建模、用户画像与主动预测能力，这是 v1.0 之后才有雏形的东西，且与我们"纯本地 + 可回溯"的信任路线冲突。
- 一句话定位必须能对外说出口而不产生误解——"找回"二字是定位与竞品（封闭记忆、云端大脑）的分界线。

### 2.2 价值主张

**核心价值一句话：省时省力——不用再向 AI 重复解释背景，不用再翻找"我之前说过什么"。**

拆解为四个层次的用户价值：

| 层次 | 价值 | 具体表现 |
|---|---|---|
| 时间价值 | 不再重复解释背景 | 提问时无需粘贴历史上下文，直接说"那个方案"，系统能自己找回背景 |
| 认知价值 | 不再翻找历史 | 跨 ChatGPT / Kimi / DeepSeek / 本地 MD 统一检索，一次找到分散在各处的结论 |
| 信任价值 | 可回溯、可验证 | 每个答案强制带来源（哪个文件/哪段对话/哪个平台），可反查原文，纯本地运行数据不出机 |
| 资产价值 | 对话资产化 | 平台对话随时可能被封/被清理/被遗忘，导出归档后成为**可检索、可复用的个人数据资产** |

**支持证据与逻辑（供验证的设计假设）：**

1. **重复解释背景是高频摩擦。** 重度用户每个会话都要"重新对齐"项目背景、技术栈、上下文，通常需要 30–60 秒打字或复制粘贴 [假设/需验证]。按每天 10 次提问估算，仅此一项每日消耗约 5–10 分钟。
2. **人类对"翻找"的容忍度极低。** 平台对话没有全文检索或检索极弱，用户通常宁可重新问一遍，也不愿翻几十条会话 [假设/需验证]——结果是同一问题的答案被反复重新生成，而非复用已有结论。
3. **"第二大脑"的价值随语料累积而增大。** 语料 < 50 个文档时手工翻找尚可忍受；一旦达到数百文档 + 数百条对话，结构化的笔记浏览方式（目录、标签）就会失效，语义检索成为唯一出路 [假设/需验证]。这正是本产品存在的时机点。
4. **隐私是信任的分水岭。** 知识工作者的语料（商业方案、财务、健康、技术文档）越有价值，越不可能上传云端。纯本地运行把"数据安全"从一句营销话术变成可验证的架构事实（数据不出机 + 可离线运行），这是云产品（personal.ai / Mem / Rewind）无法给出的承诺。

> 定位原则：我们卖的是**"找回"的效率与确定感**，不是"AI 帮你思考"。用户把语料交给系统，系统负责原样保管、快速回取；加工（总结、预测、画像）是后续版本的加分项，不是 MVP 承诺。

### 2.3 产品边界与反边界

#### 产品是（本产品做的事）

- **一个可检索的知识仓库**：统一向量化"本地文档 + 各 AI 平台导出的对话记录"，全量可被自然语言检索。
- **一个检索增强的问答器**：用户提问 → 语义检索 → 生成答案 → **强制标注来源**（文件/对话/平台 + 时间）。
- **一个可回溯的系统**：每个答案都能沿来源回查原文，知识来源透明可验证。
- **一个纯本地的工具**：所有数据、向量库、模型调用都在本机完成，数据不出机（识图模型本地 vs 云端待拍板，见 PRD 第 9 章风险）。

#### 产品不是（明确不做 / 反边界）

| 反边界 | 说明 | 为什么不做的逻辑 |
|---|---|---|
| ❌ 不是平台记忆替代品 | 不接入、不读取、不替代 ChatGPT/Kimi 等平台自身的记忆功能 | 平台记忆是封闭黑盒，无对话历史 API；token 接入被否决，走导出导入路线。我们的承诺是"你自己可控、可检索的记忆"，而非平台级记忆 |
| ❌ 不是全知 AI | 不做主动记忆、不预测用户、不自动给出未检索到的答案、不编造"我记得你说过" | 与诚实定位冲突；全知需长期画像能力（v1.0 才有雏形），且会损害可回溯信任。**只在你问的时候检索，只答检索到的内容** |
| ❌ 不是社交/协作平台 | 不做多用户、团队共享、协作编辑、知识广场 | 目标用户是个人深度用户；协作是另一类产品（Notion/Confluence），范围蔓延 |
| ❌ 不是云同步服务 | MVP 不做多设备同步、不做云账号、不做云端存储 | 纯本地是信任分水岭；云同步引入账号/鉴权/服务端，复杂度与信任成本均不可接受 |
| ❌ 不是通用爬虫/浏览器助手 | 不抓取网页链接内容、不做浏览器插件实时记录 | 范围蔓延 + 隐私风险（见 PRD 4.2 外链仅存元数据） |
| ❌ 不是实时记录器 | MVP 不做实时文件监听、不做录屏/屏幕记录 | 实时监听是增量同步的复杂度陷阱；录屏（Rewind/Recall 路线）太重且隐私争议大 |
| ❌ 不是"AI 助手本体" | 不做会话式闲聊、不做 Agent、不做自动执行任务 | 我们只负责"检索你的记忆"，生成交给用户自配的对话模型 |

**边界判断口诀**：凡是涉及"系统主动获取、主动推断、主动记忆"的，都不做；凡是"用户喂数据、系统保管、用户来取"的，都做。系统是被动可查的仓库，不是主动的管家。

### 2.4 成功指标

#### 北极星指标（North Star）

> **周活跃检索问答次数**：用户每周在本产品上发起自然语言检索问答的次数。

- 为什么是它：它同时衡量"知识库是否足够全（有东西可问）"与"检索是否足够好（问得出）"，直接对应产品最核心的承诺——"找回"被真实使用。单纯的检索命中率是技术指标，不反映用户是否真的持续使用；单纯的安装量不反映价值兑现。
- 换算逻辑：北极星 = 语料覆盖率 × 检索可用性 × 用户习惯。三者任一为 0，北极星即 0。
- **注意**：在 v0.1 个人 MVP 阶段（用户 ≈ 作者本人）该指标主要是自我验证；它作为北极星的价值在开源后社区化阶段才真正生效。个人阶段的北极星代理指标见下方"质量指标"。

#### 分阶段指标

**阶段 A：v0.1 个人 MVP（当前）——以质量指标为主**

| 指标 | 目标（假设） | 验证方式 | 是否假设 |
|---|---|---|---|
| 导入耗时 | 1000 个 MD 文件 / ~50 万 token 语料，冷启动全量导入 < 5 分钟 | 自测基准 | 数值为假设，方法已定 |
| 嵌入吞吐 | ≥ 100 文档/分钟（本地嵌入模型） | 自测基准 | [假设/需验证] |
| 增量同步成本 | 指纹比对扫描 1000 文件 < 1 秒；无变化时零重嵌入；局部修改仅更新局部块 | 自测基准 | [假设/需验证] |
| 检索命中率 | 自建评测集 Top-5 命中 ≥ 80%（语义切块 + 向量检索） | 构建 30–50 条自建评测问答集 | [假设/需验证] |
| 答案准确率 | 评测集上人工判定"答案可用且引用来源正确" ≥ 80% | 同上，人工评测 | [假设/需验证] |
| 来源标注正确率 | 100% 强制标注来源；来源指向准确 ≥ 95% | 人工抽查 | 强制标注为硬需求，准确率数值[假设/需验证] |
| 回答延迟 | 本地对话模型，首 token < 3 秒（流式） | 自测 | [假设/需验证] |
| 图片描述入库正确率（v0.2） | 识图模型对截图/图表的结构化描述可用率 ≥ 90% | 图片评测集 | [假设/需验证] |

**阶段 B：开源后社区阶段——北极星指标生效**

| 指标 | 目标（假设） | 说明 | 是否假设 |
|---|---|---|---|
| 周活跃检索问答次数（北极星） | 活跃用户 ≥ 5 次/周 | 核心承诺兑现度 | 目标值[假设/需验证] |
| 4 周留存 | ≥ 30% | 工具型产品留存基准 [假设/需验证] | [假设/需验证] |
| 使用频次分布 | 每日 > 0 的"高频用户"占比 ≥ 20% | 反映"真当成第二大脑用"而非尝鲜 | [假设/需验证] |
| 数据导入完成率 | 成功完成首次全量导入并建库的用户占比 ≥ 80% | 导入体验是漏斗第一关 | [假设/需验证] |
| 增量同步使用率 | 周活用户中每周至少同步一次占比 ≥ 70% | 不常青的知识库会衰减 | [假设/需验证] |

**阶段 C：开源价值指标——衡量"开源是否成立"**

| 指标 | 意义 |
|---|---|
| GitHub Stars / Forks | 知名度与初步认可（参考值：工具型个人项目健康量级为数百~数千 star [假设/需验证]） |
| 外部贡献者数量 | **关键转折**：是否有非作者本人的外部 PR 被合并（>3 人持续贡献 = 开源真正活过来） |
| PR / Issue 响应速度与合并率 | 社区治理健康度 |
| 平台导入器贡献数量 | 架构"只认 Markdown + 适配器"是否真的降低了贡献门槛 |
| 是否有用户自发在技术社区（HN / Reddit / V2EX 等）传播 | 真实性口碑，非投放效果 |

> **明确标注**：除"来源标注 100% 强制""数据不出机"为硬性产品承诺外，上表**所有目标数值均为假设**，须在 v0.1 阶段用真实自测数据替换后，才能进入开源阶段作为对外指标。任何数值不达预期不构成产品失败信号，只构成设计迭代输入。

### 2.5 用户画像（Persona）

> 目标用户画像的元原则：**先服务产品作者自己这一类人**——小众深度用户，不是大众。三类画像按优先级排列，Persona A 是产品"为谁而做"的锚点。

#### Persona A — 核心画像：多平台重度 AI 用户 + 有本地文档的知识工作者

- **背景**：30 岁左右的技术从业者/研究者/内容创作者。每天在 ChatGPT / Kimi / DeepSeek 等 3 个以上 AI 平台提问，日均 10–30 次交互。本机有几十到上百个 Markdown 笔记/文档/报告，多年累积。会用命令行，能装依赖、看报错、改配置。
- **痛点**：
  - 每次新会话都要重新解释项目背景、技术栈、上下文，浪费时间；
  - 想找"我上次跟 AI 讨论的某结论"却翻不到——平台历史无检索或检索极弱；
  - 同一主题的讨论碎片分散在多个平台 + 本地笔记，无法一次看清全貌；
  - 平台"记忆"功能是黑盒，不可检索、不可导出、不可控；
  - 有价值语料（商业/财务/健康/技术）不敢放进云端工具。
- **期望**：一个"问一句就找回"的统一检索层；答案带来源、可回溯；纯本地、数据绝对可控；首次配置后低维护（增量同步自动）。
- **付费/参与意愿**：**高**。愿意花一个周末搭环境、愿意接受"为数据主权付费"（一次性买断或小额订阅）、愿意在 GitHub 提 Issue/PR、愿意为开源项目贡献导入器——**这正是产品从"个人工具"走向"开源产品"的种子用户**。

#### Persona B — 次级画像：内容型知识工作者（研究者 / 分析师 / 自媒体）

- **背景**：靠写作、调研、分析吃饭的人（行业研究员、播客主、学术作者）。AI 是核心生产力工具，本地沉淀大量访谈记录、草稿、AI 辅助生成的调研材料。技术门槛中等——会用 Markdown、能按教程操作，但不热衷折腾。
- **痛点**：研究过程碎片化，写稿/出报告时要"考古"——翻旧对话、翻旧文档拼出完整的论证链；引用时记不清出处；重复向 AI 解释同一个课题的背景。
- **期望**：检索快、答案带可引用的出处、能跨对话与文档拼出上下文（v1.0 跨源融合）；隐私要求高（稿子未发布前绝不能泄露）。
- **付费/参与意愿**：**中高，但门槛敏感**。愿意为效率付费，但如果"先装 Python 环境再配置三套模型"则直接流失——**这类用户决定产品的易用性下限，是开源后"让普通人也能用"的拉动力量**。MVP 阶段不为其优化（先服务 Persona A），但验证期要留意其反馈。

#### Persona C — 次要用例画像：本地笔记党 / 数据主权原教旨主义者

- **背景**：Obsidian / Logseq / Typora 用户，本地 Markdown 笔记库已达数百篇。数据主权意识极强，拒绝任何"内容上云"的工具。与 A 的重合度高，但核心动机是**检索自己的笔记**而非"AI 对话记忆"。
- **痛点**：笔记库大了以后，目录/标签/链接式浏览失效，找不到"我半年前写的那个方案"；AI 对话内容无法和笔记放一起统一检索；对云 RAG 工具（Notion AI / 各种 SaaS）零信任。
- **期望**：作为笔记工具的**补充检索层**（而非替代品）；纯本地；简单——"给我的笔记库装一个会检索的问答层"。
- **付费/参与意愿**：**高**（数据主权是强付费动机），但**对"又多一个工具"有天然抵触**——如果无法证明比 Obsidian 自带搜索 + 内置 AI 更好，会被拒绝。这提示产品定位要强调"统一检索层"而非"新笔记应用"。

### 2.6 典型场景用户故事

> 场景按"我什么时候会用它"写成，全部源自真实工作流的复现，不编造夸张用例。目标：每个故事都能对上至少一个目标用户可立刻对照的瞬间。

**故事 1（周报 / 汇报场景）——核心场景的高频触发点**
> "我之前跟 ChatGPT 聊过一个方案，现在要写周报，直接问它。"
> 周一写周报，输入"我上周跟 ChatGPT 讨论的 K8s 迁移方案，当时得出了什么结论、有什么遗留风险？"——系统检索到上周那段对话，答案带来源标注（ChatGPT · 上周二 · 那段关于迁移的讨论），用户直接复述 + 引用，不用翻聊天记录，也不用重新问一遍。

**故事 2（问题复现 / 调试场景）**
> "这个 bug 三个月前在 Kimi 上问过解法，现在又遇到了。"
> 生产环境报同一个错，用户懒得翻三个月前的聊天窗口，直接问"之前遇到过 Postgres 连接数被打满的问题，当时的排查思路是什么？"——命中三处：两段 Kimi 对话 + 一份本地排查文档，拼出完整排查路径，直接复用。

**故事 3（决策复盘 / 上下文找回场景）**
> "AI 替我做过一次技术选型，我现在要写方案，需要当时的关键论据。"
> 需要为当前项目重写技术选型方案，问"我之前对比过 ClickHouse 和 DuckDB，结论倾向哪个、反对理由是什么？"——检索到当时的多轮对话，答案不仅给结论，还给当时考虑过的关键约束，用户不必重新思考一遍。

**故事 4（笔记检索 / 找回"我写过的东西"场景）**
> "我半年前在本地笔记里写过那个方案，不记得放哪个文件夹了。"
> 本地几百个 MD 文件，标题记不清、目录找不动，直接自然语言问"我写过的关于团队知识库冷启动的笔记里提到过哪些工具？"——语义检索跳过文件名/目录层级，直接定位内容。

**故事 5（隐私敏感 / 不能上云场景）**
> "这是个只能本地算的材料，绝不能让任何云端工具碰到。"
> 处理财务/健康/未公开的商业方案时，全程离线、纯本地检索问答；即使断网也能用（本地模型）。这个场景的用户价值不是"快"，而是"只有它能接"——是信任分水岭的直接兑现。

**故事 6（图片记忆 / 信息扩展场景，v0.2 起）**
> "这个截图里的数据，我记得讨论过，现在想找出来。"
> 用户截图过某张图表/某个方案讨论，问"我收藏过的那张用户增长曲线的截图里，关于留存拐点的结论是什么？"——图片经多模态转文字描述入库，可被文字检索；问答时还可把原图喂给识图模型"看图作答"。

### 2.7 核心场景优先级

按"先能问得出来 → 再用得久 → 再更全 → 再更强"排序，与 MVP 清单（PRD 第 6 节）一致，此处给出**为什么这个顺序**：

| 优先级 | 场景 | 为什么排在这里 |
|---|---|---|
| **P0** | 统一可检索、可回溯的问答（跨平台对话 + 本地文档，答案强制带来源） | 这是产品存在的前提与差异化根本（竞品只做文档 RAG 或封闭记忆）。没有它，其余一切无意义 |
| **P0** | 数据接入与导入体验（第三方导出 → Markdown 归一化 + 手动同步/增量） | 没有语料就没有检索。导入是漏斗第一关；增量同步决定"是否愿意长期维护"，决定了知识库是否常青。两者是 P0，因为它们是"问得出来"与"用得久"的地基 |
| **P1** | 纯本地部署 + 隐私保障（数据不出机） | 信任分水岭，一次性架构决策，属于"必须从一开始就是真的"而非"后续优化"。优先级高，但因与场景实现解耦，故标 P1 非 P0 阶段顺序 |
| **P1** | 图片转文字描述入库 | 显著扩大覆盖（截图、图表、邮件），"第二大脑"不能对图片失明。v0.2 门槛，且纯文本用户可不配识图模型（100% 不出机） |
| **P2** | 问答时喂图"看图作答"增强、混合检索 + 重排、更多文档类型 | 体验增强与质量提升，非生存功能，放 v0.2 之后 |
| **P3** | 跨源融合排序、记忆摘要/用户画像、更多平台导入器 | 这些是"更强"的差异化延伸（v1.0），但依赖 P0 的用户量与语料积累才有意义，过早做是范围蔓延 |

**排序逻辑一句话**：P0 回答"它有没有用"，P1 回答"我敢不敢用、能不能全"，P2–P3 回答"它好不好、强不强"。先证明有用与可信，再追求好与强。

### 2.8 非目标用户

明确"谁不是我们的用户"，防止在错误人群上投入：

| 非目标用户 | 为什么不服务 | 拒绝的代价（若有） |
|---|---|---|
| 只用单一 AI 平台的轻度用户 | 聊天历史少、无跨平台碎片化痛点，"第二大脑"没有足够语料值得导入；为 5 条对话配置整套流程不划算 | 无——这类用户本来就不属于本产品价值区间 |
| 不愿做数据搬家/导出的用户 | 产品价值 100% 建立在"把语料导入进来"之上；导出这一步做不到，后续价值归零 | 无——这正是小众定位的代价与选择 |
| 期待"AI 全知"、想要即开即用聊天体验的用户 | 我们明确不做主动记忆与全知 AI；这类用户会因"它不知道我上次没说的事"而失望 | 需在对外文案中持续用"找回"而非"知道"来校准预期 |
| 需要团队协作/共享知识库的用户 | 不做社交/协作/多用户（见 2.3 反边界） | 无 |
| 完全云优先、不介意隐私的用户 | 云同步/多设备/即开即用是他们的优先项，恰是我们的反边界；强推纯本地只会两败 | 无 |
| 依赖"开箱即用、零配置"的非技术用户 | 需要本地装模型、配依赖，技术门槛天然排除纯小白；MVP 阶段不为他们优化 | 这是开源后社区化阶段的长期课题（易用性下限），非当前目标 |

**非目标用户判断准则**：凡是其核心诉求落在我方反边界（云同步、协作、全知、零配置）上的，都不是目标用户——不争论，直接不做。**先服务 Persona A（产品作者同类人），再借助开源辐射 Persona B/C**，是清晰的路径而非妥协。
