## 1. 总体架构

### 1.1 架构原则

| 原则 | 含义 | 落地约束 |
|---|---|---|
| 本地优先 | 核心链路（切块/嵌入/向量库/检索）不依赖任何外部服务 | 嵌入模型必为本地模型；向量库为嵌入式进程内库 |
| 纯文本不出机（默认） | 文本数据默认永不离开本机；出网仅在用户显式配置云端模型时发生 | 见 §5 出网清单 |
| 入库一次、检索多次 | 入库阶段是唯一的计算重活（切块/识图/嵌入）；问答阶段只做检索+生成 | 识图与嵌入结果全部落盘缓存 |
| 可插拔 | 对话模型、识图模型、向量库、嵌入模型均以接口抽象，可替换 | 见 §3 各选型的 Repository/Provider 模式 |
| 简单优先 | MVP 用最简单的架构换取可迭代速度，复杂的重排/混合检索延后 | 见 §6 搜索演进路径 |

### 1.2 模块划分（对齐 PRD 5.2）

```
┌──────────────────────── 应用层 ────────────────────────┐
│  Dashboard(Web UI)   │  模型配置管理   │  增量同步调度     │
└──────────────┬───────────────────────────────┬─────────┘
               │ HTTP/SSE                       │ 启动+手动触发
┌──────────────▼───────────────────────────────▼─────────┐
│                     后端服务层 (FastAPI)                  │
│  数据接入层  文档处理管线   检索层    问答生成(流式)         │
│  (MD读取)   (解析/切块/识图) (向量检索)  (LLM+来源标注)      │
└──────────────┬──────────────┬──────────────┬────────────┘
        │             │             │            │
┌───────▼────┐ ┌───────▼────┐ ┌─────▼─────┐ ┌───▼─────────┐
│ 指纹/去重表 │ │ 嵌入模型引擎 │ │ 向量库适配层 │ │ 对话模型适配层 │
│  (SQLite)  │ │ (本地 ONNX) │ │ (Chroma)   │ │ (OpenAI兼容) │
└────────────┘ └────────────┘ └───────────┘ └─────────────┘
```

核心设计：**所有外部能力（向量库/嵌入/对话/识图）都通过薄适配层（Provider 接口）访问**，MVP 只实现默认 Provider，切换成本被隔离在单点，支撑后续开源阶段的社区可插拔适配器。

### 1.3 数据流

**入库（Ingestion）**：

```
本地目录/导入文件(MD)
   │ ① 扫描 + 指纹比对（未变跳过 / 新增处理 / 删除移除）
   ▼
数据接入层 → Markdown 归一化（标题层级/代码块/对话块/图片引用/元数据头）
   │ ② 按语义结构切块（标题锚点优先，见 §4.3）
   ▼
文档处理管线
   ├─ 纯文本块 ──────────────► 嵌入(本地) ──► 向量库 upsert（带元数据）
   ├─ 图片 ──► 识图模型(本地/可选云端)
   │             │ 文字描述 + 原图路径(元数据)
   │             ▼
   │          描述作为文本块 ──► 嵌入(本地) ──► 向量库 upsert
   └─ 对话导出 ──► 对话级去重键校验(§4.2) ──► 按消息/会话切块 ──► 嵌入
   │                                                      │
   ▼                                                      ▼
指纹/去重状态表(SQLite) 更新                       完成，可检索
```

**问答（Q&A / Generation）**：

```
用户问题
   │ ① 问题文本 → 嵌入(本地，同一模型，保证同向量空间)
   ▼
检索层：向量 top-K（可选 元数据过滤：平台/来源/时间）  →(v0.2) 混合BM25 →(v1.0) Rerank
   │ ② 命中块 + 来源元数据 + 命中图片路径
   ▼
问答生成：组装 Prompt（含检索上下文 + 强制来源标注指令）→ 对话模型
   │ ③ 流式输出（SSE，见 §3.4）
   ▼
Dashboard：流式渲染答案 + 来源卡片（文件/对话/平台/图片缩略图）
   │
   └─(可选增强, v0.2) 命中图片时，把原图 + 问题喂给多模态模型"看图作答"
```

### 1.4 运行形态与数据落盘

- 单进程运行：FastAPI 后端 + 同源静态前端，默认绑定 `127.0.0.1:<随机端口>`。
- 落盘数据（全部位于用户数据目录，如 `~/.everything-rag/`）：
  - 向量库（Chroma 持久化目录）
  - 状态库 `state.db`（SQLite：指纹表、去重键表、切块清单、任务日志）
  - 配置 `config.json`（模型配置、密钥占位引用，见 §5.3）
  - 导入日志（脱敏）
- 不拷贝、不移动用户的原始 MD 文件：原始文件就地引用，路径存入元数据（符合「原图路径存元数据用于展示」的既定决策）。

## 2. 多模态 RAG 管线落地（方案 B）

### 2.1 识图模型选型：本地 vs 云端（待拍板① → 本子代理推荐）

**推荐：本地 VLM 为默认，云端 OpenAI 兼容 VLM 为可选项。**

理由：

1. **与产品核心卖点一致**：产品边界是「数据不出本机」。识图发生在入库阶段（一次性、可异步、无延迟敏感），本地 4–8B 级别 VLM 生成的文字描述对检索召回而言质量足够——检索要的是「能搜到」，不是「描述完美」。
2. **本地硬件门槛可控**：Qwen2-VL-7B / MiniCPM-V-8B 级别模型需要约 8GB 显存（或 Apple Silicon 16GB 统一内存、或量化后 8GB 内存）。无该硬件的用户走「可选云端」或「关闭图片功能」，三种路径都在产品内闭环，不强迫所有人配 GPU。
3. **云端质量更高但引入出网**：GPT-4o / Claude / 通义千问 VL 级别云端 VLM 描述准确率明显更高（尤其图表、表格、长截图）。但它要求图片出网，且产生调用成本。→ 作为显式开关的可选项，不破坏默认的隐私承诺。
4. **MVP 决策简化**：识图模型与对话模型统一走「OpenAI 兼容」接口抽象——本地跑 Ollama/llama.cpp 暴露的就是 OpenAI 兼容端点，云端也是。一条 Provider 代码同时服务「本地 Ollama」和「云端 API」，切换只是改配置，不会因此分叉两套代码。

**落地建议（型号方向，以官方文档为准）**：
- 本地默认：`Qwen2-VL-7B`（Apache-2.0，中文识图强）或 `MiniCPM-V-8B`（体积/显存占用友好），通过 Ollama / llama.cpp(GGUF) 以 OpenAI 兼容模式暴露。
- 云端可选：任何 OpenAI 兼容 VLM 端点（如 GPT-4o、Claude、通义千问 VL），配置项为 base_url + model + key。
- 质量兜底：描述 Prompt 固定模板化——「画面主体 + 场景/物体/人物 + 图中文字(OCR) + 图表数据 + 与周边上下文的关系」，保证跨模型描述格式稳定、可检索。
- 性能兜底：识图在入库管线中是慢路径，MVP 做**异步批量**处理（先入库文本块，图片描述后台补全后 upsert），避免一张慢图阻塞整个导入。

### 2.2 入库管线技术实现

```
图片引用(MD内 ![](path) 或 图片文件夹)
  → 图片解码（PIL/opencv 校验、EXIF 方向修正、过大降采样到 VLM 输入上限）
  → 识图模型 → 结构化文字描述（模板化 Prompt）
  → 描述文本 → 与文本同一嵌入模型 → 向量
  → 向量库 upsert，元数据：
       type=image_description
       source_file / source_platform / created_time（继承所在文档/对话的元数据）
       image_path（原图绝对路径，仅用于展示）
       block_id（稳定锚点，用于局部更新，见 §4.3）
  → 命中时前端据 image_path 渲染原图缩略图 / 大图
```

要点：
- **描述与文本共用同一嵌入空间**：这是方案 B 的本质优势——图内容可被纯文本问题直接检索，无需第二套向量空间。
- **继承上下文元数据**：图片描述块的平台/来源/时间继承自其所在文档或对话，保证来源标注一致。
- **原图只存路径**：不复制图片文件进产品目录，降低存储膨胀与隐私面。

### 2.3 可选增强：问答时喂原图（v0.2，不替代方案 B）

技术实现：

```
检索命中 image_description 块（或命中其所在文档且问题疑似涉及图）
  → 取元数据中 image_path
  → 将原图 + 用户问题 + 检索到的文本上下文 组装进多模态模型 Prompt
  → 多模态模型"看图作答"，结果同样流式输出 + 标注来源
```

要点：
- 复用与识图同一套「多模态模型 Provider」，不新增模型家族。
- 出网语义必须清晰：若该多模态模型是云端，则**问答时图片会出网**——UI 需在「问答增强」开启处显式提示，且默认关闭。
- 是否喂图需要判定策略：MVP 简单规则 = 命中的 top-K 块中有 `type=image_description` 且用户问题与图片描述块相关（可先用粗召回命中直接触发）；更智能的「何时该看图」判定留待 v1.0。

### 2.4 为何不用 CLIP（L3）与 ColPali 作为 MVP 主线

| 方案 | 问题 | 结论 |
|---|---|---|
| **CLIP 图像向量（L3）** | ① 图像向量位于 **CLIP 自己的向量空间**，与文本嵌入（bge/gte）空间不兼容——要么用 CLIP 文本编码器单独做一路检索（两套空间、两套索引、排序无法统一），要么做跨模态投影（重、需训练数据）；② CLIP 对**密集文字、图表、OCR 场景召回差**，恰好是本产品（对话截图、文档配图）的主体；③ 增加一个 1–2GB 级模型 + 双向量库复杂度。收益与成本严重不成比例。 | MVP 不用；文本嵌入空间已经能检索到「文字描述」，v1.0 前无场景补强需求 |
| **ColPali（整页视觉文档检索）** | ① 设计目标是 **PDF/文档页面级**视觉检索，本产品 MVP 明确不做 PDF；② 需要 ColPali VLM 做整页向量化，**单页多向量**、存储与内存开销显著；③ 与方案 B（MD 文本为主 + 少数图片）重叠度低。 | 本产品即使 v1.0 做 PDF，也应优先评估「PDF→文本+版面识别→方案 B」而非直接上 ColPali；ColPali 仅作为远期 PDF 场景的备选调研项 |
| **方案 B（VLM 描述）** | 主流务实做法，图内容变文字后可被任意文本检索复用全部下游（混合检索/重排），原图路径保证展示闭环。 | **MVP 主线，已定** |

结论：CLIP / ColPali 均不进入 MVP 路线图；文档中保留为「远期 PDF 场景」调研项即可。

## 3. 技术选型对比

### 3.1 语言与生态（待拍板③ → 本子代理推荐：Python）

| 维度 | Python | TypeScript |
|---|---|---|
| RAG/ML 生态 | **最全**：sentence-transformers、fastembed(ONNX)、chromadb/lancedb、transformers、unstructured、rank_bm25、bge/rerank 全部 Python 一等公民 | 生态在追赶，但嵌入/切块/重排等库往往只是 Python 库的 JS 移植或包装，功能与维护滞后 |
| 本地模型推理 | **强**：ONNX Runtime / llama.cpp 绑定 / Ollama(OpenAI兼容) 均可直接调用 | 需依赖 Ollama/外部进程，或较弱的 onnxruntime-node 体验 |
| 桌面打包 | 弱（pyinstaller 等可用但体验一般） | **强**（Tauri/Electron 原生友好） |
| 后端服务 | FastAPI 生态成熟，SSE 流式一行实现 | Node/Deno 也可以，但需要自己拼 RAG 栈 |

**推荐：Python（核心管线全用 Python），前端用 Web 静态资源承载。**
- 理由：本产品的技术含量 80% 集中在「切块→嵌入→向量库→检索→重排」这条 RAG 链路上，Python 是这条链路生态最完整、迭代最快的语言；打包诉求靠「本地 Web 服务」形态化解（见 §3.5），因此 TypeScript 的桌面打包优势在 MVP 阶段不构成决策权重。
- 关键框架：FastAPI（API + SSE 流式）、pydantic（配置校验）、sentence-transformers / fastembed（本地嵌入）、Pillow（图片解码）。
- 并发：入库管线用 asyncio + 线程池（嵌入/识图为 CPU/GPU 密集，进程内线程池即可，MVP 单用户无需多进程）。
- 备选：若未来开源阶段强推「无 Python 环境的桌面分发」，可在 v1.0 评估「核心 RAG 用 Python 独立 CLI/服务 + Tauri 壳调用」的混合形态，而非整体迁移语言。

### 3.2 向量数据库（本地优先）

| 方案 | 形态 | 增量更新 | 元数据过滤 | 嵌入进程 | MVP 评价 |
|---|---|---|---|---|---|
| **Chroma** | 进程内嵌入，持久化到本地目录 | 按 ID upsert/delete，支持 | 支持（含来源/平台/时间过滤） | ✅ 原生 | **推荐**：API 最简，个人规模（<100 万块）性能足够，Python 生态最顺 |
| LanceDB | 进程内嵌入式（Lance 列存） | 按 ID upsert/delete，支持 | 支持 | ✅ 原生 | 备选：单文件、可处理更大数据，开源分发更干净；API 表达力略弱 |
| SQLite-vec | 进程内，单文件 | 支持（但需自管索引重建策略） | 支持（走 SQL） | ⚠️ 需自接 | 备选：极端可嵌入（单文件分发），但 HNSW 索引与增量维护需自研，MVP 不划算 |
| Qdrant（本地模式） | **独立进程**（本地也需跑 server） | 支持 | 强 | ❌ 需单独进程 | 备选/远期：性能与过滤最强，但「多一个进程」违背 MVP 的简单优先与分发便利 |

**推荐：Chroma 为 MVP 默认；抽象 `VectorStore` 接口（Repository 模式）隔离实现，开源阶段再评估 LanceDB/Qdrant。**
- 理由：本产品量级是「个人知识库」（预估 1 万–100 万切块），Chroma 的进程内 API、按 ID upsert/delete、元数据过滤正好覆盖全部 MVP 需求（来源标注需要元数据过滤；增量同步需要按 ID 增删）。SQLite-vec 的「单文件」优势要在 v1.0 做开源分发时才有意义，届时通过接口切换即可，不阻塞 MVP。
- 注意：所有对向量库的写操作必须走统一仓储接口，禁止在业务层直接拼 SQL/查询，保证切换成本可控。
- 距离度量：用余弦距离（bge/gte 均按归一化向量使用）。

### 3.3 嵌入模型（本地必配）

| 候选 | 多语言 | 维度 | 体积/资源 | 特点 |
|---|---|---|---|---|
| **bge-m3**（推荐默认） | 强（中英为主 100+ 语言） | 1024 | ~2GB 权重（可 ONNX 量化） | 长文本 8192、多向量（稠密+稀疏+ColBERT）；稀疏向量可复用做 BM25 混合检索（§6.2），一条模型两用 |
| **gte-multilingual-base** | 强 | 768 | ~1GB | 轻量备选，显存/内存紧张机器更友好 |
| bge-small-zh-v1.5 | 中文为主 | 512 | ~100MB | 极轻量，但英文/混合语料召回弱，仅兜底 |

- **推荐：本地 bge-m3（默认），gte-multilingual-base 为轻量备选，运行层用 ONNX Runtime（sentence-transformers 或 fastembed）以降低依赖与启动开销。**
- 云端 API（如 OpenAI text-embedding-3）不作为默认：嵌入发生在入库与每次提问两个环节，云端嵌入会让「文本不出机」的承诺破功。仅作为隐私要求较低用户的显式可选配置。
- 关键硬约束：**问答时的问题嵌入必须与入库用同一模型**（同向量空间），故嵌入模型是「必配且全局唯一」的单一配置项。
- 中文/英文混合场景：bge-m3 与 gte-multilingual 均原生覆盖，无需分词预处理。

### 3.4 对话模型与流式输出

**对话模型：可插拔，默认本地、支持云端（OpenAI 兼容统一接口）。**

- 默认：本地推理（Ollama / llama.cpp 暴露 OpenAI 兼容端点），MVP 推荐 Qwen2.5-7B-Instruct 级别（以官方文档为准），个人 PC 无独显时退化到更小量化档。
- 可选：任何 OpenAI 兼容云端 API（DeepSeek / 通义 / Kimi / OpenAI 等），base_url + model + key 三项配置即可。
- 与识图模型共用同一 `ChatModel` Provider 抽象：本地与云端只是不同 base_url。这让「纯本地」与「云端」两种用户都只维护一条代码路径。
- 隐私语义（见 §5 出网清单）：云端对话模型意味着「问题 + 检索到的上下文」出网，UI 必须在模型配置处显式提示。

**流式输出：SSE（Server-Sent Events），不用 WebSocket。**

| 方案 | 方向 | 复杂度 | 适用 | 结论 |
|---|---|---|---|---|
| **SSE** | 单向 服务器→客户端 | 低：FastAPI `StreamingResponse` + 前端 `EventSource` 即用 | LLM 流式输出天然单向，正好契合 | **推荐**：MVP 用 SSE |
| WebSocket | 双向 | 高：需协议协商、心跳、断线重连、反向代理适配 | 需要客户端中途改请求/推送时才需要 | 不用；MVP 无此诉求 |

- 理由：LLM 流式是纯下行数据流，SSE 用标准 HTTP、可自动重连、在 FastAPI 与浏览器端都是一行级实现；WebSocket 为双向带来的复杂度在 MVP 完全用不上。
- 演进：流式出口做一层 `StreamOutput` 抽象（目前实现 SSE），未来若需「取消生成」「服务端主动推送状态」再叠加 WebSocket 通道，不推翻现有接口。
- 取消机制（可选 MVP 内）：SSE 连接断开即停止生成，天然满足「用户关闭页面即取消」。

### 3.5 部署/打包形态（待拍板② → 本子代理推荐：本地 Web 服务）与开源许可

| 形态 | 体验 | 复杂度 | MVP 评价 |
|---|---|---|---|
| **本地 Web 服务**（推荐） | 启动后端 + 浏览器打开 `127.0.0.1:port`，无需安装壳 | **最低**：一套 Python 后端 + 静态前端 | **MVP 用这个**：跨平台、零原生工具链、迭代最快 |
| Tauri（桌面壳） | 原生窗口，托盘/开机自启 | 中：需 Rust 工具链，但前端可复用 Web 版 | 开源阶段（v1.0 后）可选：把 Web 前端套一层轻壳 |
| Electron | 原生窗口 | 中高：包体大（~100MB+）、内存占用高 | 备选：生态成熟但重，非首选 |
| Docker（服务形态） | 容器化部署 | 中：适合未来「家庭服务器/多用户」 | v1.0 后考虑：个人 MVP 上 Docker 是负资产（用户要装 Docker） |

**推荐：MVP = 本地 Web 服务（FastAPI 后端 + 同源静态前端，浏览器访问）。**
- 理由：① 最符合「个人工具」定位，零安装摩擦；② Python 后端天然在此形态最优（无需引入 Rust/Node 编译链）；③ 前端是纯静态资源，未来 Tauri/Electron 直接复用，打包演进不被锁死；④ 避免 Electron 的包体/内存问题。
- 前端技术：MVP 建议轻量 SPA（React 或 Vue 构建产物由 FastAPI 托管，二选一即可，不影响架构决策）；若想极致简化，纯 HTML+少量 JS 也能支撑（无构建步骤），作为 MVP 起点。
- 端口安全：绑定 `127.0.0.1` + 随机端口；不用 0.0.0.0（见 §5.4）。

**开源许可：Apache-2.0（产品代码）。**
- 理由：宽松许可利于社区 Fork 与二次分发，无传染性义务（比 GPL 友好，比 CC-BY-NC 无约束），与同类工具（如 AnythingLLM 的 MIT、RAGFlow 的 Apache-2.0）生态相容。
- **必须单列的许可风险**：产品所捆绑的「模型权重」各自有 License，且与产品代码的 Apache-2.0 无必然关联：
  - bge 系列、Qwen2-VL/2.5（Apache-2.0 或 MIT，以官方为准）——可商用可再分发；
  - 部分备选模型（如某些 Qwen-VL 早期版本为 CC-BY-NC、部分 rerank/CLIP 模型受限）——**非商用**，**严禁默认捆绑**。
  - 落地约束：模型下载与许可选择必须在「模型配置」中显式列出每个模型的许可证；凡默认推荐/内置下载的模型必须为宽松许可。此条由安全/法务评审把关。

### 3.6 选型汇总

| 决策点 | 推荐 | 备选 | 关键理由 |
|---|---|---|---|
| 语言/生态 | **Python**（FastAPI + asyncio） | TypeScript（v1.0 混合形态再评估） | RAG 生态最全，打包诉求被 Web 形态化解 |
| 向量库 | **Chroma**（进程内） | LanceDB →（远期）Qdrant | 个人规模够用、API 最简、增量/过滤齐全；接口隔离切换 |

| 部署形态 | **本地 Web 服务** | Tauri（v1.0 后套壳） | 零安装、迭代最快、前端可复用 |

| 状态存储 | SQLite（指纹/去重/切块清单/任务日志） | — | 单文件、事务、零运维 |

## 4. 增量同步技术约束

### 4.1 指纹比对

```
state.db: files(id, path, mtime_ns, size, content_hash, last_ingested_at, status)
```

- **快路径（毫秒级扫描）**：`(mtime, size)` 未变 → 跳过。这是「启动检查 + 手动同步」不卡顿的关键，全库扫描只做 stat，不做内容读。
- **慢路径（内容级复核）**：`(mtime, size)` 变了 → 读文件算 `content_hash`（xxh64 足够，冲突概率对本量级可忽略），与库中比对：
  - 未变（仅 touch 过）→ 只更新 mtime，不重处理；
  - 变了 → 标记该文件需重新入库；
  - 库中存在但磁盘缺失 → 标记删除。
- **删除一致性**：文件删除时，依据「文件→块 ID 清单」（切块清单表）级联删除向量库中该文件全部块 + 状态表记录，避免孤儿向量。
- 异常兜底：文件读取失败（编码/损坏）→ 记录失败清单并在 UI 提示，不中断整体同步。

### 4.2 对话级去重键设计

**核心矛盾**：用户手动编辑导出文件（加笔记、改排版）会改变文件 hash，但「这段对话」内容本身没变——因此**去重键锚定对话内容，而不是文件 hash**（既定决策）。

- **去重键设计**：`dedup_key = hash(归一化(platform + conversation_id))`。
  - `platform`：来源平台（ChatGPT / Kimi / DeepSeek / 本地文档）；
  - `conversation_id`：优先用导出数据自带的会话 ID/标题；缺失时退化用 `首条消息内容归一化 + 消息条数` 组合键。
  - `归一化`：去除空白/时间戳噪音、统一换行、可选降级大小写，抵抗「仅格式变化」的误判。
- **语义**：同一对话无论出现在哪个导出文件、被编辑过多少次，只入库一次。**文件重排/合并/拆分不影响去重正确性**（键在对话级而非文件级）。
- 去重键表：`conversations(dedup_key, file_path, last_seen, status)`，同步时标记 `last_seen`，某轮同步未被任何文件引用（last_seen 过期）→ 判定对话被删除 → 级联删其块。
- 同一文件内多次出现同一对话：以第一次为准，后续引用合并（`last_seen` 刷新）。

### 4.3 语义切块与边界防漂移

**目标**：局部修改只更新局部块，邻近块边界不因编辑产生漂移、不触发全量重嵌。

- **默认策略：标题锚点分层切块**（基于 MD 结构，而非固定窗口）。
  - 以 Markdown 标题（`#`~`####`）为边界切分；单块超长时按段落再细分；
  - 对话导出以「会话/消息组」为天然边界（每则消息或按角色聚合为一到多块）；
  - **块 ID = 锚点路径（标题层级链）+ 相对序号**，如 `hash(doc)::/H1/笔记方法/H2/检索#3`。
- **防漂移机制**：
  1. 块边界绑定「锚点」而非「绝对偏移量」——绝对偏移会随行文增删而漂移，标题锚点稳定；
  2. 一个锚点区间内内容变化 → 只重嵌该锚点下的块（块 hash 变化即 upsert），其他锚点块 `block_id` 不变、不动；
  3. 锚点被删除 → 只删该锚点下块；
  4. 无标题的文档（纯笔记）：退化按段落顺序切块，块 ID 用「段落 hash 前缀 + 序号」，此时允许小概率局部漂移（该文档内），作为可接受的 MVP 折衷，并在 v0.2 评估滑动窗口重叠补偿。
- **重叠与召回**：块间保留少量重叠（如每块尾部重叠 1–2 句或按标题上下文拼接），保证跨块语义不割裂；重叠块各自有独立 block_id，不互相包含。
- **切块结果缓存**：切块清单表记录「锚点→块ID→内容 hash→嵌入向量 ID」映射，同步时先用锚点层判断哪些块需要重嵌，未变块直接跳过嵌入（成本大头在嵌入，跳过即省）。

## 5. 隐私与安全架构

### 5.1 数据本地化边界

**默认边界：用户原始文件、向量库、状态库、配置全部驻留本机磁盘；除「用户显式启用的云端模型」外，不产生任何出网流量。**

- 入库链路的三个计算节点（切块 / 嵌入 / 向量库）**全部本地**，嵌入模型为本地必配（§3.3），这是「纯文本用户数据 100% 不出机」承诺的技术基础。
- 识图与对话为可配置：默认本地；用户选择云端端点时才出网，且出网对象有明确边界（见下）。

### 5.2 出网清单（按配置的完整数据流向审计表）

| 配置场景 | 出网数据 | 出网时机 | 默认 | UI 提示要求 |
|---|---|---|---|---|
| 全本地（默认） | **无** | — | ✅ | — |
| 云端对话模型 | 用户问题 + 检索到的上下文文本 + 答案 | 每次问答 | 用户显式选择 | 配置处提示「问题与检索内容将发送至 X」 |
| 云端识图模型 | **图片内容**（文字描述回传后入库） | 入库（图片功能开启时） | 用户显式选择 | 开启图片+云端识图时提示「图片将发送至 X」 |
| 云端多模态问答增强（v0.2） | 原图 + 问题 + 上下文 | 每次问答增强 | **关闭** | 开启时提示「问答时图片将发送至 X」 |

审计要点：
- 嵌入模型无云端分支，杜绝「文本间接出网」；即使将来加云端嵌入选项，也必须默认关。
- 原始对话文本、文件全文只在本机流转；云端识图仅上传图片（描述由本地管线落库）。
- 出网实现收敛在 `ChatModel` / `VisionModel` 两个 Provider 内，便于代码审计：出网流量只可能来自这两个出口，其余模块禁止发起外呼。

### 5.3 日志与配置脱敏

- **日志**：默认不含对话全文/检索上下文/文件正文；日志级别可调，仅记录结构化事件（同步条数、耗时、失败原因）与块/文件路径；debug 级日志若输出文本，必须截断（≤ 若干字符）且不得输出密钥。
- **配置脱敏**：API Key 不入 `config.json` 明文——支持环境变量注入（`EVERYTHING_RAG_OPENAI_KEY` 等），写盘时记录占位符；启动时缺失则 UI 引导填入并仅存内存 + 掩码展示。
- 配置文件权限：写入用户数据目录，权限尽量收紧（POSIX 0600）。
- 错误信息不泄露敏感数据（不打印响应体、不打印 base64 图片内容）。

### 5.4 本地服务安全

- 绑定 `127.0.0.1` + 随机端口（拒绝外部访问）；MVP 不做远程访问，天然规避端口暴露风险。
- 本地 Web UI 需防 XSS：检索上下文与模型输出可能包含不可信文本，前端渲染必须转义（不 `innerHTML` 直插），Markdown 渲染用白名单解析器。
- 若未来开放局域网访问（v1.0 可选）：必须引入本地鉴权（访问令牌/一次性口令）+ 强制 HTTPS（自签证书提示）。
- 供应链：依赖锁定（lockfile），开源分发时做依赖漏洞扫描。

## 6. 搜索演进路径

> 既定渐进路线：向量 → 混合（BM25+向量）→ 重排（Rerank）。每个阶段以独立开关演进，MVP 只交付阶段一。

### 6.1 阶段一：纯向量（MVP）

- 检索公式：问题嵌入 → 向量库余弦 top-K（默认 K=20 候选 / 取 8 入上下文）。
- 元数据过滤：按平台 / 来源 / 时间范围过滤（Chroma where 子句），支撑「只看某平台的记忆」类诉求。
- 技术要点：
  - 问题不做切块、只整段嵌入（长问题按句拆嵌入后取平均，或先交给轻量改写，MVP 简化为整段嵌入即可）；
  - 命中块按相似度倒序 + 强制携带来源元数据组装 Prompt；
  - 「无结果」阈值：低于相似度下限则明确告知「未检索到相关内容」，不硬凑答案（避免幻觉来源标注）。
- 验收：个人语料上常见问题命中 top-8 内即为可交付（§7 定义假设指标）。

### 6.2 阶段二：混合检索（BM25 + 向量，v0.2）

- 动机：向量检索对专有名词/编号/精确短语召回弱，BM25 恰好补「字面命中」。
- 技术要点：
  - **BM25 实现路径**：若嵌入模型为 bge-m3，可直接用其**稀疏向量分支**近似字面词频检索（一条模型两用，无需额外索引）；否则用独立倒排索引（rank_bm25 内存索引，或切块清单表上的词项索引）。
  - **融合**：RRF（Reciprocal Rank Fusion，固定 k=60）合并两路排序，**不依赖分数归一化**，实现简单、鲁棒。
  - 合并后仍走元数据过滤，保证过滤语义一致。
- 开关：配置项 `search.mode = vector | hybrid`，默认 v0.2 起开 hybrid。

### 6.3 阶段三：重排序（Rerank，v1.0）

- 动机：双路候选混合后，top-K 内仍有噪声；交叉编码器可做细粒度相关性重排。
- 技术要点：
  - 重排器选型：`bge-reranker-v2-m3`（中英多语言，本地 ONNX，与嵌入模型同源）为默认候选（以官方文档为准）。
  - 流程：混合召回 top-50 → 交叉编码器逐条打分 → 取 top-8 入上下文。
  - 交叉编码器逐条打分是 O(K) 次前向，K=50 时个人机器可接受；超过则分级（先粗排截断再精排）。
- 开关：`search.mode = vector | hybrid | hybrid+rerank`，与二阶段可平滑切换。
- 说明：重排器与嵌入模型同为本地必配口径，不引入新的出网面。

## 7. 性能与非功能目标（全部为假设，需在 v0.1 验收中实测校准）

> 以下目标均为**假设值**，用于给架构选择划出合理量级边界，实际以「个人语料基准集 + 用户硬件」实测后修订。

| 维度 | 假设目标 | 备注 |
|---|---|---|
| 导入吞吐（纯文本） | 1 万字符/秒级（CPU + bge-m3 ONNX），即约 5–10 MB/分钟的 MD 文档处理能力 | 受嵌入模型推理速度约束；可对纯文本块做批量化嵌入提升 |
| 导入吞吐（含图片，本地 VLM） | 约 0.2–1 张/分钟/图（视硬件） | 识图为慢路径，异步后台补全，不阻塞文本入库 |
| 导入吞吐（含图片，云端 VLM） | 约 10–60 张/分钟 | 受 API 限流影响，以官方文档为准 |
| 同步全库扫描（快路径） | 10 万文件 < 3 秒（仅 stat） | 指纹比对快路径的硬约束 |
| 检索延迟（P95） | 单次向量检索 top-10 **< 100ms**（≤100 万块）；完整问答链路「问题→上下文就绪」**< 300ms** | 向量库本地进程内即可达成；本地嵌入问题文本约 50–200ms（CPU） |
| 流式首字延迟（TTFT） | 本地 7B（独显）：0.5–2s；云端：0.5–1.5s（假设，以官方/实测为准） | 影响「自然感」的核心指标，须在验收中实测 |
| 流式吐字速率 | 本地 7B：20–60 tok/s；云端：20–50 tok/s（假设） | 低于 10 tok/s 视为不可用，需降模型档 |
| 启动耗时 | 冷启动 < 5s（加载嵌入模型约 2–4s，可做惰性加载：首次检索才加载） | 惰性加载嵌入模型可显著改善感知启动 |
| 内存占用 | 常驻 < 2GB（8GB 机器可跑）；嵌入模型 ONNX 内存峰值另计 | 轻量备选 gte-multilingual-base 可在 4GB 内存机器兜底 |
| 磁盘增量 | 向量库约 5–10% 的语料文本量级（假设，随维度/量化而定） | 1024 维 × 4 字节/维的原始体积；可评估量化压缩（v0.2） |
| 并发 | 单用户 1–2 并发问答；入库与问答互不阻塞（异步任务池） | 个人场景无需横向扩展 |
| 可靠性 | 同步中断可重入（幂等：按块 ID upsert）；失败不污染已有数据（先处理、后提交状态） | 事务边界在「文件级」，单文件失败不影响其他 |
| 跨平台 | Windows / macOS / Linux 一致可用 | Python + 静态前端天然跨平台 |

验收口径：以上「假设」标注指标在 v0.1 阶段用「作者本人真实语料（≥100 篇 MD + ≥100 张图 + 若干导出对话）」跑出基线，写入第 8 章验收标准，超界项决定是否降档模型/切向量库。

## 8. 待拍板项汇总与推荐

| # | 待拍板项 | 本子代理推荐 | 一句话理由 |
|---|---|---|---|
| ① | 识图模型本地 vs 云端 | **本地 VLM 为默认，云端为显式可选** | 入库一次性、无延迟敏感，本地 4–8B 质量足够且保住「数据不出机」卖点；云端作可选增强并显式提示出网 |
