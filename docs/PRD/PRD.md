## 1. 执行摘要

**一句话**：把"本地文档 + 各 AI 平台对话记录"统一向量化、用自然语言问答检索的个人知识第二大脑；纯本地运行、答案永远带来源。

**可行性结论：值得做（条件成立）。**

| 判断维度 | 结论 |
|---|---|
| 需求真实性 | 高。痛点真实且随 AI 使用时长增长而加剧；"第二大脑/记忆"已被大量近邻产品验证，本产品填补"跨平台 AI 对话记忆"这一明确空白格 |
| 技术可行性 | 高。2026 年本地嵌入/向量库/LLM/识图四链成熟，数据管线是主攻难点而非技术壁垒 |
| 竞争窗口 | 存在但非独占（约 12–24 个月，假设需验证）；需快速验证 + 快速开源建社区 |
| 最大风险 | 第三方导出工具供应链依赖 + 隐私信任（均为高，已有缓解方案） |
| MVP 成功标准 | 作者自用顺手 + H1–H5 假设被验证 + 开源获早期采用（不以营收为目标） |

**关键差异化**：现有 11 个竞品在"跨平台 AI 对话记忆"维度上要么不具备、要么仅单平台/非结构化；**没有任何产品同时满足"跨平台对话记忆 + 纯本地 + 可主动检索回溯 + 开源"**。

**8 条既定关键决策**（详见第 13 章决策记录）：纯本地部署；数据接入走"第三方导出 → Markdown 归一化"（不绑 token/API/工具）；图片方案 B（识图→文字描述→文本嵌入）；增量同步手动+启动检查（指纹比对 + 对话级去重）；三模型配置（嵌入/对话必配、识图条件配）；MVP 只认 MD；诚实定位"检索找回"而非"AI 全知"；MVP 个人→开源。

**4 项待拍板**（详见 12.2）：识图模型本地 vs 云端；对话边界/去重键规范；Dashboard 形态；开源许可。

## 2. 多模态 RAG 调研结论（方向验证）

> 本节由主协调者联网实测验证，结论已写入架构决策，用于回答"图片到底怎么进向量库"。

**结论：方案 B 为检索主干，方案 A 的"存链接"升级为生成时喂图增强。** 验证过程与依据：

1. **图片进向量库的三种主流做法（均已核实存在）**：
   - **方案 B（图片→文字描述→文本嵌入）**：多模态识图模型给图写描述，描述当文本嵌入，检索纯文本。**这是内嵌图片 RAG 的主流务实做法**，图内容可被文字检索，且复用全部文本下游（混合检索/重排）。
   - **L3 多模态嵌入（CLIP 等）**：LlamaIndex 官方多模态检索即用 CLIP 图像嵌入单独建图像索引 + 文本索引并列，查询用两种编码器分别检索。真实存在但重：图像专用向量空间与文本嵌入不兼容、需双索引、对密集文字/图表 OCR 场景召回差。
   - **ColPali / ColQwen（视觉文档检索）**：用 VLM 对整页文档图像做多向量检索，免 OCR/版面解析。面向整页 PDF/扫描件，对本产品 markdown 内嵌图是"杀鸡用牛刀"。

2. **方案 A（存链接、召回时识别）的致命缺陷**：识别发生在"块已被召回之后"，而决定召回与否的向量相似度只认文字。若图内容从未进入向量空间，则任何关于图内容的提问都检索不到该块，图根本没有被识别机会。

3. **方案 A 的正确归宿 = 生成时喂图增强**：LlamaIndex "Multi-Modal RAG with GPT-4V" 模式——按文字召回块后，把原图直接喂给多模态模型"看图作答"。这必须叠加在 B 之上（因为召回仍靠文字），作为 v0.2 可选增强，不替代 B。

**架构定论**：入库时识图模型把图转文字描述 → 描述进向量库（检索主干）；原图路径存元数据（展示/溯源）；问答时默认不调识图模型，v0.2 可选"喂原图给多模态模型看图作答"。CLIP(L3) 与 ColPali 不进 MVP。

# 3. 产品背景

### 1.1 痛点拆解

#### 1.1.1 核心痛点一句话

> 重度 AI 用户同时在多个平台（ChatGPT / Kimi / DeepSeek / Claude / Gemini 等）提问，对话是碎片化、被平台锁死、不可检索的；同时本地文档与线上对话是两套互相不通的系统。用户被迫反复解释背景、反复翻找"我之前说过什么"。

#### 1.1.2 子痛点拆解

把上述一句话拆成六个可独立论证、可逐一被产品解决（或不解决）的子痛点：

**P1 跨平台对话信息碎片化（知识被平台锁死）**

- 用户为了任务、成本、地区、模型能力等原因，在多平台并行使用 AI（例如长文本写作用 A、代码用 B、中文问答用 C）。同一主题的知识被拆散在 N 个平台、N 个会话里。
- 各主流 AI 平台均未开放"历史对话全文检索/导出 API"（2024–2026 现状稳定，**需验证**），对话数据只能靠平台内手动滚动翻查或第三方工具导出，高价值语料难以聚合。
- 后果：用户在"哪台对话里说过 X"这件事上完全依赖人肉记忆。

**P2 重复解释背景（context 重复成本）**

- 每次开新对话都要重新交代：我是谁、项目背景、上次结论、偏好约束。AI 没有跨会话记忆（或只有黑盒记忆），用户被迫把上下文反复灌输。
- 每次重述都是"损失翻译"：重述会丢细节、引入偏差，且新模型并不天然知道历史结论，容易给出与之前相悖的答案。
- 成本量级：重度用户每日新开会话 5–20 个，每个会话背景重述 2–5 分钟，日损耗 10–100 分钟（**假设/需验证**）。这不是偶发摩擦，而是与"使用 AI 的时长"成正比增长的慢性税。

**P3 信息难回溯（"我之前说过什么"不可检索）**

- 想找回一段历史：只模糊记得"有次和 AI 讨论过 X"。滚动翻历史会话不可行、平台无全文搜索（或搜索很弱）、本地文档只能靠文件名/文件夹层级。
- 非结构化知识无法用精确关键词命中，而"语义级模糊检索"恰恰是 AI 的强项——但目前没有任何工具把这些对话内容放进来做语义检索。

**P4 平台记忆封闭、黑盒、不可主动检索**

- ChatGPT Memory、Claude 记忆等内建记忆是"被动记忆"：模型在生成时自动想起什么，由黑盒决定；用户不可主动"搜索记忆库"、不可按来源回溯、不可编辑精确条目（部分可删除但不透明）。
- 记忆不可控：记了不该记的（隐私风险）、该记的没记（失效），用户无感知、无导出、无自托管。
- 关键区别：**被动记忆 ≠ 主动检索**。用户需要的是像搜索引擎一样"主动翻查自己的知识"，而不是祈祷模型记得。

**P5 本地文档与线上对话两套系统无统一入口**

- 知识工作者本地有大量文档（笔记、草稿、报告、Markdown 知识库），线上有大量 AI 对话——两者语义相关（文档启发对话、对话修正文档），但没有统一入口可以联合检索。
- 需要一个"第二大脑"把两路数据合流，一次提问同时覆盖本地文档与历史对话，且答案能带来源。

**P6 供应商锁定 / 数据可携带性风险**

- 对话是用户在该平台沉淀的"知识资产"。平台策略变动（记忆功能调整、收费、模型替换、服务关停）会直接贬损用户的数据价值。
- 在"个人数据资产化"趋势下（见 1.2），用户对数据可携带性（data portability）的诉求会上升：**我的对话属于我，应当可导出、可带走、可跨平台统一管理**。

#### 1.1.3 为什么这是真实且持续的痛点

**真实性论证：**

- 直接来自产品作者本人的工作流观察——作者即是"多平台重度 AI 用户 + 有本地文档的知识工作者"，P1–P6 均为作者（及其同类用户）自身体验，立项即 dogfooding（自己用）。
- 近邻验证：ChatGPT Memory / Claude 记忆 / Notion AI / personal.ai / Mem / Rewind 等产品的大量真实用户与资本投入，证明"AI 记忆/个人第二大脑"是真实被验证的需求类别（见第 10 章），本产品的空白点只是其中"跨平台 + 本地 + 主动检索"的未被占据的格子。
- 可验证性：以上每个子痛点都对应一个可在 MVP 前后用种子用户访谈验证的假设（见 1.3 假设清单 H1–H3）。

**持续性论证（为什么不会自愈）：**

1. **会话积累是单向、不可逆的**：AI 使用时长仍在增长，对话数据只增不减，碎片化随时间加剧而非缓解。
2. **多平台并行是结构常态**：平台靠模型能力、定价、地区可用性竞争，用户为了利益不会只留在单一平台；这意味着"对话记忆"天然是跨平台的，单一平台无法垄断用户所有对话。
3. **平台不开放导出 API 是结构性约束**：开放历史对话 API 与平台的商业利益（留存、数据壁垒）冲突，且涉及隐私合规；短期内不会因个别厂商改变（**需验证，但方向上稳定**）。因此"第三方导出 + 归一化"路线是长期可行的现实路线。
4. **本地优先与数据主权意识在上升**：云端记忆的隐私不透明（黑盒、不可导出、数据在服务商服务器）会持续把一部分敏感用户推向本地方案。

### 1.2 市场现状与趋势

#### 1.2.1 三股趋势的交汇

本产品的市场位置由三股已经成熟的趋势交汇而成，缺一不可：

**趋势 A：个人知识管理（PKM）持续升温，但停留在"文档层"**

- Notion、Obsidian、Roam、Logseq 等工具用户基数巨大，证明"个人第二大脑"是真实、被大规模验证的需求类别。
- 但它们全部停留在"文档/笔记"层面：没有把 **AI 对话** 这种 2023 年后才大规模出现的新型知识资产纳入管理。AI 对话是人类历史上第一次大规模、日常化、连续产生的"个人思考数字记录"（数字日记），PKM 工具普遍没有接住它。

**趋势 B：RAG 技术栈从"实验室"走向"个人笔记本可跑"**

- 嵌入模型：本地可跑且质量可用（bge-m3 / BGE 系列、gte、nomic-embed、mxbai-embed-large 等；中文与多语言覆盖良好）。
- 向量库：SQLite-vec、LanceDB、Chroma、Qdrant、FAISS、Milvus Lite、pgvector 等嵌入式/本地选项丰富，无需要求部署独立服务。
- 检索工程：语义切块、混合检索（向量 + 全文）、重排（rerank）已成标准化流水线。
- 工程化验证：Dify、RAGFlow、Khoj 等证明"文档 RAG"从云端 GPU + 工程师门槛，降到了个人开发者可在消费级笔记本跑通（第 10 章可对照）。
- **结论**：做"文档 RAG"不再是技术壁垒，壁垒转移到"数据接入管线"（谁能拿到、归一化、结构化成什么数据）——这正是本产品选择的主攻方向。

**趋势 C：本地优先 AI（local-first AI）成为真实分支**

- 本地 LLM：Ollama、llama.cpp、LM Studio 一键跑 Qwen、DeepSeek、Llama、Gemma、Phi 等，Apple Silicon 统一内存与中端 RTX 即可流畅跑 7B–32B（**需验证**具体型号性能，方向性成立）。
- 本地多模态：Qwen2-VL、MiniCPM-V、Moondream、LLaVA 等识图模型本地可用，支撑本产品的"方案 B 图片→文字描述"管线（见基础 PRD 4.2、5.1）。
- 用户画像：开发者、隐私敏感者、企业数据合规个人。本地 RAG / 本地 LLM 类开源项目高 star 高下载量，社区活跃（**需验证**具体数字）。
- **结论**："数据不出机"不再是极客特立独行，而是有真实付费/选用意愿的产品卖点。

#### 1.2.2 宏观趋势：个人数据资产化

- **数据主权与可携带性意识上升**：GDPR 第 20 条（数据可携带权）、AI 训练数据与数据泄露事件的反复出现，让"我的数据应当属于我、可导出、可带走"成为越来越多用户的理性诉求。
- **AI 对话成为新型"数字日记"**：用户每天与 AI 的交互大量反映个人思考、项目进展、偏好与决策过程——这是以往任何工具（文档、笔记、社交）都没能沉淀下来的全新数据资产。
- **资产化的自然延伸**：把对话记录、笔记、创作统合为一个可检索、可回溯、可长期积累的个人知识库，是"个人数据资产化"在知识工作者场景下的具体落点。
- **与隐私冲突的张力**：云端厂商一面沉淀用户数据、一面黑盒使用（训练/记忆），反而放大了"数据自己管"的本地优先价值主张。

#### 1.2.3 为什么 2026 年是合适的时机（技术栈成熟度论证）

| 技术环节 | 2026 年的成熟度 | 对本产品的意义 |
|---|---|---|
| 本地嵌入模型 | 多语言（含中文）质量可用，消费级硬件可跑 | "只认 Markdown + 文本嵌入"的核心管线可纯本地 |
| 本地向量库 | 嵌入式选项成熟，零运维 | 数据不出机的硬约束可满足 |
| 本地 LLM | 7B–32B 个人笔记本可用 | Dashboard 问答可纯本地（可选云端更强模型） |
| 本地识图模型 | 多模态小模型质量够用 | 方案 B 图片管线可落地，隐私文案可承诺"图片不出机" |
| 第三方导出生态 | ChatGPT/Kimi/DeepSeek/Claude 等导出工具已丰富（**需验证**） | "导出导入 + Markdown 归一化"路线可落地，不依赖平台 API |
| 平台对话历史 API | 各主流平台均未开放（2024–2026 稳定，**需验证**） | 本产品不做 token 接入的方向正确，且该路线长期成立 |
| 竞争窗口 | 尚无产品占据"跨平台 AI 对话记忆 + 本地 + 主动检索 + 开源"组合位（见第 10 章） | 2026 年进入仍有空白 |

**时机的双面性（诚实的判断）**：技术栈成熟意味着"进入门槛低"——同类项目也会变多；但本产品的护城河不在技术栈而在**数据管线与组合位**（见 10.4）。因此 2026 年是"窗口期存在但不独占"的时机，需要快速验证需求并建立开源社区。

### 1.3 目标市场规模（定性）

> 原则：不编造精确数字。以下按漏斗分层给出**定性量级 + 可验证假设**。MVP 阶段不以营收为目标（见结论 10.5），市场规模用于判断"是否值得做"，不用于承诺收入。

#### 1.3.1 定性分层

| 层级 | 定义 | 定性量级 | 判断依据 |
|---|---|---|---|
| TAM（总可用市场） | 全球生成式 AI 用户 | 数亿级（**假设/需验证**） | 主流平台周活达数亿量级（方向性，需验证） |
| SAM（可服务市场） | 重度 AI 用户 ∩ 知识工作者 | 数千万量级（**假设/需验证**） | 每周多次用 AI、有本地文档习惯、会遇到重复解释背景/回溯困难的人群 |
| SOM（可获得市场） | 开源 + 隐私敏感 + 开发者用户 | 数十万～百万量级（**假设/需验证**） | 与本地 LLM/RAG 开源项目受众重叠；MVP 实际目标仅"数百～数千早期用户 + 作者自用" |

#### 1.3.2 可验证假设清单（MVP 前后必须验证，H1–H5）

- **H1**：目标画像用户每周至少 3 次因"忘了之前和 AI 说过什么 / 要重复解释背景"而浪费时间。→ 验证 P2/P3。
- **H2**：目标用户中"使用 ≥2 个 AI 平台"的比例显著高于单一平台依赖。→ 验证 P1。
- **H3**：用户愿意支付"一次性导出 + 手动同步"的操作成本，换取统一检索 + 数据不出机（本地优先接受度）。→ 验证 P5/P6 与本地叙事。
- **H4**：本地嵌入/对话模型在用户常用语言（尤其中文）上达到"可接受的检索/问答质量"。→ 验证技术可行性。
- **H5**：开源发布后能在 RAG / 本地优先社区获得早期采用者与导入器贡献者。→ 验证社区飞轮（见 10.4）。

**判断：** 若 H1–H3 在种子用户访谈中被否定，则"跨平台对话记忆"可能是伪需求/低频需求，MVP 应回到"纯本地文档第二大脑"作为保底定位（风险应对见 10.5）。

# 4. 竞品对照

### 10.1 竞品谱系与分类

把相关产品按"数据来源 + 部署形态"两个坐标分成五类，本产品的位置也就清楚了：

| 类别 | 代表 | 数据来源 | 部署形态 |
|---|---|---|---|
| A. 开源/自托管 文档 RAG | Khoj、AnythingLLM、Quivr、RAGFlow | 用户文档（本地/上传/连接器） | 本地/自托管 |
| B. 平台内建记忆 | ChatGPT Memory、Claude 记忆、Notion AI Q&A、（Gemini 记忆、Kimi 记忆） | 平台内对话 +（Notion）工作区 | 云端、黑盒 |
| C. 云端"AI 第二大脑" | personal.ai、Mem | 用户导入的对话/笔记/邮件 | 云端 SaaS |
| D. 录屏/活动记录 | Rewind、微软 Recall | 系统屏幕活动快照 | 本地（设备端） |
| E. 文档 RAG 之外的 PKM | Obsidian、Notion、Logseq（非 AI 检索焦点，略） | 笔记/文档 | 本地/云 |
| **F. 本产品（空白位）** | Everything RAG | **第三方导出的多平台 AI 对话 + 本地文档** | **纯本地** |

> 下面对标按任务要求覆盖：Khoj、AnythingLLM、Quivr、RAGFlow、ChatGPT Memory、Claude 记忆、Notion AI Q&A、personal.ai、Mem、Rewind/微软 Recall。

### 10.2 逐一深度对照

每个竞品按统一维度描述：**核心能力 / 数据接入 / 部署形态 / 是否覆盖"跨平台 AI 对话记忆" / 优势 / 与本产品的差距**。

#### 10.2.1 Khoj（类别 A）

- **核心能力**：开源 AI 第二大脑，成熟的文档 RAG（Markdown/PDF/Org/图像），多端覆盖（桌面 / Emacs / Obsidian / 网页 / 移动），支持增量同步、OCR、多模型。
- **数据接入**：读取本地文档目录；提供 Notion、GitHub 等连接器；应用内自己的对话（Khoj 的 chats）可纳入记忆。
- **部署形态**：自托管（Docker）+ 官方云端托管，开源。
- **跨平台 AI 对话记忆**：**部分**——仅覆盖"Khoj 自己产生的对话"，**不聚合 ChatGPT/Kimi/DeepSeek/Claude 等第三方平台的对话**。
- **优势**：社区大、功能全、文档 RAG 最成熟的一档、多端体验好。
- **与本产品差距**：不解决"多平台 AI 对话聚合"这一核心场景；第三方平台对话无法接入（本产品的核心差异点）。

#### 10.2.2 AnythingLLM（类别 A）

- **核心能力**：开源全栈 RAG 桌面应用/自托管，多文档类型、多向量库后端、多模型支持，有 Workspace（工作区）概念，支持本地 Agent 流程。
- **数据接入**：文档上传（本地文件）、URL 抓取、Git、应用内对话记录；连接器较广。
- **部署形态**：桌面应用（本地优先）+ Docker 自托管，开源。
- **跨平台 AI 对话记忆**：**无**——针对"你上传的文档"问答；对话记忆仅限应用内会话。
- **优势**：桌面体验好、上手快、文档/音视频/URL 支持广。
- **与本产品差距**：无"跨平台 AI 对话"数据源；URL 抓取属于本产品明确不做的范围（基础 PRD 4.2），方向不同。

#### 10.2.3 Quivr（类别 A）

- **核心能力**：开源"第二大脑"，文档 RAG，Web 界面，Brain（大脑）概念，支持团队协作。
- **数据接入**：文件上传（PDF/MD/TXT/音频等）、URL、Notion、Google Drive、Slack 等连接器。
- **部署形态**：Docker 自托管 + 官方云端（有商业化）。
- **跨平台 AI 对话记忆**：**无**。
- **优势**：功能丰富、连接器多、支持多用户。
- **与本产品差距**：同样不做第三方平台对话聚合；自托管/多用户形态偏团队，对个人"对话记忆"场景不聚焦。

#### 10.2.4 RAGFlow（类别 A）

- **核心能力**：开源企业级 RAG 引擎（InfiniFlow 出品），强在文档解析（DeepDoc：版面、表格、OCR），知识库管理 + Agent 编排。
- **数据接入**：文档导入（多格式）+ 页面抓取；面向文档/知识库，非对话。
- **部署形态**：Docker/集群自托管，面向服务器/企业部署，开源。
- **跨平台 AI 对话记忆**：**无**。
- **优势**：中文友好、企业级文档解析质量、RAG 工程化最完整的一档。
- **与本产品差距**：偏企业/重型，个人安装与运行门槛高；不覆盖对话类数据；定位是"企业 RAG 平台"而非"个人第二大脑"。

#### 10.2.5 ChatGPT Memory（类别 B）

- **核心能力**：OpenAI 官方记忆：自动记住用户偏好与事实并跨会话用于生成；Saved Memories（用户可编辑的持久记忆）；Projects 维度。
- **数据接入**：模型在对话中自动提取记忆；用户可手动增删；**不提供导出**。
- **部署形态**：云端（OpenAI 服务器）。
- **跨平台 AI 对话记忆**：**仅限 ChatGPT 单平台**——跨 ChatGPT/其他平台对话不可聚合。
- **优势**：零成本（对话自动沉淀）、生成时自动使用、品牌信任、记忆可一定程度编辑。
- **与本产品差距**：黑盒不可主动检索（不能搜索记忆库、不能按来源回溯）；单平台锁定；不可导出、不可自托管；数据在云端（隐私不透明）。

#### 10.2.6 Claude 记忆（类别 B）

- **核心能力**：Anthropic 官方记忆 / Projects 记忆：跨会话记住用户偏好；Projects 用用户上传的文档作为长上下文（相对用户可见、可组织）。
- **数据接入**：对话中自动沉淀记忆（黑盒）；Projects 文档由用户上传组织（较透明）。
- **部署形态**：云端。
- **跨平台 AI 对话记忆**：**仅限 Claude 单平台**；记忆本身不可导出、不可主动检索。
- **优势**：生成质量高、Projects 的文档上下文比纯记忆更结构化透明。
- **与本产品差距**：与 ChatGPT Memory 同类——单平台、黑盒、无导出、云端；Projects 覆盖面只限 Claude 内。

#### 10.2.7 Notion AI Q&A（类别 B）

- **核心能力**：在 Notion 笔记/知识库上的问答（AI Q&A），答案引用页面来源。
- **数据接入**：直接读取用户 Notion 工作区（页面、数据库）——用户已在 Notion 中主动整理的内容。
- **部署形态**：云端 SaaS。
- **跨平台 AI 对话记忆**：**无**——只覆盖 Notion 内内容，不含任何第三方 AI 平台对话。
- **优势**：内容治理度高（用户主动维护的结构化知识库）、来源引用清晰、与笔记工作流深度整合。
- **与本产品差距**：绑定 Notion 生态；不含对话类数据；云端 + 订阅成本；"来源引用清晰"这一点本产品必须对标（基础 PRD 4.5 强制来源标注）。

#### 10.2.8 personal.ai（类别 C）

- **核心能力**：Personal AI"数字分身"（Digital Twin）：用个人数据（对话、邮件、文档）训练一个以用户为中心、用"你"的口吻回答问题的 AI。
- **数据接入**：连接器导入对话/邮件/文档、手动上传、持续学习；提供对话 API。
- **部署形态**：云端 SaaS（有自托管选项的历史，主打托管）。
- **跨平台 AI 对话记忆**：**部分**——聚合用户导入的各类对话，但主打社交/邮件/消息类对话，且要求数据上云；叙事是"生成一个像你的分身"，而非"可回溯检索的知识库"。
- **优势**：记忆训练导向、长期画像、"数字分身"叙事有差异化。
- **与本产品差距**：云端（数据出机，与本地优先硬冲突）；闭源、订阅制、供应商锁定；生成导向（输出像你）≠ 检索导向（主动查证 + 来源回溯）。

#### 10.2.9 Mem（类别 C）

- **核心能力**：AI 笔记"第二大脑"：自动链接/组织笔记、语义搜索、AI 生成知识卡片；曾是早期 AI 笔记标杆。
- **数据接入**：笔记/文档导入 + 浏览器扩展等连接器；对话类数据弱。
- **部署形态**：云端 SaaS（早期有开源自托管版，后转向商业）。
- **跨平台 AI 对话记忆**：**无/弱**——聚焦笔记内容，不聚合 AI 平台对话。
- **优势**：语义搜索体验、自动组织理念先进。
- **与本产品差距**：云端、闭源、个人产品活性下降（转向企业销售，**需验证**）；不覆盖第三方 AI 对话；不可本地。

#### 10.2.10 Rewind / 微软 Recall（类别 D）

- **核心能力**：Rewind 为"个人可搜索活动记录"——录屏 + 本地语义处理，可搜索"之前看过什么"；微软 Recall 为 Windows 原生"屏幕时间轴快照"（Copilot+ PC，本地 NPU 处理），可搜索屏幕历史。
- **数据接入**：系统级屏幕活动连续捕获（快照/OCR/嵌入），本地处理。
- **部署形态**：设备端本地处理（Rewind 桌面端 / Recall 集成于 Windows）。
- **跨平台 AI 对话记忆**：**间接覆盖**——用户在 ChatGPT/Kimi 等页面上的内容会被屏幕记录捕获；但它是"屏幕帧记录"而非"对话结构化数据"，不识别平台、不切对话边界、不给会话元数据；对 AI 对话的记忆是"顺带覆盖"而非"专门优化"。
- **优势**：无感自动、本地处理（隐私友好）、覆盖一切屏幕活动（不止 AI 对话）。
- **与本产品差距**：全屏快照体积大、检索粒度为"截图帧"而非"对话"；索引/OCR 开销高；Recall 依赖新硬件（NPU/Copilot+ PC）；缺少"来源平台/时间/会话"的结构化元数据，无法回答"这段是哪个平台、哪次会话说的"；对文本对话的语义质量不如直接处理文本。

### 10.4 差异化分析（空白点与护城河）

#### 10.4.1 空白点（为什么没人在做）

1. **平台内建记忆没有动机跨平台**：ChatGPT Memory / Claude 记忆是平台留存工具，帮助平台锁住用户，天然不会去聚合对手平台的对话。
2. **云端第二大脑商业模型冲突**：personal.ai / Mem / Notion AI 靠订阅与数据画像盈利，做"数据不出机的本地开源版"会摧毁自身商业模型。
3. **本地文档 RAG 没有对话数据管线**：Khoj / AnythingLLM / Quivr / RAGFlow 专注文档解析，而"多平台导出 → Markdown 归一化 → 对话边界识别 → 来源元数据"是一套全新的、针对对话结构的数据管线，不属于它们的既有技术栈。
4. **屏幕记录非结构化**：Rewind / Recall 记录"屏幕"，不识别"这是哪个 AI 平台的哪段对话"，无法给出对话级检索。

→ **空白点成立：本产品是"跨平台 AI 对话记忆 × 本地优先 × 可主动检索 × 开源"组合位的第一个占据者**（截至 2026-08，**需持续监控**）。

#### 10.4.2 护城河（组合位难以被单点模仿）

1. **数据管线壁垒（最硬）**：各平台导出格式差异巨大，把"任意第三方导出 → Markdown 归一化 → 对话边界识别 → 元数据（平台/时间/会话）→ 对话级去重键"做成高质量、可扩展的适配器体系，需要持续投入打磨。文档 RAG 玩家没有动机去啃第三方平台导出的碎活；云端玩家被商业模型锁死。
2. **对话级工程积累**：对话结构理解（边界、角色、消息）进切块与去重、配合指纹增量同步，是文档 RAG 没有的独特工程资产。
3. **本地优先的信任位**：隐私叙事是长期资产且随时间增值（数据泄露事件只会更多）；云端玩家无法回头做"真本地"。
4. **开源社区飞轮**：早期用户即开发者，贡献新平台导入器 → 覆盖平台越多、用户越多、贡献者越多。导入器生态是本产品最具可放大性的杠杆。
5. **心智与先发**：抢占"跨平台 AI 对话记忆"这一心智词与开源生态位。

#### 10.4.3 诚实的局限与风险（差异化分析的另一面）

- 空白点对应的人群是"重度多平台 AI 用户 ∩ 愿意手动导出 ∩ 本地优先"，相对小众；存在**伪需求风险**（用 H1–H3 验证，见 1.3）。
- 第三方导出工具是外部依赖：平台改版或导出工具消失会中断管线 → 缓解：产品只认 Markdown、适配器可插拔、生态分散（见 10.5）。
- 平台可能未来开放对话导出/聚合（可能性低但存在）→ 缓解：本产品不绑定平台、只认 Markdown，即便平台开放 API，本产品的"本地统一检索 + 来源回溯"价值仍成立。
- 技术栈门槛低 → 竞争者（尤其文档 RAG 工具加对话导入器）可能追赶 → 缓解：快速开源、建立导入器生态，把"覆盖平台数量"做成相对护城河。

### 10.5 结论（市场可行性判断）

**综合判断：值得做（条件成立）。** 理由如下：

1. **需求真实性：高**。痛点 P1–P6 真实、持续、随 AI 使用增长而加剧；"个人第二大脑 / AI 记忆 / 本地 RAG"已被大量近邻产品验证，本产品填补的是其中"跨平台对话记忆"这一明确空白格（10.3 读表结论）。
2. **技术可行性：高**。2026 年本地嵌入/向量库/LLM/识图四链成熟（1.2.3），数据管线是主攻难点而非技术壁垒。
3. **竞争窗口：存在但非独占**。空白位成立，但进入门槛低；窗口期估计 12–24 个月（**假设/需验证**），需要快速验证需求 + 快速开源建社区，否则文档 RAG 竞品补一个"对话导入器"即可逼近。
4. **商业可行性：MVP 不以营收为目标**。MVP 成功标准 = 作者自用顺手 + H1–H5 假设被验证 + 开源获得早期采用与贡献；长期商业化（开源订阅 / 企业隐私版等）是 v1.0 之后的开放问题，不在 MVP 承诺内。
5. **风险与缓解**：
   - 伪需求/低频需求 → 用种子用户访谈验证 H1–H3，未通过则回退"纯本地文档第二大脑"保底定位；
   - 第三方导出依赖 → 只认 Markdown、适配器可插拔、社区化分摊风险；
   - 本地模型质量 → 模型配置灵活（基础 PRD 4.6），允许用户换更强/云端模型（隐私文案随之分级）。

> **一句话结论**：在"跨平台 AI 对话记忆 + 本地优先 + 主动检索 + 开源"的组合位上，2026 年尚无人占据，需求与技术栈均成熟，**值得以"聚焦 MVP + 快速验证 + 快速开源"的方式进入**；成功前提是严守范围（基础 PRD 第 6 节"明确不做"清单），把精力集中在数据管线这一真正的护城河上。

# 5. 产品定位

### 2.1 一句话定位

**个人知识第二大脑——把本地文档与各 AI 平台的对话记录统一向量化，用自然语言问答即可快速找回"我说过的、查过的一切"，纯本地运行、答案永远带来源。**

对外传达的口径（诚实版）：

> **"AI 能快速找回我的一切。"**
> —— 不是"AI 知道我的一切"。

- **"找回"** 是我们承诺的全部：检索增强（RAG）——用户提问，系统从用户自己的语料中检索并作答。这是检索、是定位，不是生成记忆。
- **"知道"** 是过度承诺：任何宣称"AI 懂你"的产品都需要长期记忆建模、用户画像与主动预测能力，这是 v1.0 之后才有雏形的东西，且与我们"纯本地 + 可回溯"的信任路线冲突。
- 一句话定位必须能对外说出口而不产生误解——"找回"二字是定位与竞品（封闭记忆、云端大脑）的分界线。

### 2.2 价值主张

**核心价值一句话：省时省力——不用再向 AI 重复解释背景，不用再翻找"我之前说过什么"。**

拆解为四个层次的用户价值：

| 层次 | 价值 | 具体表现 |
|---|---|---|
| 时间价值 | 不再重复解释背景 | 提问时无需粘贴历史上下文，直接说"那个方案"，系统能自己找回背景 |
| 认知价值 | 不再翻找历史 | 跨 ChatGPT / Kimi / DeepSeek / 本地 MD 统一检索，一次找到分散在各处的结论 |
| 信任价值 | 可回溯、可验证 | 每个答案强制带来源（哪个文件/哪段对话/哪个平台），可反查原文，纯本地运行数据不出机 |
| 资产价值 | 对话资产化 | 平台对话随时可能被封/被清理/被遗忘，导出归档后成为**可检索、可复用的个人数据资产** |

**支持证据与逻辑（供验证的设计假设）：**

1. **重复解释背景是高频摩擦。** 重度用户每个会话都要"重新对齐"项目背景、技术栈、上下文，通常需要 30–60 秒打字或复制粘贴 [假设/需验证]。按每天 10 次提问估算，仅此一项每日消耗约 5–10 分钟。
2. **人类对"翻找"的容忍度极低。** 平台对话没有全文检索或检索极弱，用户通常宁可重新问一遍，也不愿翻几十条会话 [假设/需验证]——结果是同一问题的答案被反复重新生成，而非复用已有结论。
3. **"第二大脑"的价值随语料累积而增大。** 语料 < 50 个文档时手工翻找尚可忍受；一旦达到数百文档 + 数百条对话，结构化的笔记浏览方式（目录、标签）就会失效，语义检索成为唯一出路 [假设/需验证]。这正是本产品存在的时机点。
4. **隐私是信任的分水岭。** 知识工作者的语料（商业方案、财务、健康、技术文档）越有价值，越不可能上传云端。纯本地运行把"数据安全"从一句营销话术变成可验证的架构事实（数据不出机 + 可离线运行），这是云产品（personal.ai / Mem / Rewind）无法给出的承诺。

> 定位原则：我们卖的是**"找回"的效率与确定感**，不是"AI 帮你思考"。用户把语料交给系统，系统负责原样保管、快速回取；加工（总结、预测、画像）是后续版本的加分项，不是 MVP 承诺。

### 2.3 产品边界与反边界

#### 产品是（本产品做的事）

- **一个可检索的知识仓库**：统一向量化"本地文档 + 各 AI 平台导出的对话记录"，全量可被自然语言检索。
- **一个检索增强的问答器**：用户提问 → 语义检索 → 生成答案 → **强制标注来源**（文件/对话/平台 + 时间）。
- **一个可回溯的系统**：每个答案都能沿来源回查原文，知识来源透明可验证。
- **一个纯本地的工具**：所有数据、向量库、模型调用都在本机完成，数据不出机（识图模型本地 vs 云端待拍板，见 PRD 第 9 章风险）。

#### 产品不是（明确不做 / 反边界）

| 反边界 | 说明 | 为什么不做的逻辑 |
|---|---|---|
| ❌ 不是平台记忆替代品 | 不接入、不读取、不替代 ChatGPT/Kimi 等平台自身的记忆功能 | 平台记忆是封闭黑盒，无对话历史 API；token 接入被否决，走导出导入路线。我们的承诺是"你自己可控、可检索的记忆"，而非平台级记忆 |
| ❌ 不是全知 AI | 不做主动记忆、不预测用户、不自动给出未检索到的答案、不编造"我记得你说过" | 与诚实定位冲突；全知需长期画像能力（v1.0 才有雏形），且会损害可回溯信任。**只在你问的时候检索，只答检索到的内容** |
| ❌ 不是社交/协作平台 | 不做多用户、团队共享、协作编辑、知识广场 | 目标用户是个人深度用户；协作是另一类产品（Notion/Confluence），范围蔓延 |
| ❌ 不是云同步服务 | MVP 不做多设备同步、不做云账号、不做云端存储 | 纯本地是信任分水岭；云同步引入账号/鉴权/服务端，复杂度与信任成本均不可接受 |
| ❌ 不是通用爬虫/浏览器助手 | 不抓取网页链接内容、不做浏览器插件实时记录 | 范围蔓延 + 隐私风险（见 PRD 4.2 外链仅存元数据） |
| ❌ 不是实时记录器 | MVP 不做实时文件监听、不做录屏/屏幕记录 | 实时监听是增量同步的复杂度陷阱；录屏（Rewind/Recall 路线）太重且隐私争议大 |
| ❌ 不是"AI 助手本体" | 不做会话式闲聊、不做 Agent、不做自动执行任务 | 我们只负责"检索你的记忆"，生成交给用户自配的对话模型 |

**边界判断口诀**：凡是涉及"系统主动获取、主动推断、主动记忆"的，都不做；凡是"用户喂数据、系统保管、用户来取"的，都做。系统是被动可查的仓库，不是主动的管家。

### 2.4 成功指标

#### 北极星指标（North Star）

> **周活跃检索问答次数**：用户每周在本产品上发起自然语言检索问答的次数。

- 为什么是它：它同时衡量"知识库是否足够全（有东西可问）"与"检索是否足够好（问得出）"，直接对应产品最核心的承诺——"找回"被真实使用。单纯的检索命中率是技术指标，不反映用户是否真的持续使用；单纯的安装量不反映价值兑现。
- 换算逻辑：北极星 = 语料覆盖率 × 检索可用性 × 用户习惯。三者任一为 0，北极星即 0。
- **注意**：在 v0.1 个人 MVP 阶段（用户 ≈ 作者本人）该指标主要是自我验证；它作为北极星的价值在开源后社区化阶段才真正生效。个人阶段的北极星代理指标见下方"质量指标"。

#### 分阶段指标

**阶段 A：v0.1 个人 MVP（当前）——以质量指标为主**

| 指标 | 目标（假设） | 验证方式 | 是否假设 |
|---|---|---|---|
| 导入耗时 | 1000 个 MD 文件 / ~50 万 token 语料，冷启动全量导入 < 5 分钟 | 自测基准 | 数值为假设，方法已定 |
| 嵌入吞吐 | ≥ 100 文档/分钟（本地嵌入模型） | 自测基准 | [假设/需验证] |

| 检索命中率 | 自建评测集 Top-5 命中 ≥ 80%（语义切块 + 向量检索） | 构建 30–50 条自建评测问答集 | [假设/需验证] |
| 答案准确率 | 评测集上人工判定"答案可用且引用来源正确" ≥ 80% | 同上，人工评测 | [假设/需验证] |

# 6. 目标用户与场景

### 6.1 用户画像（Persona）

> 目标用户画像的元原则：**先服务产品作者自己这一类人**——小众深度用户，不是大众。三类画像按优先级排列，Persona A 是产品"为谁而做"的锚点。

#### Persona A — 核心画像：多平台重度 AI 用户 + 有本地文档的知识工作者

- **背景**：30 岁左右的技术从业者/研究者/内容创作者。每天在 ChatGPT / Kimi / DeepSeek 等 3 个以上 AI 平台提问，日均 10–30 次交互。本机有几十到上百个 Markdown 笔记/文档/报告，多年累积。会用命令行，能装依赖、看报错、改配置。
- **痛点**：
  - 每次新会话都要重新解释项目背景、技术栈、上下文，浪费时间；
  - 想找"我上次跟 AI 讨论的某结论"却翻不到——平台历史无检索或检索极弱；
  - 同一主题的讨论碎片分散在多个平台 + 本地笔记，无法一次看清全貌；
  - 平台"记忆"功能是黑盒，不可检索、不可导出、不可控；
  - 有价值语料（商业/财务/健康/技术）不敢放进云端工具。
- **期望**：一个"问一句就找回"的统一检索层；答案带来源、可回溯；纯本地、数据绝对可控；首次配置后低维护（增量同步自动）。
- **付费/参与意愿**：**高**。愿意花一个周末搭环境、愿意接受"为数据主权付费"（一次性买断或小额订阅）、愿意在 GitHub 提 Issue/PR、愿意为开源项目贡献导入器——**这正是产品从"个人工具"走向"开源产品"的种子用户**。

#### Persona B — 次级画像：内容型知识工作者（研究者 / 分析师 / 自媒体）

- **背景**：靠写作、调研、分析吃饭的人（行业研究员、播客主、学术作者）。AI 是核心生产力工具，本地沉淀大量访谈记录、草稿、AI 辅助生成的调研材料。技术门槛中等——会用 Markdown、能按教程操作，但不热衷折腾。
- **痛点**：研究过程碎片化，写稿/出报告时要"考古"——翻旧对话、翻旧文档拼出完整的论证链；引用时记不清出处；重复向 AI 解释同一个课题的背景。
- **期望**：检索快、答案带可引用的出处、能跨对话与文档拼出上下文（v1.0 跨源融合）；隐私要求高（稿子未发布前绝不能泄露）。
- **付费/参与意愿**：**中高，但门槛敏感**。愿意为效率付费，但如果"先装 Python 环境再配置三套模型"则直接流失——**这类用户决定产品的易用性下限，是开源后"让普通人也能用"的拉动力量**。MVP 阶段不为其优化（先服务 Persona A），但验证期要留意其反馈。

#### Persona C — 次要用例画像：本地笔记党 / 数据主权原教旨主义者

- **背景**：Obsidian / Logseq / Typora 用户，本地 Markdown 笔记库已达数百篇。数据主权意识极强，拒绝任何"内容上云"的工具。与 A 的重合度高，但核心动机是**检索自己的笔记**而非"AI 对话记忆"。
- **痛点**：笔记库大了以后，目录/标签/链接式浏览失效，找不到"我半年前写的那个方案"；AI 对话内容无法和笔记放一起统一检索；对云 RAG 工具（Notion AI / 各种 SaaS）零信任。
- **期望**：作为笔记工具的**补充检索层**（而非替代品）；纯本地；简单——"给我的笔记库装一个会检索的问答层"。
- **付费/参与意愿**：**高**（数据主权是强付费动机），但**对"又多一个工具"有天然抵触**——如果无法证明比 Obsidian 自带搜索 + 内置 AI 更好，会被拒绝。这提示产品定位要强调"统一检索层"而非"新笔记应用"。

### 6.2 典型场景用户故事

> 场景按"我什么时候会用它"写成，全部源自真实工作流的复现，不编造夸张用例。目标：每个故事都能对上至少一个目标用户可立刻对照的瞬间。

**故事 1（周报 / 汇报场景）——核心场景的高频触发点**
> "我之前跟 ChatGPT 聊过一个方案，现在要写周报，直接问它。"
> 周一写周报，输入"我上周跟 ChatGPT 讨论的 K8s 迁移方案，当时得出了什么结论、有什么遗留风险？"——系统检索到上周那段对话，答案带来源标注（ChatGPT · 上周二 · 那段关于迁移的讨论），用户直接复述 + 引用，不用翻聊天记录，也不用重新问一遍。

**故事 2（问题复现 / 调试场景）**
> "这个 bug 三个月前在 Kimi 上问过解法，现在又遇到了。"
> 生产环境报同一个错，用户懒得翻三个月前的聊天窗口，直接问"之前遇到过 Postgres 连接数被打满的问题，当时的排查思路是什么？"——命中三处：两段 Kimi 对话 + 一份本地排查文档，拼出完整排查路径，直接复用。

**故事 3（决策复盘 / 上下文找回场景）**
> "AI 替我做过一次技术选型，我现在要写方案，需要当时的关键论据。"
> 需要为当前项目重写技术选型方案，问"我之前对比过 ClickHouse 和 DuckDB，结论倾向哪个、反对理由是什么？"——检索到当时的多轮对话，答案不仅给结论，还给当时考虑过的关键约束，用户不必重新思考一遍。

**故事 4（笔记检索 / 找回"我写过的东西"场景）**
> "我半年前在本地笔记里写过那个方案，不记得放哪个文件夹了。"
> 本地几百个 MD 文件，标题记不清、目录找不动，直接自然语言问"我写过的关于团队知识库冷启动的笔记里提到过哪些工具？"——语义检索跳过文件名/目录层级，直接定位内容。

**故事 5（隐私敏感 / 不能上云场景）**
> "这是个只能本地算的材料，绝不能让任何云端工具碰到。"
> 处理财务/健康/未公开的商业方案时，全程离线、纯本地检索问答；即使断网也能用（本地模型）。这个场景的用户价值不是"快"，而是"只有它能接"——是信任分水岭的直接兑现。

**故事 6（图片记忆 / 信息扩展场景，v0.2 起）**
> "这个截图里的数据，我记得讨论过，现在想找出来。"
> 用户截图过某张图表/某个方案讨论，问"我收藏过的那张用户增长曲线的截图里，关于留存拐点的结论是什么？"——图片经多模态转文字描述入库，可被文字检索；问答时还可把原图喂给识图模型"看图作答"。

### 6.3 核心场景优先级

按"先能问得出来 → 再用得久 → 再更全 → 再更强"排序，与 MVP 清单（PRD 第 6 节）一致，此处给出**为什么这个顺序**：

| 优先级 | 场景 | 为什么排在这里 |
|---|---|---|
| **P0** | 统一可检索、可回溯的问答（跨平台对话 + 本地文档，答案强制带来源） | 这是产品存在的前提与差异化根本（竞品只做文档 RAG 或封闭记忆）。没有它，其余一切无意义 |
| **P0** | 数据接入与导入体验（第三方导出 → Markdown 归一化 + 手动同步/增量） | 没有语料就没有检索。导入是漏斗第一关；增量同步决定"是否愿意长期维护"，决定了知识库是否常青。两者是 P0，因为它们是"问得出来"与"用得久"的地基 |
| **P1** | 纯本地部署 + 隐私保障（数据不出机） | 信任分水岭，一次性架构决策，属于"必须从一开始就是真的"而非"后续优化"。优先级高，但因与场景实现解耦，故标 P1 非 P0 阶段顺序 |
| **P1** | 图片转文字描述入库 | 显著扩大覆盖（截图、图表、邮件），"第二大脑"不能对图片失明。v0.2 门槛，且纯文本用户可不配识图模型（100% 不出机） |
| **P2** | 问答时喂图"看图作答"增强、混合检索 + 重排、更多文档类型 | 体验增强与质量提升，非生存功能，放 v0.2 之后 |
| **P3** | 跨源融合排序、记忆摘要/用户画像、更多平台导入器 | 这些是"更强"的差异化延伸（v1.0），但依赖 P0 的用户量与语料积累才有意义，过早做是范围蔓延 |

**排序逻辑一句话**：P0 回答"它有没有用"，P1 回答"我敢不敢用、能不能全"，P2–P3 回答"它好不好、强不强"。先证明有用与可信，再追求好与强。

### 6.4 非目标用户

明确"谁不是我们的用户"，防止在错误人群上投入：

| 非目标用户 | 为什么不服务 | 拒绝的代价（若有） |
|---|---|---|
| 只用单一 AI 平台的轻度用户 | 聊天历史少、无跨平台碎片化痛点，"第二大脑"没有足够语料值得导入；为 5 条对话配置整套流程不划算 | 无——这类用户本来就不属于本产品价值区间 |
| 不愿做数据搬家/导出的用户 | 产品价值 100% 建立在"把语料导入进来"之上；导出这一步做不到，后续价值归零 | 无——这正是小众定位的代价与选择 |
| 期待"AI 全知"、想要即开即用聊天体验的用户 | 我们明确不做主动记忆与全知 AI；这类用户会因"它不知道我上次没说的事"而失望 | 需在对外文案中持续用"找回"而非"知道"来校准预期 |
| 需要团队协作/共享知识库的用户 | 不做社交/协作/多用户（见 2.3 反边界） | 无 |
| 完全云优先、不介意隐私的用户 | 云同步/多设备/即开即用是他们的优先项，恰是我们的反边界；强推纯本地只会两败 | 无 |
| 依赖"开箱即用、零配置"的非技术用户 | 需要本地装模型、配依赖，技术门槛天然排除纯小白；MVP 阶段不为他们优化 | 这是开源后社区化阶段的长期课题（易用性下限），非当前目标 |

**非目标用户判断准则**：凡是其核心诉求落在我方反边界（云同步、协作、全知、零配置）上的，都不是目标用户——不争论，直接不做。**先服务 Persona A（产品作者同类人），再借助开源辐射 Persona B/C**，是清晰的路径而非妥协。

## 4.1 数据接入

### 功能概述

用户通过**拖拽**或**选择目录**两种方式导入 Markdown 文件。导入器是系统的唯一数据入口，承担两项核心职责：

1. **类型识别**：自动区分「对话文档」与「普通文档」。对话文档来源于第三方 AI 平台（如 ChatGPT / Kimi / DeepSeek 等）的对话导出；普通文档为本地知识类 Markdown。
2. **归一化**：将对话导出内容归一化为标准 Markdown 纯文本输入，并识别**对话边界**（user / assistant 消息轮次），为每条对话打上元数据：来源平台、时间、对话标题、角色序列。普通文档不打对话类元数据。

架构原则（继承框架决策）：产品**只认 Markdown**，不绑定任何具体工具、token、API 或浏览器抓取。多来源的价值集中在元数据上。对话边界识别采用**通用对话结构特征识别**（消息轮次标记、角色标签等）+ 可插拔的格式适配器机制（开源后社区可扩展），而非逐平台写死。

对外链 URL：仅将 URL 与链接文本存入元数据，**不发起任何网络请求抓取链接内容**。

导入全流程提供**反馈与错误处理**：实时进度、成功/失败/跳过统计、可读失败原因、失败项重试入口。

**非目标（MVP）**：不支持 PDF / DOCX / 结构化数据；不支持通过 token 或浏览器抓取对话；不做实时监听（见 4.5）。

### 用户故事

1. 作为重度 AI 用户，我希望把 ChatGPT / Kimi / DeepSeek 等平台导出的对话文件直接拖进应用，以便不用手动整理就能在统一知识库里检索。
2. 作为用户，我希望按目录一次导入多份文件，以便批量建立知识库而不用逐个操作。
3. 作为用户，我希望导入时看到进度和结果，以便知道哪些文件成功、哪些失败及失败原因。
4. 作为用户，我希望系统能自动判断一份文件是"对话"还是"普通文档"，以便对话能带上平台/时间信息、文档按文档处理。
5. 作为用户，我希望导入器不要求我提供任何平台账号或 token，以便我的数据来源完全由我自己掌控。
6. 作为用户，我希望文档里的外链只是被记录，以便系统不会去抓取网页内容、也不因此引入额外风险。

### 关键验收标准

1. WHEN 用户将一个或多个 `.md` 文件拖拽到导入区 THEN 系统立即开始解析并显示实时进度。
2. WHEN 用户选择"选择目录"导入一个文件夹 THEN 系统递归扫描该目录下（含子目录）所有 `.md` 文件；对不可读文件或非 MD 文件给出跳过说明，不中断整体导入。
3. IF 文件内容呈现对话结构特征（存在连续的多轮消息标记、角色标签等）THEN 系统将其识别为「对话文档」并解析消息边界（user / assistant / system / tool 等角色轮次）。
4. IF 文件不呈现对话结构特征 THEN 系统将其识别为「普通文档」，不解析对话边界、不设置平台/对话类元数据。
5. WHEN 对话文档解析成功 THEN 系统保存以下元数据：来源平台、时间（导出时间或对话开始时间，取可用者）、对话标题、消息角色序列。
6. IF 对话文档的来源平台无法自动识别（文件名/目录名/格式特征均无法推断）THEN 系统按「未知平台」处理，并在导入完成后允许用户手动补充来源平台元数据。
7. WHEN 文档中出现 Markdown 外链（URL）THEN 系统仅将 URL 与链接文本存入该块的元数据，不发起任何网络请求。
8. WHEN 导入过程中部分文件失败（编码不支持、格式损坏等）THEN 系统继续处理其余文件，并在完成报告中列出每个失败项及可读原因（如"文件编码无法识别"）。
9. WHEN 导入完成 THEN 系统展示成功 / 失败 / 跳过数量统计，并提供「重试失败项」入口（仅对失败项重跑管线）。
10. WHEN 用户重复导入已存在的文件 THEN 系统按 4.5 的去重键规则处理：不产生重复块，并在反馈中提示"已存在，跳过"。
11. WHEN 用户导入不支持的文件类型（如 `.pdf`、`.docx`）THEN 系统明确提示"当前版本仅支持 Markdown 文本"，并继续处理批次内其他受支持的文件。
12. IF 导入批次中某一文件的读取编码非 UTF-8 但可自动检测 THEN 系统按检测结果读取并标注编码来源；若检测失败则将该文件标记为失败项（遵循第 8 条）。

## 4.2 文档处理管线（文本）

### 功能概述

对导入的 Markdown 执行「解析 → 语义切块 → 元数据保留」三步，产出供向量化的**块**。核心约束（继承框架决策）：**按语义结构切块（标题 / 段落），明确不用固定窗口切分**。

- **MD 解析**：将 Markdown 解析为结构化文档树，正确识别标题、段落、列表、表格、代码块、图片引用、引用块等元素。
- **语义切块**：以标题层级为一级边界（每个标题及其下内容构成块），以段落（空行分隔）为最小单元；代码块整体成块；超过最大长度阈值的语义块按段落/句子拆分并继承标题路径。不按固定字符窗口硬切。
- **上下文保留**：每个块携带**标题路径**（如「项目笔记 > 架构决策 > 技术选型」）作为上下文元数据。
- **元数据保留**：来源文件路径、来源平台（对话）、时间（对话）、角色（对话）、标题路径。
- **对话文档**：每条消息（或其内的语义段）作为带角色的块处理。

切块结果直接决定 4.5 增量同步"局部修改只更新局部块（防边界漂移）"的可行性：由于块边界由语义结构决定而非固定位置，局部编辑后各块边界保持稳定，只有被修改的块需要重新嵌入。

**非目标（MVP）**：不做 PDF / 结构化数据的解析；不做跨源融合重排（见 4.6 范围）。

### 用户故事

1. 作为用户，我希望长文档被按主题切开，以便问答时只检索相关内容，而不是把整篇塞给模型。
2. 作为用户，我希望检索结果能保留文档层级上下文，以便答案能指到具体章节、我也能理解上下文。
3. 作为用户，我希望代码块不被拆散，以便检索到整段代码而非碎块。
4. 作为用户，我希望我改一个段落只影响那一段，以便增量同步既快又不会让附近内容的检索边界漂移。

### 关键验收标准

1. WHEN 系统处理一个 Markdown 文档 THEN 先将 MD 解析为结构化文档树（标题、段落、列表、表格、代码块、图片引用等元素均被正确识别）。
2. IF 文档包含多级标题（H1~H6）THEN 切块以标题为语义边界：每个标题及其下内容构成一个独立块，子标题内容优先归属最近一级父标题。
3. WHEN 文档存在无标题的长段落 THEN 系统以段落（空行分隔）为最小切分单元生成块，不按固定字符窗口硬切。
4. IF 单个语义块的内容超过系统设定的最大长度阈值（常量，默认约 2000 字符）THEN 系统在该块内进一步按段落 / 句子拆分为子块，子块继承相同的标题路径上下文。
5. WHEN 系统生成每个文本块 THEN 保存块元数据：来源文件路径、标题路径（如「项目笔记 > 架构决策 > 技术选型」）、块内序号。
6. WHEN 对话文档进入管线 THEN 每条消息（或其内语义段）作为带角色的块处理，块元数据额外包含：来源平台、消息角色、对话时间。
7. IF 文档中存在代码块 THEN 系统将整个代码块作为独立语义块处理，不拆散代码内容。
8. IF 文档中存在图片引用（`![...](路径)`）THEN 系统保留该引用，并将图片交由图片处理管线（4.3）；文本块中保留图片引用的占位/链接信息。
9. IF 文档损坏或无法解析为有效 Markdown THEN 系统跳过该文档并在导入报告中标注原因，不中断整体管线（与 4.1 失败处理衔接）。
10. WHEN 同一文档被再次处理（增量更新场景，见 4.5）THEN 系统尽量复用未被修改的块的向量与元数据，仅对内容变化的块重新切分与嵌入。

## 4.3 图片处理（方案 B）

### 功能概述

对文档中的图片引用执行「多模态识图 → 文字描述 → 文本嵌入」，即**方案 B**（检索主干）。关键决策（继承框架决策）：

- **方案 B 为检索主干**：图片经多模态识图模型转为文字描述，描述作为文本被嵌入进向量库，使图片内容可被文字检索。
- **原图路径进元数据**：原图路径（绝对路径或相对知识库根目录路径）存入图片块的元数据，用于展示与溯源。
- **识图功能是开关**：默认可关闭。关闭后图片仅作为文本元数据占位，不产生向量块、不调用识图模型。
- **批量与失败处理**：批量处理并发受控、进度可见、失败重试与降级（单图失败不阻塞整批）。
- **可选增强（v0.2+）**：「问答时把相关原图喂给多模态模型看图作答」是叠加增强，**不替代方案 B**；且仅当用户开启该增强开关时，问答流程才调用识图模型。

管线流程约束（继承框架决策）：识图**只在入库时发生一次**；默认问答流程**不调用识图模型**。

**性能/成本优化**：同一图片在多个文档中被引用时，识图描述只计算一次（按图片内容 / 路径去重），避免重复计算成本。

**非目标（MVP）**：不做 L3 多模态图像向量（CLIP）；不做图片生成类任务。

### 用户故事

1. 作为用户，我希望图片里的内容也能被搜到，以便我问"那天的架构图里写了什么"时能命中。
2. 作为用户，我希望通过开关控制是否启用识图，以便在不愿图片出网或想省资源时仅索引文本。
3. 作为用户，我希望看到图片处理进度和失败清单，以便知道哪些图没进库、为什么。
4. 作为用户，我希望一张图在多处被引用时只处理一次，以便导入不会因重复识图而变慢变贵。
5. 作为用户，我希望问答时默认不调用识图模型，以便纯文本流程完全可控、可预测。

### 关键验收标准

1. IF 识图功能开关为开启 THEN 管线中发现图片引用时调用配置的识图模型生成文字描述。
2. IF 识图功能开关为关闭 THEN 系统跳过识图，图片引用仅以元数据形式保留（不产生向量块），且所在文本块不因缺图而失败。
3. WHEN 识图模型成功返回描述 THEN 系统将描述文本走文本嵌入流程（与 4.2 产出块一致），并把描述与图片引用关联保存在同一图片块中。
4. WHEN 系统处理图片 THEN 原图路径（绝对路径或相对知识库根目录的路径）存入该图片块的元数据。
5. IF 识图失败（网络错误、模型拒绝、图片损坏等）THEN 系统自动重试设定次数（默认 2 次）；重试仍失败则将该图标记为失败并继续处理后续图片，不阻塞整体任务。
6. WHEN 批量图片处理进行中 THEN 系统显示进度（已处理 / 总数、成功 / 失败数），并在完成后提供「仅重试失败图片」入口。
7. IF 图片文件缺失或无法解码 THEN 系统将该图标记为不可读并跳过，在报告中标明原因，不中断批次。
8. WHEN 同一图片在多个文档中被引用 THEN 识图描述只计算一次（按图片内容 / 路径去重），各引用位置保留独立的元数据链接。
9. WHEN 用户启用「看图作答」增强且检索命中原图 THEN 系统可在答案展示时调用识图模型看图辅助作答；该增强仅作用于展示环节。
10. IF 用户未启用「看图作答」增强 THEN 问答流程完全不调用识图模型（与"入库时只发生一次、问答时不调用识图模型"一致）。

## 4.4 向量化与向量库

### 功能概述

将 4.2 的文本块与 4.3 的图片描述块**统一走同一嵌入模型**生成向量，写入**本地向量库**。核心约束（继承框架决策）：

- 文本与图片描述统一嵌入，检索时**同一模型**对问题做嵌入，保证向量同空间可比。
- **向量库本地化**：向量、块文本、元数据、来源映射均存储于本机数据目录，不出本机。
- 支持**重跑 / 重建索引**：更换嵌入模型或向量库异常时，一键全量重建。

向量与块元数据、原始文本、来源映射（块 ID → 文件 / 对话 / 平台）原子存储，保证任一向量的来源可回溯。

**非目标（MVP）**：不做混合检索 + 重排（v0.2+）、不做跨源融合排序（v1.0+）。

### 用户故事

1. 作为用户，我希望文本和图片描述用同一套向量，以便统一检索、无差别命中。
2. 作为用户，我希望向量和原始内容都保存在我本机，以便数据不出本机。
3. 作为用户，我希望在更换嵌入模型或向量库异常后能重建索引，以便恢复可检索状态。

### 关键验收标准

1. WHEN 文本块或图片描述块通过管线 THEN 系统调用配置的嵌入模型生成向量，并将「向量 + 块文本 + 块元数据 + 来源映射」原子写入本地向量库。
2. IF 嵌入调用失败 THEN 系统记录失败块，不中断批量任务，并在完成后允许针对失败块重试。
3. WHEN 问答检索时 THEN 用户问题经与库内块相同的嵌入模型生成查询向量（保证同空间可比）。
4. IF 用户更换嵌入模型 THEN 系统提示需重建索引（不同模型向量空间不兼容），并提供一键重建入口。
5. WHEN 用户触发「重建索引」THEN 系统全量重新向量化知识库；重建期间旧索引保持可读，或给出明确的不可用提示（二选一，实现期定）。
6. WHEN 向量库写入成功 THEN 系统持久化块 ID 与来源映射，确保任一向量的来源可回溯到具体文件 / 对话 / 平台。
7. IF 向量库本地存储目录空间不足 THEN 系统给出可读告警并阻止写入，避免静默失败。
8. WHEN 系统启动时检测到向量库与数据目录不一致（如缺少索引或元数据文件）THEN 系统提示用户执行同步（4.5）或重建索引（本条），不静默降级。

## 4.5 增量同步

### 功能概述

让知识库与本地源文件保持一致的增量更新机制。核心约束（继承框架决策）：

- **触发方式**：手动「同步」按钮 + 启动时自动检查；**不做实时文件监听（MVP）**。
- **指纹比对**：扫描所有已知文件，未变化跳过（毫秒级），变化才重新处理，删除则移除。
- **对话级去重**：去重键 = **来源平台 + 对话内容（规范化后）**，不是文件 hash——防止用户手动编辑导出文件（文件名、导出时间戳变化等）导致 hash 失效而重复入库。
- **防边界漂移**：局部修改只更新局部块。得益于 4.2 的语义切块，块边界由语义结构决定而非固定位置，单处编辑只影响对应块。

**指纹（fingerprint）定义**：文件级指纹 = 内容哈希 + 已知元数据（用于快速判断"是否变化"）；对话去重键 = 平台 + 规范化后的对话内容（用于判断"是否同源对话"）。两者职责不同、独立使用：指纹判断变更，去重键判断同源。

### 用户故事

1. 作为用户，我希望修改了文档或新增导出对话后点一下「同步」，以便知识库跟得上我的更新，又不用重复处理所有文件。
2. 作为用户，我希望启动应用时它会自动检查一遍，以便我不必记得每次手动同步。
3. 作为用户，我希望改一行只更新那一块，以便增量同步快且不会让附近内容的检索结果边界漂移。
4. 作为用户，我希望删掉源文件后知识库也移除对应内容，以便不留"幽灵数据"。
5. 作为用户，我希望同一段对话换了个文件名重新导出，不会被当成两份，以便知识库不重复不膨胀。

### 关键验收标准

1. WHEN 应用启动 THEN 系统自动触发一次增量同步检查（后台执行，不阻塞用户操作），并在 UI 提示同步状态与结果。
2. WHEN 用户点击「同步」按钮 THEN 系统立即执行增量同步并展示进度与结果（新增 / 更新 / 删除 / 跳过计数）。
3. WHEN 同步扫描到某个已知文件且其指纹（内容哈希 + 已知元数据）未变化 THEN 系统跳过该文件的重新处理，单文件跳过耗时保持在毫秒级。
4. WHEN 已知文件的指纹发生变化 THEN 系统仅对该文件重新走文档处理管线，不处理库中其他文件。
5. WHEN 已知文件的指纹变化属于局部编辑（仅某一段被修改）THEN 基于语义切块，仅重新嵌入受影响的块，其余块复用旧向量与元数据（防边界漂移）。
6. IF 某文件曾被导入但同步时已不存在（被删除 / 移出导入目录）THEN 系统移除该文件对应的所有向量、块与元数据记录，库中不残留孤儿数据。
7. WHEN 同步导入对话文档 THEN 去重键按「来源平台 + 对话内容（规范化后）」计算，而非文件哈希。
8. IF 同一对话以不同文件名 / 不同导出格式重复出现 THEN 规范化后去重键相同，系统判定为同一对话，不产生重复块；若内容有增量变化则按更新处理。
9. WHEN 对话被用户手动编辑（如清理冗余消息、调整排版）THEN 规范化去重键不受文件元数据变化影响，仍能识别为同一对话并按增量更新处理。
10. WHEN 两个不同来源（不同平台）存在相似对话 THEN 因去重键包含平台维度，系统不将其合并去重，各自独立入库。
11. IF 同步过程中某文件处理失败 THEN 系统在同步报告中单独列出失败项并允许重试，不影响其他文件的同步结果。
12. WHEN 同步完成 THEN 系统展示本次同步汇总，并给出与上次同步的差异摘要（新增 X / 更新 Y / 删除 Z）。
13. IF 已知文件的路径发生变化（被移动后重新导入）THEN 系统按「原路径记录移除 + 新路径记录新增」处理，并在报告中提示该情况，避免路径漂移造成静默重复。

## 4.6 问答 Dashboard

### 功能概述

面向自然语言问答的检索增强生成（RAG）界面，是用户与知识库交互的主入口。核心约束（继承框架决策）：

- **检索增强生成**：问题嵌入 → 本地向量检索 → 取 top-k 相关块 → 组装上下文 → 对话模型生成答案。
- **答案强制标注来源**：每个答案必须标注来源（哪个文件 / 哪段对话 / 哪个平台），支持点击跳转原文核验。
- **流式输出**：答案逐字流式返回，UI 持续渲染增量。
- **多轮对话**：支持基于历史上下文的追问。
- **无结果 / 低置信处理**：检索结果不足或相关度低于阈值时，明确告知"未检索到足够相关内容"，不编造看似确定实则无依据的答案。

**检索策略范围（MVP）**：仅向量检索。混合检索 + 重排为 v0.2、跨源融合排序为 v1.0，均不在本期。

### 用户故事

1. 作为用户，我希望用自然语言问"我上次关于迁移数据库说了什么"，以便不用翻聊天记录就能找回记忆。
2. 作为用户，我希望每个答案都标注来源，以便点过去核验并信任答案。
3. 作为用户，我希望答案像聊天一样流式出来，以便等待不焦虑、可提前判断方向。
4. 作为用户，我希望在问不到时知道"为什么没答上"，以便决定是否补数据，而不是被模型瞎编骗到。
5. 作为用户，我希望支持多轮追问，以便在一条脉络上深入而不是每次重新起头。

### 关键验收标准

1. WHEN 用户在 Dashboard 输入问题并提交 THEN 系统将问题经嵌入模型向量化后，在本地向量库检索 top-k 相关块（k 为可配置常量，默认 5）。
2. WHEN 生成答案 THEN 系统以流式方式逐字返回内容，UI 持续渲染增量（首字延迟与稳定输出速率满足非功能指标，见第 8 章）。
3. WHEN 生成答案 THEN 答案中每个事实性论断均附带来源标注：来源文件路径 / 对话标题 / 来源平台。
4. WHEN 用户点击答案中的来源标注 THEN 系统跳转展示对应原文块及上下文（含原图引用时展示缩略图或图片路径）。
5. IF 检索到的 top-k 块相关度低于系统设定的置信阈值 THEN 系统明确告知「未检索到足够相关的知识」，并附上最相关片段供用户判断，不生成看似确定实则无依据的答案。
6. WHEN 知识库为空或检索结果为空 THEN 系统提示用户先导入 / 同步数据，不执行生成。
7. WHEN 用户发起多轮对话 THEN 系统将历史轮次的问答摘要或相关上下文带入检索与生成，支持追问（如"那迁移后出了什么问题"）。
8. IF 对话历史超出上下文长度限制 THEN 系统仅保留相关历史或最近 N 轮（N 可配置），保证生成不超限，并提示用户。
9. WHEN 答案生成过程中模型或服务异常 THEN 系统保留已流出的部分，提示错误并允许重试，不静默截断。
10. IF 用户未启用「看图作答」增强 THEN 问答过程中不调用识图模型，图片相关命中仅以文字描述参与检索（与 4.3 约束一致）。

## 4.7 模型配置

### 功能概述

管理三模型分工与相关开关。核心约束（继承框架决策）：

- **三模型分工**：嵌入模型（必配）、对话模型（必配）、识图模型（条件性配置——仅开启图片功能时才需要）。
- **配置向导**：首次使用分步引导，让不熟悉配置的用户也能完成。
- **功能开关联动**：识图模型 = 功能开关。不开图片功能就不用配识图模型，保证「纯文本用户数据 100% 不出机」。
- **本地 / 云端切换位**：每个模型提供 provider 切换（本地运行 vs 云端 API），并在切换处展示对应隐私影响（详见 4.8）。

### 用户故事

1. 作为用户，我希望只配嵌入 + 对话就能用起来，以便最快上手、不被迫为用不上的功能付费或冒隐私风险。
2. 作为纯文本用户，我希望不配识图模型也能完整使用，以便我的数据 100% 不出机。
3. 作为用户，我希望按向导一步步配置，以便不熟悉模型配置也能完成。
4. 作为用户，我希望每个模型都能在本地与云端之间切换，以便我按隐私 / 性能 / 成本权衡。

### 关键验收标准

1. WHEN 首次启动配置向导 THEN 系统分步引导：① 数据接入 → ② 嵌入模型 → ③ 对话模型 → ④（可选）识图模型 → ⑤ 完成预览。
2. WHEN 用户未配置嵌入模型或对话模型 THEN 系统阻塞问答与同步入库的核心流程，并给出明确的「去配置」引导。
3. IF 用户未开启图片功能 THEN 系统不要求配置识图模型，配置向导跳过该步，纯文本流程可完整闭环。
4. WHEN 用户开启图片功能 THEN 系统提示需配置识图模型；未配置时阻塞图片入库，并在相关入口显示缺失提示。
5. WHEN 用户开启图片功能后又关闭 THEN 系统不再要求识图模型；已入库的图片描述块保留，后续图片不再调用识图（降级为元数据，见 4.3）。
6. WHEN 配置每个模型时 THEN 系统提供本地 / 云端 provider 切换位，并展示所选 provider 的隐私影响（本地不出网；云端需外发对应数据）。
7. IF 用户选择云端 provider 且该模型涉及图片处理 THEN 系统显著提示图片将离开本机，需用户显式确认后方可继续。
8. WHEN 用户保存模型配置 THEN 系统校验配置可达性（如嵌入模型可正常调用）；失败则给出可读错误并阻止保存无效配置。
9. WHEN 用户修改模型配置 THEN 系统提示该项变更的连带影响：嵌入模型变更需重建索引（4.4），对话 / 识图模型变更不影响既有向量。
10. IF 系统启动时检测到配置不完整（如对话模型缺失）THEN 系统引导用户进入配置向导补齐，不进入不可用的半配置状态。

## 4.8 隐私与安全

### 功能概述

保障「数据不出本机」的核心承诺，覆盖数据流控制、知识库管理、日志与提示四方面：

- **纯本地**：所有数据处理（解析、切块、嵌入、检索、生成）与存储（源文件索引、向量库、元数据、缓存）均在本地完成。唯一的例外是用户显式将模型配置为云端 provider 的场景。
- **知识库导出 / 删除**：支持一键导出备份、一键删除全部派生数据（含向量、元数据、缓存、日志相关内容），删除前二次确认。
- **日志脱敏**：日志不记录对话正文、文件路径、文件名等敏感信息，仅保留脱敏的操作事件、耗时、错误类型与错误码。
- **隐私影响提示**：识图模型本地 / 云端选择直接影响"图片是否出网"，必须在配置处显著提示并需显式确认（见 4.7 第 7 条）。

**待拍板衔接**：基础框架第 9 章列出的「识图模型本地 vs 云端」作为开放问题，本节将提示机制定为必做，具体默认值与默认 provider 由第 9 章决议后回填。

### 用户故事

1. 作为用户，我希望确认我的数据从没离开过我的电脑，以便放心导入私密对话。
2. 作为用户，我希望一键删除知识库（含向量与缓存），以便不再需要时彻底清除、不留残余。
3. 作为用户，我希望一键导出知识库，以便备份或迁移到其他设备。
4. 作为用户，我希望在选云端识图模型前被明确提醒，以便我知情决定图片是否出网。

### 关键验收标准

1. WHEN 系统运行 THEN 所有数据处理、嵌入、检索、生成均在本地完成，知识库文件与向量库仅存储于本机数据目录。
2. IF 用户全程使用本地模型 / 本地嵌入 THEN 系统可保证文本与图片数据 100% 不出机。
3. IF 用户将任一模型配置为云端 provider THEN 系统在该场景执行前（尤其是图片入库、问答调用时）展示隐私提示，明确该操作会将相应数据发送至所选服务商。
4. WHEN 用户执行「删除知识库」THEN 系统清除源文件索引、向量库、元数据、缓存与日志中的相关内容，并二次确认后执行。
5. WHEN 用户执行「导出知识库」THEN 系统生成可移植的导出包（原始文档、元数据、向量 / 索引备份），供备份或迁移。
6. WHEN 系统写日志 THEN 日志中不得包含：对话正文内容、源文件路径、文件名、文档摘要等敏感信息；仅保留脱敏的操作事件、耗时、错误类型与错误码。
7. IF 错误信息需记录上下文用于排障 THEN 系统仅记录非敏感的结构信息（块数、文件类型、错误码），并提供一键清除日志的入口。
8. WHEN 系统展示隐私 / 安全相关设置 THEN 提供直观的「数据流向」视图：本地数据路径、各模型配置（本地 / 云端）、是否有数据外发，便于用户一眼确认。
9. IF 知识库数据目录权限异常或被外部访问 THEN 系统在启动时检测并提示，避免数据被意外读写。
10. WHEN 应用首次启动 THEN 系统向用户展示隐私承诺说明（数据本地化原则、例外场景、删除能力），供用户知情使用。

# 8. 技术架构与技术选型

## 1. 总体架构

### 1.1 架构原则

| 原则 | 含义 | 落地约束 |
|---|---|---|
| 本地优先 | 核心链路（切块/嵌入/向量库/检索）不依赖任何外部服务 | 嵌入模型必为本地模型；向量库为嵌入式进程内库 |
| 纯文本不出机（默认） | 文本数据默认永不离开本机；出网仅在用户显式配置云端模型时发生 | 见 §5 出网清单 |
| 入库一次、检索多次 | 入库阶段是唯一的计算重活（切块/识图/嵌入）；问答阶段只做检索+生成 | 识图与嵌入结果全部落盘缓存 |
| 可插拔 | 对话模型、识图模型、向量库、嵌入模型均以接口抽象，可替换 | 见 §3 各选型的 Repository/Provider 模式 |
| 简单优先 | MVP 用最简单的架构换取可迭代速度，复杂的重排/混合检索延后 | 见 §6 搜索演进路径 |

### 1.2 模块划分（对齐 PRD 5.2）

```
┌──────────────────────── 应用层 ────────────────────────┐
│  Dashboard(Web UI)   │  模型配置管理   │  增量同步调度     │
└──────────────┬───────────────────────────────┬─────────┘
               │ HTTP/SSE                       │ 启动+手动触发
┌──────────────▼───────────────────────────────▼─────────┐
│                     后端服务层 (FastAPI)                  │
│  数据接入层  文档处理管线   检索层    问答生成(流式)         │
│  (MD读取)   (解析/切块/识图) (向量检索)  (LLM+来源标注)      │
└──────────────┬──────────────┬──────────────┬────────────┘
        │             │             │            │
┌───────▼────┐ ┌───────▼────┐ ┌─────▼─────┐ ┌───▼─────────┐
│ 指纹/去重表 │ │ 嵌入模型引擎 │ │ 向量库适配层 │ │ 对话模型适配层 │
│  (SQLite)  │ │ (本地 ONNX) │ │ (Chroma)   │ │ (OpenAI兼容) │
└────────────┘ └────────────┘ └───────────┘ └─────────────┘
```

核心设计：**所有外部能力（向量库/嵌入/对话/识图）都通过薄适配层（Provider 接口）访问**，MVP 只实现默认 Provider，切换成本被隔离在单点，支撑后续开源阶段的社区可插拔适配器。

### 1.3 数据流

**入库（Ingestion）**：

```
本地目录/导入文件(MD)
   │ ① 扫描 + 指纹比对（未变跳过 / 新增处理 / 删除移除）
   ▼
数据接入层 → Markdown 归一化（标题层级/代码块/对话块/图片引用/元数据头）
   │ ② 按语义结构切块（标题锚点优先，见 §4.3）
   ▼
文档处理管线
   ├─ 纯文本块 ──────────────► 嵌入(本地) ──► 向量库 upsert（带元数据）
   ├─ 图片 ──► 识图模型(本地/可选云端)
   │             │ 文字描述 + 原图路径(元数据)
   │             ▼
   │          描述作为文本块 ──► 嵌入(本地) ──► 向量库 upsert
   └─ 对话导出 ──► 对话级去重键校验(§4.2) ──► 按消息/会话切块 ──► 嵌入
   │                                                      │
   ▼                                                      ▼
指纹/去重状态表(SQLite) 更新                       完成，可检索
```

**问答（Q&A / Generation）**：

```
用户问题
   │ ① 问题文本 → 嵌入(本地，同一模型，保证同向量空间)
   ▼
检索层：向量 top-K（可选 元数据过滤：平台/来源/时间）  →(v0.2) 混合BM25 →(v1.0) Rerank
   │ ② 命中块 + 来源元数据 + 命中图片路径
   ▼
问答生成：组装 Prompt（含检索上下文 + 强制来源标注指令）→ 对话模型
   │ ③ 流式输出（SSE，见 §3.4）
   ▼
Dashboard：流式渲染答案 + 来源卡片（文件/对话/平台/图片缩略图）
   │
   └─(可选增强, v0.2) 命中图片时，把原图 + 问题喂给多模态模型"看图作答"
```

### 1.4 运行形态与数据落盘

- 单进程运行：FastAPI 后端 + 同源静态前端，默认绑定 `127.0.0.1:<随机端口>`。
- 落盘数据（全部位于用户数据目录，如 `~/.everything-rag/`）：
  - 向量库（Chroma 持久化目录）
  - 状态库 `state.db`（SQLite：指纹表、去重键表、切块清单、任务日志）
  - 配置 `config.json`（模型配置、密钥占位引用，见 §5.3）
  - 导入日志（脱敏）
- 不拷贝、不移动用户的原始 MD 文件：原始文件就地引用，路径存入元数据（符合「原图路径存元数据用于展示」的既定决策）。

## 2. 多模态 RAG 管线落地（方案 B）

### 2.1 识图模型选型：本地 vs 云端（待拍板① → 本子代理推荐）

**推荐：本地 VLM 为默认，云端 OpenAI 兼容 VLM 为可选项。**

理由：

1. **与产品核心卖点一致**：产品边界是「数据不出本机」。识图发生在入库阶段（一次性、可异步、无延迟敏感），本地 4–8B 级别 VLM 生成的文字描述对检索召回而言质量足够——检索要的是「能搜到」，不是「描述完美」。
2. **本地硬件门槛可控**：Qwen2-VL-7B / MiniCPM-V-8B 级别模型需要约 8GB 显存（或 Apple Silicon 16GB 统一内存、或量化后 8GB 内存）。无该硬件的用户走「可选云端」或「关闭图片功能」，三种路径都在产品内闭环，不强迫所有人配 GPU。
3. **云端质量更高但引入出网**：GPT-4o / Claude / 通义千问 VL 级别云端 VLM 描述准确率明显更高（尤其图表、表格、长截图）。但它要求图片出网，且产生调用成本。→ 作为显式开关的可选项，不破坏默认的隐私承诺。
4. **MVP 决策简化**：识图模型与对话模型统一走「OpenAI 兼容」接口抽象——本地跑 Ollama/llama.cpp 暴露的就是 OpenAI 兼容端点，云端也是。一条 Provider 代码同时服务「本地 Ollama」和「云端 API」，切换只是改配置，不会因此分叉两套代码。

**落地建议（型号方向，以官方文档为准）**：
- 本地默认：`Qwen2-VL-7B`（Apache-2.0，中文识图强）或 `MiniCPM-V-8B`（体积/显存占用友好），通过 Ollama / llama.cpp(GGUF) 以 OpenAI 兼容模式暴露。
- 云端可选：任何 OpenAI 兼容 VLM 端点（如 GPT-4o、Claude、通义千问 VL），配置项为 base_url + model + key。
- 质量兜底：描述 Prompt 固定模板化——「画面主体 + 场景/物体/人物 + 图中文字(OCR) + 图表数据 + 与周边上下文的关系」，保证跨模型描述格式稳定、可检索。
- 性能兜底：识图在入库管线中是慢路径，MVP 做**异步批量**处理（先入库文本块，图片描述后台补全后 upsert），避免一张慢图阻塞整个导入。

### 2.2 入库管线技术实现

```
图片引用(MD内 ![](path) 或 图片文件夹)
  → 图片解码（PIL/opencv 校验、EXIF 方向修正、过大降采样到 VLM 输入上限）
  → 识图模型 → 结构化文字描述（模板化 Prompt）
  → 描述文本 → 与文本同一嵌入模型 → 向量
  → 向量库 upsert，元数据：
       type=image_description
       source_file / source_platform / created_time（继承所在文档/对话的元数据）
       image_path（原图绝对路径，仅用于展示）
       block_id（稳定锚点，用于局部更新，见 §4.3）
  → 命中时前端据 image_path 渲染原图缩略图 / 大图
```

要点：
- **描述与文本共用同一嵌入空间**：这是方案 B 的本质优势——图内容可被纯文本问题直接检索，无需第二套向量空间。
- **继承上下文元数据**：图片描述块的平台/来源/时间继承自其所在文档或对话，保证来源标注一致。
- **原图只存路径**：不复制图片文件进产品目录，降低存储膨胀与隐私面。

### 2.3 可选增强：问答时喂原图（v0.2，不替代方案 B）

技术实现：

```
检索命中 image_description 块（或命中其所在文档且问题疑似涉及图）
  → 取元数据中 image_path
  → 将原图 + 用户问题 + 检索到的文本上下文 组装进多模态模型 Prompt
  → 多模态模型"看图作答"，结果同样流式输出 + 标注来源
```

要点：
- 复用与识图同一套「多模态模型 Provider」，不新增模型家族。
- 出网语义必须清晰：若该多模态模型是云端，则**问答时图片会出网**——UI 需在「问答增强」开启处显式提示，且默认关闭。
- 是否喂图需要判定策略：MVP 简单规则 = 命中的 top-K 块中有 `type=image_description` 且用户问题与图片描述块相关（可先用粗召回命中直接触发）；更智能的「何时该看图」判定留待 v1.0。

### 2.4 为何不用 CLIP（L3）与 ColPali 作为 MVP 主线

| 方案 | 问题 | 结论 |
|---|---|---|
| **CLIP 图像向量（L3）** | ① 图像向量位于 **CLIP 自己的向量空间**，与文本嵌入（bge/gte）空间不兼容——要么用 CLIP 文本编码器单独做一路检索（两套空间、两套索引、排序无法统一），要么做跨模态投影（重、需训练数据）；② CLIP 对**密集文字、图表、OCR 场景召回差**，恰好是本产品（对话截图、文档配图）的主体；③ 增加一个 1–2GB 级模型 + 双向量库复杂度。收益与成本严重不成比例。 | MVP 不用；文本嵌入空间已经能检索到「文字描述」，v1.0 前无场景补强需求 |
| **ColPali（整页视觉文档检索）** | ① 设计目标是 **PDF/文档页面级**视觉检索，本产品 MVP 明确不做 PDF；② 需要 ColPali VLM 做整页向量化，**单页多向量**、存储与内存开销显著；③ 与方案 B（MD 文本为主 + 少数图片）重叠度低。 | 本产品即使 v1.0 做 PDF，也应优先评估「PDF→文本+版面识别→方案 B」而非直接上 ColPali；ColPali 仅作为远期 PDF 场景的备选调研项 |
| **方案 B（VLM 描述）** | 主流务实做法，图内容变文字后可被任意文本检索复用全部下游（混合检索/重排），原图路径保证展示闭环。 | **MVP 主线，已定** |

结论：CLIP / ColPali 均不进入 MVP 路线图；文档中保留为「远期 PDF 场景」调研项即可。

## 3. 技术选型对比

### 3.1 语言与生态（待拍板③ → 本子代理推荐：Python）

| 维度 | Python | TypeScript |
|---|---|---|
| RAG/ML 生态 | **最全**：sentence-transformers、fastembed(ONNX)、chromadb/lancedb、transformers、unstructured、rank_bm25、bge/rerank 全部 Python 一等公民 | 生态在追赶，但嵌入/切块/重排等库往往只是 Python 库的 JS 移植或包装，功能与维护滞后 |
| 本地模型推理 | **强**：ONNX Runtime / llama.cpp 绑定 / Ollama(OpenAI兼容) 均可直接调用 | 需依赖 Ollama/外部进程，或较弱的 onnxruntime-node 体验 |
| 桌面打包 | 弱（pyinstaller 等可用但体验一般） | **强**（Tauri/Electron 原生友好） |
| 后端服务 | FastAPI 生态成熟，SSE 流式一行实现 | Node/Deno 也可以，但需要自己拼 RAG 栈 |

**推荐：Python（核心管线全用 Python），前端用 Web 静态资源承载。**
- 理由：本产品的技术含量 80% 集中在「切块→嵌入→向量库→检索→重排」这条 RAG 链路上，Python 是这条链路生态最完整、迭代最快的语言；打包诉求靠「本地 Web 服务」形态化解（见 §3.5），因此 TypeScript 的桌面打包优势在 MVP 阶段不构成决策权重。
- 关键框架：FastAPI（API + SSE 流式）、pydantic（配置校验）、sentence-transformers / fastembed（本地嵌入）、Pillow（图片解码）。
- 并发：入库管线用 asyncio + 线程池（嵌入/识图为 CPU/GPU 密集，进程内线程池即可，MVP 单用户无需多进程）。
- 备选：若未来开源阶段强推「无 Python 环境的桌面分发」，可在 v1.0 评估「核心 RAG 用 Python 独立 CLI/服务 + Tauri 壳调用」的混合形态，而非整体迁移语言。

### 3.2 向量数据库（本地优先）

| 方案 | 形态 | 增量更新 | 元数据过滤 | 嵌入进程 | MVP 评价 |
|---|---|---|---|---|---|
| **Chroma** | 进程内嵌入，持久化到本地目录 | 按 ID upsert/delete，支持 | 支持（含来源/平台/时间过滤） | ✅ 原生 | **推荐**：API 最简，个人规模（<100 万块）性能足够，Python 生态最顺 |
| LanceDB | 进程内嵌入式（Lance 列存） | 按 ID upsert/delete，支持 | 支持 | ✅ 原生 | 备选：单文件、可处理更大数据，开源分发更干净；API 表达力略弱 |
| SQLite-vec | 进程内，单文件 | 支持（但需自管索引重建策略） | 支持（走 SQL） | ⚠️ 需自接 | 备选：极端可嵌入（单文件分发），但 HNSW 索引与增量维护需自研，MVP 不划算 |
| Qdrant（本地模式） | **独立进程**（本地也需跑 server） | 支持 | 强 | ❌ 需单独进程 | 备选/远期：性能与过滤最强，但「多一个进程」违背 MVP 的简单优先与分发便利 |

**推荐：Chroma 为 MVP 默认；抽象 `VectorStore` 接口（Repository 模式）隔离实现，开源阶段再评估 LanceDB/Qdrant。**
- 理由：本产品量级是「个人知识库」（预估 1 万–100 万切块），Chroma 的进程内 API、按 ID upsert/delete、元数据过滤正好覆盖全部 MVP 需求（来源标注需要元数据过滤；增量同步需要按 ID 增删）。SQLite-vec 的「单文件」优势要在 v1.0 做开源分发时才有意义，届时通过接口切换即可，不阻塞 MVP。
- 注意：所有对向量库的写操作必须走统一仓储接口，禁止在业务层直接拼 SQL/查询，保证切换成本可控。
- 距离度量：用余弦距离（bge/gte 均按归一化向量使用）。

### 3.3 嵌入模型（本地必配）

| 候选 | 多语言 | 维度 | 体积/资源 | 特点 |
|---|---|---|---|---|
| **bge-m3**（推荐默认） | 强（中英为主 100+ 语言） | 1024 | ~2GB 权重（可 ONNX 量化） | 长文本 8192、多向量（稠密+稀疏+ColBERT）；稀疏向量可复用做 BM25 混合检索（§6.2），一条模型两用 |
| **gte-multilingual-base** | 强 | 768 | ~1GB | 轻量备选，显存/内存紧张机器更友好 |
| bge-small-zh-v1.5 | 中文为主 | 512 | ~100MB | 极轻量，但英文/混合语料召回弱，仅兜底 |

- **推荐：本地 bge-m3（默认），gte-multilingual-base 为轻量备选，运行层用 ONNX Runtime（sentence-transformers 或 fastembed）以降低依赖与启动开销。**
- 云端 API（如 OpenAI text-embedding-3）不作为默认：嵌入发生在入库与每次提问两个环节，云端嵌入会让「文本不出机」的承诺破功。仅作为隐私要求较低用户的显式可选配置。
- 关键硬约束：**问答时的问题嵌入必须与入库用同一模型**（同向量空间），故嵌入模型是「必配且全局唯一」的单一配置项。
- 中文/英文混合场景：bge-m3 与 gte-multilingual 均原生覆盖，无需分词预处理。

### 3.4 对话模型与流式输出

**对话模型：可插拔，默认本地、支持云端（OpenAI 兼容统一接口）。**

- 默认：本地推理（Ollama / llama.cpp 暴露 OpenAI 兼容端点），MVP 推荐 Qwen2.5-7B-Instruct 级别（以官方文档为准），个人 PC 无独显时退化到更小量化档。
- 可选：任何 OpenAI 兼容云端 API（DeepSeek / 通义 / Kimi / OpenAI 等），base_url + model + key 三项配置即可。
- 与识图模型共用同一 `ChatModel` Provider 抽象：本地与云端只是不同 base_url。这让「纯本地」与「云端」两种用户都只维护一条代码路径。
- 隐私语义（见 §5 出网清单）：云端对话模型意味着「问题 + 检索到的上下文」出网，UI 必须在模型配置处显式提示。

**流式输出：SSE（Server-Sent Events），不用 WebSocket。**

| 方案 | 方向 | 复杂度 | 适用 | 结论 |
|---|---|---|---|---|
| **SSE** | 单向 服务器→客户端 | 低：FastAPI `StreamingResponse` + 前端 `EventSource` 即用 | LLM 流式输出天然单向，正好契合 | **推荐**：MVP 用 SSE |
| WebSocket | 双向 | 高：需协议协商、心跳、断线重连、反向代理适配 | 需要客户端中途改请求/推送时才需要 | 不用；MVP 无此诉求 |

- 理由：LLM 流式是纯下行数据流，SSE 用标准 HTTP、可自动重连、在 FastAPI 与浏览器端都是一行级实现；WebSocket 为双向带来的复杂度在 MVP 完全用不上。
- 演进：流式出口做一层 `StreamOutput` 抽象（目前实现 SSE），未来若需「取消生成」「服务端主动推送状态」再叠加 WebSocket 通道，不推翻现有接口。
- 取消机制（可选 MVP 内）：SSE 连接断开即停止生成，天然满足「用户关闭页面即取消」。

### 3.5 部署/打包形态（待拍板② → 本子代理推荐：本地 Web 服务）与开源许可

| 形态 | 体验 | 复杂度 | MVP 评价 |
|---|---|---|---|
| **本地 Web 服务**（推荐） | 启动后端 + 浏览器打开 `127.0.0.1:port`，无需安装壳 | **最低**：一套 Python 后端 + 静态前端 | **MVP 用这个**：跨平台、零原生工具链、迭代最快 |
| Tauri（桌面壳） | 原生窗口，托盘/开机自启 | 中：需 Rust 工具链，但前端可复用 Web 版 | 开源阶段（v1.0 后）可选：把 Web 前端套一层轻壳 |
| Electron | 原生窗口 | 中高：包体大（~100MB+）、内存占用高 | 备选：生态成熟但重，非首选 |
| Docker（服务形态） | 容器化部署 | 中：适合未来「家庭服务器/多用户」 | v1.0 后考虑：个人 MVP 上 Docker 是负资产（用户要装 Docker） |

**推荐：MVP = 本地 Web 服务（FastAPI 后端 + 同源静态前端，浏览器访问）。**
- 理由：① 最符合「个人工具」定位，零安装摩擦；② Python 后端天然在此形态最优（无需引入 Rust/Node 编译链）；③ 前端是纯静态资源，未来 Tauri/Electron 直接复用，打包演进不被锁死；④ 避免 Electron 的包体/内存问题。
- 前端技术：MVP 建议轻量 SPA（React 或 Vue 构建产物由 FastAPI 托管，二选一即可，不影响架构决策）；若想极致简化，纯 HTML+少量 JS 也能支撑（无构建步骤），作为 MVP 起点。
- 端口安全：绑定 `127.0.0.1` + 随机端口；不用 0.0.0.0（见 §5.4）。

**开源许可：Apache-2.0（产品代码）。**
- 理由：宽松许可利于社区 Fork 与二次分发，无传染性义务（比 GPL 友好，比 CC-BY-NC 无约束），与同类工具（如 AnythingLLM 的 MIT、RAGFlow 的 Apache-2.0）生态相容。
- **必须单列的许可风险**：产品所捆绑的「模型权重」各自有 License，且与产品代码的 Apache-2.0 无必然关联：
  - bge 系列、Qwen2-VL/2.5（Apache-2.0 或 MIT，以官方为准）——可商用可再分发；
  - 部分备选模型（如某些 Qwen-VL 早期版本为 CC-BY-NC、部分 rerank/CLIP 模型受限）——**非商用**，**严禁默认捆绑**。
  - 落地约束：模型下载与许可选择必须在「模型配置」中显式列出每个模型的许可证；凡默认推荐/内置下载的模型必须为宽松许可。此条由安全/法务评审把关。

### 3.6 选型汇总

| 决策点 | 推荐 | 备选 | 关键理由 |
|---|---|---|---|
| 语言/生态 | **Python**（FastAPI + asyncio） | TypeScript（v1.0 混合形态再评估） | RAG 生态最全，打包诉求被 Web 形态化解 |
| 向量库 | **Chroma**（进程内） | LanceDB →（远期）Qdrant | 个人规模够用、API 最简、增量/过滤齐全；接口隔离切换 |
| 嵌入模型 | **bge-m3 本地 ONNX** | gte-multilingual-base | 本地必配保隐私；稀疏向量复用做混合检索 |
| 对话模型 | **OpenAI 兼容可插拔**（默认本地） | — | 一条 Provider 覆盖本地/云端 |
| 流式 | **SSE** | WebSocket（远期叠加） | 单向流天然契合、实现最简 |
| 识图模型 | **本地 VLM（Qwen2-VL/MiniCPM-V）默认，云端可选** | — | 隐私一致、质量够用、慢路径异步化 |
| 部署形态 | **本地 Web 服务** | Tauri（v1.0 后套壳） | 零安装、迭代最快、前端可复用 |
| 开源许可 | **Apache-2.0** | MIT | 宽松、生态相容；模型权重许可须逐项审计 |
| 状态存储 | SQLite（指纹/去重/切块清单/任务日志） | — | 单文件、事务、零运维 |

## 4. 增量同步技术约束

### 4.1 指纹比对

```
state.db: files(id, path, mtime_ns, size, content_hash, last_ingested_at, status)
```

- **快路径（毫秒级扫描）**：`(mtime, size)` 未变 → 跳过。这是「启动检查 + 手动同步」不卡顿的关键，全库扫描只做 stat，不做内容读。
- **慢路径（内容级复核）**：`(mtime, size)` 变了 → 读文件算 `content_hash`（xxh64 足够，冲突概率对本量级可忽略），与库中比对：
  - 未变（仅 touch 过）→ 只更新 mtime，不重处理；
  - 变了 → 标记该文件需重新入库；
  - 库中存在但磁盘缺失 → 标记删除。
- **删除一致性**：文件删除时，依据「文件→块 ID 清单」（切块清单表）级联删除向量库中该文件全部块 + 状态表记录，避免孤儿向量。
- 异常兜底：文件读取失败（编码/损坏）→ 记录失败清单并在 UI 提示，不中断整体同步。

### 4.2 对话级去重键设计

**核心矛盾**：用户手动编辑导出文件（加笔记、改排版）会改变文件 hash，但「这段对话」内容本身没变——因此**去重键锚定对话内容，而不是文件 hash**（既定决策）。

- **去重键设计**：`dedup_key = hash(归一化(platform + conversation_id))`。
  - `platform`：来源平台（ChatGPT / Kimi / DeepSeek / 本地文档）；
  - `conversation_id`：优先用导出数据自带的会话 ID/标题；缺失时退化用 `首条消息内容归一化 + 消息条数` 组合键。
  - `归一化`：去除空白/时间戳噪音、统一换行、可选降级大小写，抵抗「仅格式变化」的误判。
- **语义**：同一对话无论出现在哪个导出文件、被编辑过多少次，只入库一次。**文件重排/合并/拆分不影响去重正确性**（键在对话级而非文件级）。
- 去重键表：`conversations(dedup_key, file_path, last_seen, status)`，同步时标记 `last_seen`，某轮同步未被任何文件引用（last_seen 过期）→ 判定对话被删除 → 级联删其块。
- 同一文件内多次出现同一对话：以第一次为准，后续引用合并（`last_seen` 刷新）。

### 4.3 语义切块与边界防漂移

**目标**：局部修改只更新局部块，邻近块边界不因编辑产生漂移、不触发全量重嵌。

- **默认策略：标题锚点分层切块**（基于 MD 结构，而非固定窗口）。
  - 以 Markdown 标题（`#`~`####`）为边界切分；单块超长时按段落再细分；
  - 对话导出以「会话/消息组」为天然边界（每则消息或按角色聚合为一到多块）；
  - **块 ID = 锚点路径（标题层级链）+ 相对序号**，如 `hash(doc)::/H1/笔记方法/H2/检索#3`。
- **防漂移机制**：
  1. 块边界绑定「锚点」而非「绝对偏移量」——绝对偏移会随行文增删而漂移，标题锚点稳定；
  2. 一个锚点区间内内容变化 → 只重嵌该锚点下的块（块 hash 变化即 upsert），其他锚点块 `block_id` 不变、不动；
  3. 锚点被删除 → 只删该锚点下块；
  4. 无标题的文档（纯笔记）：退化按段落顺序切块，块 ID 用「段落 hash 前缀 + 序号」，此时允许小概率局部漂移（该文档内），作为可接受的 MVP 折衷，并在 v0.2 评估滑动窗口重叠补偿。
- **重叠与召回**：块间保留少量重叠（如每块尾部重叠 1–2 句或按标题上下文拼接），保证跨块语义不割裂；重叠块各自有独立 block_id，不互相包含。
- **切块结果缓存**：切块清单表记录「锚点→块ID→内容 hash→嵌入向量 ID」映射，同步时先用锚点层判断哪些块需要重嵌，未变块直接跳过嵌入（成本大头在嵌入，跳过即省）。

## 5. 隐私与安全架构

### 5.1 数据本地化边界

**默认边界：用户原始文件、向量库、状态库、配置全部驻留本机磁盘；除「用户显式启用的云端模型」外，不产生任何出网流量。**

- 入库链路的三个计算节点（切块 / 嵌入 / 向量库）**全部本地**，嵌入模型为本地必配（§3.3），这是「纯文本用户数据 100% 不出机」承诺的技术基础。
- 识图与对话为可配置：默认本地；用户选择云端端点时才出网，且出网对象有明确边界（见下）。

### 5.2 出网清单（按配置的完整数据流向审计表）

| 配置场景 | 出网数据 | 出网时机 | 默认 | UI 提示要求 |
|---|---|---|---|---|
| 全本地（默认） | **无** | — | ✅ | — |
| 云端对话模型 | 用户问题 + 检索到的上下文文本 + 答案 | 每次问答 | 用户显式选择 | 配置处提示「问题与检索内容将发送至 X」 |
| 云端识图模型 | **图片内容**（文字描述回传后入库） | 入库（图片功能开启时） | 用户显式选择 | 开启图片+云端识图时提示「图片将发送至 X」 |
| 云端多模态问答增强（v0.2） | 原图 + 问题 + 上下文 | 每次问答增强 | **关闭** | 开启时提示「问答时图片将发送至 X」 |

审计要点：
- 嵌入模型无云端分支，杜绝「文本间接出网」；即使将来加云端嵌入选项，也必须默认关。
- 原始对话文本、文件全文只在本机流转；云端识图仅上传图片（描述由本地管线落库）。
- 出网实现收敛在 `ChatModel` / `VisionModel` 两个 Provider 内，便于代码审计：出网流量只可能来自这两个出口，其余模块禁止发起外呼。

### 5.3 日志与配置脱敏

- **日志**：默认不含对话全文/检索上下文/文件正文；日志级别可调，仅记录结构化事件（同步条数、耗时、失败原因）与块/文件路径；debug 级日志若输出文本，必须截断（≤ 若干字符）且不得输出密钥。
- **配置脱敏**：API Key 不入 `config.json` 明文——支持环境变量注入（`EVERYTHING_RAG_OPENAI_KEY` 等），写盘时记录占位符；启动时缺失则 UI 引导填入并仅存内存 + 掩码展示。
- 配置文件权限：写入用户数据目录，权限尽量收紧（POSIX 0600）。
- 错误信息不泄露敏感数据（不打印响应体、不打印 base64 图片内容）。

### 5.4 本地服务安全

- 绑定 `127.0.0.1` + 随机端口（拒绝外部访问）；MVP 不做远程访问，天然规避端口暴露风险。
- 本地 Web UI 需防 XSS：检索上下文与模型输出可能包含不可信文本，前端渲染必须转义（不 `innerHTML` 直插），Markdown 渲染用白名单解析器。
- 若未来开放局域网访问（v1.0 可选）：必须引入本地鉴权（访问令牌/一次性口令）+ 强制 HTTPS（自签证书提示）。
- 供应链：依赖锁定（lockfile），开源分发时做依赖漏洞扫描。

## 6. 搜索演进路径

> 既定渐进路线：向量 → 混合（BM25+向量）→ 重排（Rerank）。每个阶段以独立开关演进，MVP 只交付阶段一。

### 6.1 阶段一：纯向量（MVP）

- 检索公式：问题嵌入 → 向量库余弦 top-K（默认 K=20 候选 / 取 8 入上下文）。
- 元数据过滤：按平台 / 来源 / 时间范围过滤（Chroma where 子句），支撑「只看某平台的记忆」类诉求。
- 技术要点：
  - 问题不做切块、只整段嵌入（长问题按句拆嵌入后取平均，或先交给轻量改写，MVP 简化为整段嵌入即可）；
  - 命中块按相似度倒序 + 强制携带来源元数据组装 Prompt；
  - 「无结果」阈值：低于相似度下限则明确告知「未检索到相关内容」，不硬凑答案（避免幻觉来源标注）。
- 验收：个人语料上常见问题命中 top-8 内即为可交付（§7 定义假设指标）。

### 6.2 阶段二：混合检索（BM25 + 向量，v0.2）

- 动机：向量检索对专有名词/编号/精确短语召回弱，BM25 恰好补「字面命中」。
- 技术要点：
  - **BM25 实现路径**：若嵌入模型为 bge-m3，可直接用其**稀疏向量分支**近似字面词频检索（一条模型两用，无需额外索引）；否则用独立倒排索引（rank_bm25 内存索引，或切块清单表上的词项索引）。
  - **融合**：RRF（Reciprocal Rank Fusion，固定 k=60）合并两路排序，**不依赖分数归一化**，实现简单、鲁棒。
  - 合并后仍走元数据过滤，保证过滤语义一致。
- 开关：配置项 `search.mode = vector | hybrid`，默认 v0.2 起开 hybrid。

### 6.3 阶段三：重排序（Rerank，v1.0）

- 动机：双路候选混合后，top-K 内仍有噪声；交叉编码器可做细粒度相关性重排。
- 技术要点：
  - 重排器选型：`bge-reranker-v2-m3`（中英多语言，本地 ONNX，与嵌入模型同源）为默认候选（以官方文档为准）。
  - 流程：混合召回 top-50 → 交叉编码器逐条打分 → 取 top-8 入上下文。
  - 交叉编码器逐条打分是 O(K) 次前向，K=50 时个人机器可接受；超过则分级（先粗排截断再精排）。
- 开关：`search.mode = vector | hybrid | hybrid+rerank`，与二阶段可平滑切换。
- 说明：重排器与嵌入模型同为本地必配口径，不引入新的出网面。

## 7. 性能与非功能目标（全部为假设，需在 v0.1 验收中实测校准）

> 以下目标均为**假设值**，用于给架构选择划出合理量级边界，实际以「个人语料基准集 + 用户硬件」实测后修订。

| 维度 | 假设目标 | 备注 |
|---|---|---|
| 导入吞吐（纯文本） | 1 万字符/秒级（CPU + bge-m3 ONNX），即约 5–10 MB/分钟的 MD 文档处理能力 | 受嵌入模型推理速度约束；可对纯文本块做批量化嵌入提升 |
| 导入吞吐（含图片，本地 VLM） | 约 0.2–1 张/分钟/图（视硬件） | 识图为慢路径，异步后台补全，不阻塞文本入库 |
| 导入吞吐（含图片，云端 VLM） | 约 10–60 张/分钟 | 受 API 限流影响，以官方文档为准 |
| 同步全库扫描（快路径） | 10 万文件 < 3 秒（仅 stat） | 指纹比对快路径的硬约束 |
| 检索延迟（P95） | 单次向量检索 top-10 **< 100ms**（≤100 万块）；完整问答链路「问题→上下文就绪」**< 300ms** | 向量库本地进程内即可达成；本地嵌入问题文本约 50–200ms（CPU） |
| 流式首字延迟（TTFT） | 本地 7B（独显）：0.5–2s；云端：0.5–1.5s（假设，以官方/实测为准） | 影响「自然感」的核心指标，须在验收中实测 |
| 流式吐字速率 | 本地 7B：20–60 tok/s；云端：20–50 tok/s（假设） | 低于 10 tok/s 视为不可用，需降模型档 |
| 启动耗时 | 冷启动 < 5s（加载嵌入模型约 2–4s，可做惰性加载：首次检索才加载） | 惰性加载嵌入模型可显著改善感知启动 |
| 内存占用 | 常驻 < 2GB（8GB 机器可跑）；嵌入模型 ONNX 内存峰值另计 | 轻量备选 gte-multilingual-base 可在 4GB 内存机器兜底 |
| 磁盘增量 | 向量库约 5–10% 的语料文本量级（假设，随维度/量化而定） | 1024 维 × 4 字节/维的原始体积；可评估量化压缩（v0.2） |
| 并发 | 单用户 1–2 并发问答；入库与问答互不阻塞（异步任务池） | 个人场景无需横向扩展 |
| 可靠性 | 同步中断可重入（幂等：按块 ID upsert）；失败不污染已有数据（先处理、后提交状态） | 事务边界在「文件级」，单文件失败不影响其他 |
| 跨平台 | Windows / macOS / Linux 一致可用 | Python + 静态前端天然跨平台 |

验收口径：以上「假设」标注指标在 v0.1 阶段用「作者本人真实语料（≥100 篇 MD + ≥100 张图 + 若干导出对话）」跑出基线，写入第 8 章验收标准，超界项决定是否降档模型/切向量库。

## 6.2 MoSCoW 优先级拆解

### Must Have（缺失则不能称之为 MVP）

**M-R1：目录扫描 → 切块 → 向量化**
- 内容：选择本地知识库目录；扫描其中所有 `.md`；按语义结构（标题/段落）切块；文本块经嵌入模型向量化入库。
- 排序理由：这是整个产品的**管线主干**，没有它就没有索引、没有检索、没有问答。它是 R2/R3/R4/R5 的共同前置。作为验证「本地优先 + MD 归一化」技术假设的最小可运行切片，必须最先落地。
- 依赖：无（但要求切块模块从第一天就**稳定性优先**——语义切块锚点规则先冻结，为 R4 的增量同步打底）。

**M-R4：手动「同步」——指纹比对 → 增量更新（增/改/删）**
- 内容：提供手动同步按钮 + 启动时自动检查；对已知文件做指纹比对，未变化的毫秒级跳过，新增/修改/删除的文件只做对应增量处理；**去重键 = 平台 + 对话内容（规范化），而非文件 hash**；硬约束：局部修改只更新局部块，防止边界漂移导致整篇重做。
- 排序理由：知识库是**持续演化**的活体数据，若每次同步都全量重建，用户在文档规模变大后必然放弃使用。增量同步是「个人知识库」从玩具变成工具的分水岭，是留存相关的核心体验，必须进 MVP。
- 依赖：R1 的切块稳定性 + 指纹算法 + 去重键规范（与开放问题②联动）。

**M-R5：Dashboard 问答——检索增强 + 流式输出 + 强制来源标注**
- 内容：用户输入自然语言问题；问题嵌入 → 向量检索召回候选块；拼装上下文交给对话模型生成答案；**答案强制标注来源**（哪个文件 / 哪段对话 / 哪个平台，可点击跳转原文）；流式输出。
- 排序理由：这是产品价值的**兑现点**——用户真正付费/投入时间的动作是「问」。没有问答，前面的索引只是哑数据。强制来源标注是信任与可回溯性的承诺，与「第二大脑」定位强绑定。
- 依赖：R1（向量库 + 嵌入）、模型配置（对话模型可本地运行、支持流式）。

**M-R6：数据不出本机（贯穿性硬约束）**
- 内容：知识库文件、切块、向量库、问答上下文、日志均不出本机；纯文本路径默认零外发；所有网络行为（若有）显式可见、可配置、可关闭。
- 排序理由：这是产品定位的**存在前提**（纯本地是差异化核心），不是可裁剪的功能而是所有实现必须满足的架构约束。MVP 验收中必须包含「数据不出机验证」专项测试。
- 依赖：约束 R1-R5 的一切实现，贯穿各模块。

### Should Have（理想情况下 MVP 交付，必要时可作为 v0.1 尾期或 v0.2 开头）

**S-R2：导入器——第三方导出对话 MD**
- 内容：识别第三方平台导出文件中的对话边界（会话标题/日期/分隔符启发式），为每个对话块打**来源平台 + 时间**元数据；导入后走 R1 的 MD 归一化管线。
- 排序理由：这是「跨平台 AI 对话记忆」差异化诉求的直接载体。但 MVP 最小闭环「纯文档 RAG」也能独立成立，因此降为 Should——先保证端到端管线稳，再接入对话记忆；若时间允许，MVP 内至少支持 **1 个平台**的导出格式跑通全链路。
- 依赖：R1、元数据 schema、对话边界/去重键规范（开放问题②定稿后实现）。

**S-R3：图片——识图模型转文字描述进库**
- 内容：MD 中的图片经识图模型转为**文字描述**，描述作为文本块嵌入向量库；**原图路径存入元数据**（用于展示/回链）；问答时不调用识图模型（只发生在入库时）。
- 排序理由：图片是知识工作者语料的高价值部分，方案 B 已定、成本可控。但它依赖开放问题①（识图模型本地 vs 云端）拍板，且是**条件性配置**（不开图片功能就不用配识图模型），故作为 Should——纯文本用户不受影响，图片作为可选增强。
- 依赖：R1、识图模型 provider 适配层、本地/云端决策（开放问题①）。

### Could Have（加分项，纳入 v0.1 但允许砍）

**C-启动时自动检查同步**
- 内容：应用启动时自动做一次轻量指纹检查，发现过期则提示用户（或按配置自动同步）。
- 排序理由：已定决策「手动同步 + 启动检查」中的**启动检查**是纯增益（成本低、防遗忘），但手动按钮已能闭环，故列为 Could——实现顺序靠后，砍掉不影响 MVP 成立。
- 依赖：R4 的指纹机制。

### Won't Have（v0.1 明确不做，见 6.4 不做清单）

见第 6.4 节完整清单。此处强调：**PDF/结构化数据、实时文件监听、CLIP 图像向量、链接内容抓取、跨源融合排序、记忆摘要/用户画像、多设备同步**——均不在 v0.1。

## 6.3 依赖关系

```
M-R6 数据不出本机（贯穿性约束，约束所有模块实现）
        │
        ▼
M-R1 目录扫描 → 切块 → 向量化 ←──── 技术选型落地（向量库/嵌入模型）
   ▲    ▲    ▲
   │    │    └── S-R3 图片（识图 provider；开放问题①）
   │    │
   │    └── S-R2 导入器（对话边界/去重键规范；开放问题②）
   │
   └── M-R4 增量同步（切块稳定性 + 指纹 + 去重键）
              │
              ▼

```

- **关键路径**：R1 → R4 → R5，三者是 MVP 的脊梁；R6 全程并行约束。
- **待拍板阻塞项**：开放问题①（识图本地/云端）阻塞 S-R3；开放问题②（对话边界/去重键）阻塞 S-R2 的实现细节。两者不阻塞 M 级需求。

## 6.4 明确不做清单（YAGNI）

> 原则：每项「不做」都有明确原因与「回看时机」，避免范围蔓延；任何一项进入后续版本都必须以**用户真实需求 + 触发信号**为依据，而非「顺手做」。

| 能力 | 不做原因 | 回看时机 | 触发信号 |
|---|---|---|---|
| **PDF/结构化数据**（docx/xlsx/EPUB 等） | PDF 版面、表格、扫描件 OCR 解析复杂度高、质量参差，与「对话记忆」核心定位无关；MVP 只认 MD，让管线单一、可验证、质量可控 | v0.2 先做轻量文本格式（TXT/HTML），PDF 视调研放 v0.2 后期或 v1.0 | 用户抽样中「PDF/表格类文档」导入诉求占比显著（假设：>30%） |
| **实时文件监听** | 文件系统事件（inotify/FSEvents/ReadDirectoryChangesW）跨平台兼容坑多；引入后台常驻进程，违背「轻量、按需」的本地优先原则，扩大崩溃面；作者本人「手动 + 启动检查」已够用 | v1.0 之后，作为**可选**能力（保留手动兜底） | 「总忘同步」「文档改了就想要新结果」成为高频抱怨 |
| **CLIP 图像向量（L3 多模态嵌入）** | 方案 B（识图→文字→文本嵌入）已被调研验证为主流务实做法，图内容可被文字检索；L3 增加模型下载体积、算力、向量库多模态复杂度，收益在 MVP 不成立 | v1.0 后评估；当「图片局部内容检索/图搜图」成为真实需求且本地 L3 模型成本显著下降 | 检索到图片但「具体是图里哪个细节」无法命中 |
| **链接内容抓取** | 外链抓取 = 爬虫，引入反爬、动态渲染、版权、脏内容、无限范围膨胀；MVP 仅把 URL 存元数据展示 | 当「网页收藏」成为主要使用方式时，作为独立能力（reader 类）而非核心管线 | 用户反馈「存了链接但内容搜不到」且占比高 |
| **跨源融合排序** | 按来源/新鲜度/画像加权融合涉及大量调参与评测，MVP 阶段先用「召回 + 相似度 + 强制来源标注」闭环，让用户自行判断来源可信度 | v1.0（已列入路线图），与记忆摘要同时做（届时已有时间衰减、画像信号可融入） | MVP 用户明确表达「文档结果总排在对话结果前面，我不想要」 |
| **记忆摘要/用户画像** | 属于「长期记忆/主动召回」层，依赖稳定语料积累与评测集；MVP 先验证「被动检索」体验，主动层（遗忘/冲突消解/主动提示）语义复杂度高，会拖垮 MVP | v1.0（已列入路线图） | 「被动问答」验证通过后，出现「跨会话一致性」诉求（用户希望 AI 记得之前说过什么） |
| **多设备同步** | 与「数据不出本机」存在张力（同步=数据至少经过中间层）；引入身份、冲突合并、端到端加密等大工程 | 开源后社区可做可选插件（自建存储/网盘）；产品层 v1.0 后评估，且必须显式声明数据路径 | 用户明确需要手机/笔记本双端访问 |

## 6.5 范围边界原则

1. **只认 MD**：一切外部数据先归一化为 Markdown 纯文本；多来源价值靠**元数据**体现，不靠格式堆砌。
2. **入库时一次处理**：图片识图、解析、切块、嵌入只发生在入库/同步时；问答路径不引入额外模型调用。
3. **可裁剪**：MVP 的每一项都必须能独立验证价值；砍掉任一 Could/Should 不影响 Must 闭环。
4. **隐私为默认**：任何「可能出网」的能力都必须是显式 opt-in，纯文本默认零外发。

# 10. 版本路线图

## 7.0 路线图总览

| 版本 | 定位 | 核心命题 | 目标用户 |
|---|---|---|---|
| **v0.1 MVP** | 单机闭环验证 | 「能不能把文档+对话变成可问答的第二大脑」 | 作者本人（dogfood） |
| **v0.2** | 问答体验增强 + 类型扩展 | 「好不好用」——检索质量与多模态问答提升 | 作者 + 少量内测用户 |
| **v1.0** | 长期记忆 + 融合排序 + 平台扩展 | 「像不像第二大脑」——跨会话一致性、跨源融合、多平台覆盖 | 早期社区用户 |
| **开源** | 社区化与生态 | 「社区能不能自己长」——可插拔适配器、信任共建 | 公众开发者 |

## 7.1 v0.1（MVP）

- **目标**：跑通「文档 + 对话 → 向量库 → 问答」最小闭环，验证核心价值（不用重复向 AI 解释背景、答案可回溯、带来源标注）；以作者本人真实语料做 dogfood，收集第一批体验反馈。
- **关键特性**：见第 6 章 MoSCoW。Must：R1/R4/R5/R6；Should：R2/R3（至少 1 个平台导入器端到端）；Could：启动时自动检查同步。
- **验收点**：见 8.1「v0.1 验收」。核心红线：导入 100 个 MD 全流程正确、改一处只更新相关块、问答必带来源标注、数据不出机验证通过。
- **依赖的前置条件**：
  - 技术选型落地（语言、向量库、嵌入模型 + 对话模型可本地运行、流式输出方案）——基础 PRD 5.3，见第 8 章。
  - 开放问题①（识图本地/云端）拍板，否则 S-R3 无法定实现。
  - 开放问题②（对话边界/去重键规范）定稿，否则 S-R2 的实现细节悬空。
  - 导入器目标平台的导出格式样本（作者真实导出文件）到位。

## 7.2 v0.2（问答体验增强 + 类型扩展）

- **目标**：把「能用」升级为「好用」——检索命中率显著提升、图片可被「看图问答」、覆盖更多文档类型；建立评测集，让检索质量可量化、可回归。
- **关键特性**：
  1. **图片问答时喂图增强**：生成时把检索命中的相关**原图**喂给多模态对话模型「看图作答」；叠加在方案 B 之上（B 负责检索定位图片，喂图负责生成质量），**不替代 B**。
  2. **混合检索 + 重排**：稀疏检索（BM25）与稠密向量检索（双路召回）→ Rerank 重排模型（本地可选）→ 输出；渐进式落地，评测集驱动调参。
  3. **更多文档类型**：优先轻量文本格式（TXT / HTML / 纯文本导出），PDF 视 6.4 触发信号按需评估。
  4. **质量基建**：自建评测集（golden set，覆盖文档/对话/图片三类来源）；检索命中率、端到端正确率纳入 CI 回归。
- **验收点**：见 8.1「v0.2 验收」。核心红线：Top-5 命中率相对 v0.1 提升达阈值、喂图问答正确率提升可测、流式首 token 延迟不劣化、评测集回归通过。
- **依赖的前置条件**：
  - v0.1 稳定并已积累真实使用语料（喂图、重排评测需要真实数据）。
  - 对话模型支持多模态输入（喂图增强的前提）。
  - 混合检索/重排库选型落地（sub-agent 4 调研）。

## 7.3 v1.0（长期记忆 + 融合排序 + 平台扩展）

- **目标**：从「知识库」升级为「第二大脑」——具备跨会话的长期记忆与用户画像、跨来源融合排序、覆盖主流 AI 平台的导入器。
- **关键特性**：
  1. **记忆摘要 / 用户画像**：从导入语料提取长期摘要与用户偏好画像（存储在本机，符合「数据不出机」承诺）；支持跨会话一致性（「上次我说的那个方案」能定位到）；可在问答时注入画像作为轻量上下文增强，**保持被动检索主导，不喧宾夺主**。
  2. **跨源融合排序**：来源权重（文档/对话/图片描述）+ 时间衰减 + 画像偏好融合进排序，排序依据可解释（答案旁展示排序因子）。
  3. **更多平台导入器**：覆盖 ChatGPT / Kimi / DeepSeek / Claude 等主流平台的导出格式适配器（≥3 个端到端验证）。
  4. **管理面**：知识库统计（来源占比、语料规模）、来源可视化、重复/噪声清理工具、去重。
- **验收点**：见 8.1「v1.0 验收」。核心红线：跨会话一致性示例通过、融合排序在评测集上优于 v0.2、平台导入器 ≥3 个端到端、画像数据不出机验证。
- **依赖的前置条件**：
  - v0.2 稳定且评测集成熟（融合排序与画像的效果需要基准）。
  - 真实对话语料已积累到可支撑摘要/画像的量（假设：个人语料 > 1,000 个对话块）。
  - 时间衰减与画像算法设计（可利用 v0.2 期间积累的排序信号）。
  - 更多平台导出格式的供应链评估（见风险 9.1-R1）。

## 7.4 开源

- **目标**：代码开源建立信任（「数据不出本机」可由代码证伪/证实）、社区共建可插拔适配器生态、降低作者单人维护压力。
- **关键特性**：
  1. **打包形态落地**：本地 Web / 桌面壳（Tauri 等）/ 插件（Obsidian 等）三形态待拍板（开放问题③），至少交付一种开箱即用的安装包。
  2. **可插拔适配器规范**：导入器、嵌入模型 provider、向量库后端、对话模型 provider、识图模型 provider 的统一插件接口 + 示例适配器 + 文档。
  3. **工程质量**：CI/CD、发布流水线、自动化测试、安全审计、依赖更新机器人、行为准则与贡献指南、issue 模板。
  4. **隐私合规材料**：隐私声明与代码行为逐条对应（网络审计面板公开）。
- **验收点**：见 8.1「开源验收」。核心红线：新人 30 分钟跑通、≥1 个第三方适配器贡献、安全审计无 CRITICAL、隐私声明与代码一致。
- **依赖的前置条件**：
  - v1.0 稳定。
  - 开源许可拍板（开放问题④）。
  - 打包形态拍板（开放问题③）。
  - 作者对维护投入的心理预期与边界（见风险 9.1-R7）。

# 11. 验收与质量

## 8.1 分版本验收标准

> 格式：每版本含「功能验收」「性能指标」「隐私合规」三类。带 ★ 的为硬性验收红线。

### v0.1 验收

**功能验收**
- ★ 全流程：选择目录 → 扫描 → 切块 → 向量化 → 问答，端到端无人工介入可跑通。
- ★ 导入正确性：100 个 MD（含嵌套目录、中文/英文混合、大小写/空行异常）导入后：文件数、切块数、向量入库数逐一核对一致；无丢块、无重复块。
- ★ 对话边界识别：1 个导出文件含多段对话时能正确拆分；每块的来源平台、时间元数据正确。
- ★ 图片（启用时）：识图描述入库、原图路径在元数据中、通过描述可检索到该图。
- ★ 增量同步一致性：**改一处只更新相关块**（不整篇重做）；新增文件入库、删除文件移除、未变化文件跳过；同步前后库内总块数核验一致。
- ★ 问答：对三类问题（事实提取 / 跨文档关联 / 对话回忆）给出答案且**强制来源标注**（文件 + 段落 + 平台），点击来源可跳转原文；流式输出正常；答案为空时明确提示「未检索到相关内容」而非编造。
- 可用性：首次引导（选目录 → 配模型 → 首次同步）无需文档即可完成。

**性能指标（假设，需验证）**
| 项 | 目标 | 说明 |
|---|---|---|
| 首次导入 100 个 MD（10-50MB） | 嵌入耗时 ≤ 5-10 分钟 | 取决于设备与嵌入模型；支持后台异步 + 进度条 |
| 指纹比对跳过未变化文件 | 单文件 < 10ms；100 文件全量 < 1s | 快速路径（mtime+size）+ 内容 hash 兜底 |
| 检索（不含生成）P95 | < 1s | 本地向量库 |
| 问答首 token（本地对话模型） | < 3s | 需验证模型与硬件 |
| 常驻内存（不含本地大模型进程） | ≤ 2GB | 向量库 + 索引 |

**隐私合规**
- ★ 数据不出机验证：运行期「网络审计面板」显示**零外发**（纯文本路径）；除显式配置的模型 API 外无任何出网调用；日志无敏感内容（脱敏）。
- ★ 知识库文件、向量库、切块缓存、临时文件均落在本机指定目录；退出/清理不残留。
- 若开放问题①拍板为「识图可云端」：则纯文本路径仍为零外发，云端仅作用于用户显式开启的图片功能，且首次开启有醒目二次确认（见 9.2）。

## 8.2 非功能需求

### 性能
- **导入**：支持后台异步 + 进度反馈；长任务可中断/续跑（幂等）；对超大单文件（对话导出常有大文件）有切块/分批策略。
- **检索与生成**：检索 P95 < 1s；流式首 token 与帧率可感知流畅；对话模型与嵌入模型分离，避免问答时阻塞其他功能。

- 依赖供应链：锁定版本 + 依赖扫描 + CVE 跟踪（开源后由 CI 自动化）。

### 可用性
- 首次引导（onboarding 向导）覆盖：选目录 → 配置模型 → 首次同步 → 首个问题。

- 增量同步**幂等且原子**：中途失败/断电不损坏既有库，可重试续跑；部分成功有明确记录。

- 向量库损坏/升级：提供重建（重建索引）与备份/恢复指引。
- 模型调用失败（provider 不可用、超时）：降级提示而非静默失败；重试策略可配置。

### 可维护性（模块化 / 可插拔适配器）
- 分层模块：数据接入 / 文档处理管线（切块 + 图片描述）/ 向量化 / 向量库 / 检索层 / 问答生成 / Dashboard / 增量同步 / 模型配置管理 / 隐私安全。单一职责，每层接口稳定。
- 可插拔适配器接口（目标：v0.1 起就保持抽象，开源时正式化）：
  - 导入器适配器（平台导出格式 → 归一化 MD + 元数据）
  - 嵌入模型 provider（本地 / 云端，统一接口）
  - 对话模型 provider（支持流式与多模态可选）

- 配置驱动：模型选择、目录、开关均走配置中心，不改代码。
- 测试与文档：单元 / 集成 / E2E 三层自动化测试；关键模块（切块、同步、导入器）文档化。

### 兼容性
- 跨平台：Windows 首发（作者主环境），macOS / Linux 为发布目标（架构分层需避免平台强耦合）。

# 12. 风险与开放问题

## 9.1 风险清单与缓解

> 等级：高 / 中 / 低。每个风险给出描述与缓解；缓解措施全部落在地图内已规划能力上，不新增颠覆性范围。

### R1 第三方导出工具供应链依赖（高）
- **描述**：导入器依赖 ChatGPT / Kimi / DeepSeek 等平台的「导出」能力。平台可能随时改格式、下线导出功能、或导出格式为非官方非稳定；上游一变动 → 导入器断裂 → 用户无法增量导入既有语料，信任受损。
- **缓解**：
  1. 架构上「只认 MD」：任何上游格式先归一化为 MD + 元数据，把易变部分**隔离在单个适配器内**，改格式只动一个适配器，核心管线不受影响。
  2. 容错降级：解析失败 → 保留原文为纯文本入库，**绝不丢数据**；元数据缺失时标注「未知来源/未知时间」而非报错。
  3. 文档明确「平台导出文件是事实源」：用户保留导出文件，上游格式变更后可重新导出再同步。
  4. 平台变更监控：社区/官方论坛变更情报 + 适配器变更日志。
  5. MVP 先只支持 1 个作者真实使用的平台，验证模式后横向复制。

### R2 增量同步体验质量（中）
- **描述**：指纹比对的准确性（hash 失效）、语义切块边界漂移导致「改一处重做一大片」、用户遗忘手动同步、启动检查时机冲突，都会让同步成为负面体验。
- **缓解**：
  1. 去重键 = 平台 + 内容规范化，而非文件 hash（防手动编辑后 hash 失效）——已定决策。
  2. 指纹快速路径（mtime+size） + 内容 hash 兜底双通道。
  3. 切块锚点稳定化（标题层级锚点 + 受控重叠），边界漂移纳入回归测试。
  4. 同步前差异预览（「将新增 N / 更新 M / 删除 K」）+ 失败原子化（部分成功不损坏既有库）。
  5. 启动检查做「过期提示」而非强制阻塞；同步可后台异步。

### R3 隐私信任（高）
- **描述**：产品核心卖点是「数据不出本机」，一旦被用户怀疑（识图是否出网、日志是否泄敏、是否有隐含外发），信任崩塌不可逆。隐私文案与真实行为的任何不一致都会被放大。
- **缓解**：
  1. 网络审计面板：运行期可查看**所有**外发行为，默认零外发（可被验证的承诺）。
  2. 纯文本路径强制不出网；云端模型（若开放问题①拍板）一律 **opt-in + 首次醒目二次确认 + 配置持久化可见**。
  3. 日志脱敏、临时文件清理、退出无残留。
  4. 开源 = 代码可审，隐私声明与代码行为逐条对应（开源验收红线）。
  5. 隐私文案分场景声明数据路径（入库 / 问答 / 图片 / 配置）。

### R4 对话语料质量（噪声 / 重复 / 时间衰减）（中高）
- **描述**：AI 对话含系统消息、客套话、反复追问同一主题（大量语义重复）、错别字/复制粘贴垃圾；信息随时间过时（「现在的价格」「上个月的计划」），直接检索会给出过期答案。
- **缓解**：
  1. 导入清洗规则：系统消息/空段/超长回复剔除与截断（v0.1）。
  2. 时间元数据从一开始就规范存储（v0.1），排序阶段按时间衰减（v1.0 融合排序）。
  3. 答案旁展示来源时间，「时间敏感问题」提供过期提示设计。
  4. 语义/相似去重（v1.0 管理面清理工具）。
  5. 评测集纳入噪声样本，防止清洗规则退化。

### R5 检索质量（模糊回忆弱）（中高）
- **描述**：用户问法常模糊（「我之前说过的那个想法」），向量检索对同义改写、缩写、口语化召回弱；切块过细丢上下文、过粗噪声多；召回够但排序差，用户翻不到想要的。
- **缓解**：
  1. 混合检索 + 重排（v0.2 已规划），渐进落地。
  2. 查询改写/同义扩展（后续评估）。
  3. 块级上下文扩展（标题层级锚点 + 邻块补全）。
  4. 强制来源标注让用户自行判断与回链——MVP 阶段不追求完美排序，先保证「可找到、可溯源」。
  5. 评测集（golden set）驱动量化迭代，命中率指标进 CI。

### R6 冷启动（中）
- **描述**：新用户需先积累足够语料（导入几百份文档/对话）检索才有价值；首次导入耗时成为首个负体验；「不知道能问什么」导致使用率低。
- **缓解**：
  1. onboarding 引导：内置示例知识库 / 导入向导 / 预设目录。
  2. 后台异步导入 + 进度条 + 可中断续跑。
  3. 语料质量诊断：导入后展示来源统计、主题词云、规模概览。
  4. 基于语料生成「你可以这样问」预置问题，降低提问门槛。
  5. 文档少的用户自然降级为纯文档问答（对话导入为可选加分项），不强制。

### R7 开源项目维护成本（中）
- **描述**：单人开源：issue 洪水、依赖过时、CVE 通报压力、文档过期；用户期望（「为什么还不支持 X」）全部压向维护者，容易 burnout 或项目烂尾。
- **缓解**：
  1. 发布前明确维护边界与 SLA（README 声明实验性阶段、issue 模板、贡献指南）。
  2. CI 自动化：依赖更新机器人、依赖扫描、自动发布、CHANGELOG 纪律。
  3. 插件生态把扩展压力转移给社区；核心小而稳，扩展靠插件。
  4. 先用自用工具跑稳再开源（本文路线图即为此设计）。
  5. 分层承诺：核心模块由作者维护，适配器可由社区认领。

### R8 补充：模型与依赖供应链（中）
- **描述**：嵌入/对话/识图模型下载体积大（本地模型数个 GB）、模型许可证不一（商用限制）、依赖库许可证合规；对「纯本地」体验与开源合规构成隐性成本。
- **缓解**：默认对接已有本地推理服务（Ollama / LM Studio / llama.cpp），避免重复下载与打包模型；模型提供商选择说明许可证；依赖许可证清单开源前核查。

## 9.2 开放问题（待拍板）

> 每项给出：背景、决策影响、推荐倾向、备选。四者均为 MVP 阶段需拍板的阻塞项或后续阶段的战略项。

### 开放问题① 识图模型本地 vs 云端（图片是否出网）——影响 S-R3，影响隐私文案

- **背景**：基础 PRD 4.6/4.7 已定「识图模型为条件性配置、默认不开」，但「图片是否出网」未拍板。本地识图（如 Qwen2.5-VL / MiniCPM-V / Llama 3.2 Vision）效果好时需较大显存与模型下载，普通用户门槛高；云端识图（GPT-4o mini / 智谱 GLM-4V 等）效果好、门槛低，但图片出网，动摇「数据不出本机」的卖点。
- **决策影响**：
  - 隐私承诺措辞：本地 = 「所有数据默认不出机」；云端 = 必须改为「文本默认不出机，图片在显式开启后出网」。
  - 技术：本地方案需识图 provider 适配层 + 模型下载/硬件要求文档；云端方案需 API key 管理 + 网络审计覆盖。
  - 验收：隐私回归测试的断言范围（是否允许图片外发）。
- **推荐倾向**：**本地优先，云端作为显式 opt-in 的可选 provider**。纯文本路径 100% 不出机（不变）；识图功能默认关闭，检测到本地可用模型时自动使用本地；云端需用户在配置中显式添加 key 并二次确认。理由：最大化保护核心卖点，同时保留「图片大户」用户的可选路径，隐私文案按「默认全不出网、云端为显式例外」宣传。
- **备选**：a) 纯本地识图（更保守，但牺牲低端设备用户与图片质量）；b) 纯云端识图（体验最好，但重写隐私定位，不建议）。

### 开放问题② 对话边界 / 去重键规范——影响 S-R2 与 R4，阻塞导入器实现细节

- **背景**：第三方导出格式各异，对话边界识别（多段对话混在一个文件、日期/标题分隔符不统一）与去重键（防同一对话重复入库）依赖一套规范。基础 PRD 4.4 已定「去重键 = 平台 + 内容规范化，非文件 hash」，但「规范化」的具体规则待定。
- **决策影响**：
  - 决定切块粒度、增量同步的稳定性、元数据 schema；边界识别弱会把多段对话混成一块，来源标注错乱；去重键不规范会导致跨导出批次重复入库。
  - 决定导入器适配器是否依赖用户的「预规范文件」（作者是否要提前把导出转成推荐格式）。
- **推荐倾向**：**约定式启发式解析 + 显式元数据头兜底**。默认基于常见导出格式的启发式（会话标题/日期模式/分隔符）识别边界；去重键 =（平台，规范化对话内容哈希，时间）；提供「推荐对话导出格式」规范文档，引导工具生成规范文件，未知格式走降级（保留原文 + 未知元数据）。理由：兼容主流导出无需用户预加工，同时给高级用户一条规范化路径。
- **备选**：a) 纯约定式（只认规范格式，简单但导入门槛高）；b) 纯启发式（兼容广但误判率高，需大量规则维护）。

### 开放问题③ Dashboard 形态（本地 Web / 桌面壳 / 插件）——影响技术栈、分发、开源形态

- **背景**：基础 PRD 7 章列了三形态待定。本地 Web（内置 HTTP 服务 + 自动打开浏览器）最轻、跨平台最省事，但无系统托盘、体验偏「开发工具」；桌面壳（Tauri / Electron）体验好但打包体积大、维护重；插件（Obsidian 等）获客顺但被宿主平台的能力与更新节奏约束。
- **决策影响**：
  - 技术栈：本地 Web 决定「后端服务 + 前端页面」分层，桌面壳引入 Rust/JS 桌面框架，插件引入宿主 API 约束。
  - 分发与安装门槛、开源打包形态、Dashboard 与后端进程的进程模型。
- **推荐倾向**：**v0.1 用本地 Web**（内置 HTTP 服务，自动打开浏览器），把「后端核心 + 前端」清晰分层，Dashboard 形态只影响前端壳。理由：MVP 求快求稳，服务形态天然可复用（未来桌面壳/插件都能复用同一后端）；避免桌面框架的跨平台打包负担。开源时评估 Tauri 桌面壳作为 v1.0 后的增值形态。
- **备选**：a) 桌面壳首发（体验好、打包成本高、跨平台测试重）；b) 插件首发（获客顺、被宿主约束、依赖作者使用该宿主）。

### 开放问题④ 开源许可选择——影响社区模式、商业路线、贡献者协议

- **背景**：开源发布需确定许可证。MIT / Apache-2.0 宽松、社区友好但可被闭源套壳；GPL / AGPL 强传染、保护理念但可能吓退企业用户与部分贡献者；SSPL 等争议许可不推荐；Commons Clause / Elastic License 防套壳但社区接受度低。
- **决策影响**：
  - 决定社区参与方式（宽松许可更容易吸引第三方适配器贡献）、作者对「套壳/云化」的容忍度、未来商业增值层（托管版/企业版）的法律空间。
  - 影响贡献者协议（CLA）是否必要、第三方适配器的许可兼容。
- **推荐倾向**：**核心代码 Apache-2.0**（宽松、含专利授权、与多数生态兼容），并辅以：商标保护（禁止「Everything RAG 官方」冒用）、行为准则与贡献指南、可选的 CLA。若作者强烈反对「闭源套壳」，备选 AGPL-3.0，但需接受企业贡献意愿下降的代价。推荐主选 Apache-2.0：作为本地优先的个人工具，开源的主要目的是信任共建 + 插件生态，宽松许可更有利于生态目标。
- **备选**：a) MIT（更简，无专利条款，差异不大）；b) AGPL-3.0（强约束，适合反套壳诉求强、社区规模预期小的场景）。

# 13. 决策记录

## 13.1 既定关键决策（已拍板）

1. **纯本地部署**：数据不出本机，隐私是信任分水岭。
2. **数据接入**：第三方工具导出 → Markdown 归一化；不绑 token/API/具体工具，只认 Markdown。
3. **图片方案 B**：识图 → 文字描述 → 文本嵌入（检索主干）；原图路径存元数据；问答默认不调识图，v0.2 可选"喂图增强"。
4. **增量同步**：手动"同步"按钮 + 启动时自动检查；指纹比对（未变跳过/变化重处理/删除移除）；去重键 = 平台 + 规范化内容（非文件 hash）；语义切块防边界漂移。
5. **三模型配置**：嵌入/对话必配，识图条件性配置（功能开关联动）。
6. **MVP 只认 MD**；外链仅存元数据，不抓取链接内容。
7. **诚实定位**："检索找回我的一切"，而非"AI 知道我的一切"。
8. **MVP 个人使用 → 开源产品**。
