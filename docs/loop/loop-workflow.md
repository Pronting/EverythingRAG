# Loop 工作流规范 — Everything RAG

> 本文是项目的**循环工程规范**：如何让 Claude Code 多轮次自主推进、每轮自动验收、不污染主会话上下文。
> 适用范围：MVP 及后续里程碑的「横向任务队列」推进。

## 1. 为什么是「瘦控制器 + sub-agent」

目标：**减少人工干预**——Agent 一轮做完自动验收，验收通过自动进下一轮。

核心约束：**轮次正文永远不进主会话上下文**。多轮次最大的坑是中间产物堆进主上下文 → 被迫压缩 → 忘事。解法不是"压缩上下文"，而是让每轮的实现跑在**隔离的 sub-agent** 里，主会话只做三件事：选任务、派发、验收。

```
主会话 = 控制器（瘦：任务表 + 每轮一行摘要）
   └─ 派发 sub-agent（上下文完全独立）
        ├─ TDD：写测试(RED)→实现(GREEN)→重构
        ├─ test_gate hook 自动跑测试（验收第一段）
        └─ commit
   └─ 收「结果摘要 + commit hash」（正文不回流）
   └─ code-reviewer sub-agent 双审（验收第二段）
        └─ 通过 → 更新 loop-state.md → 下一轮
```

## 2. 三种循环与选型

| 循环类型 | 场景 | 机制 | 本项目用途 |
|---|---|---|---|
| **横向任务循环** | 一串不同任务，验收后推进 | 控制器 + sub-agent + 文件交接（本规范） | ✅ MVP 构建（默认） |
| 纵向迭代循环 | 同一个任务反复迭代到测试通过 | Stop-hook 自引用（官方 ralph-loop 插件） | 预留：单测反复失败时的收敛 |
| 定时巡检 | 按间隔重复同一条 prompt | `/loop` 或 CronCreate | 预留：看门狗 / 定时同步 |

> 选型原则：任务不同 → 横向；任务相同但没通过 → 纵向；时间驱动 → 定时。本项目 MVP 以**横向**为主。

## 3. 文件与角色

| 文件 | 角色 |
|---|---|
| `.claude/loop-state.md` | 任务队列，循环的**唯一事实来源**（状态机） |
| `.claude/commands/loop-plan.md` | 循环入口 slash 命令（控制器 prompt） |
| `project-state.md` | 阶段级状态（SessionStart 自动注入），循环收尾时更新 |
| `.claude/hooks/test_gate.py` | 验收第一段：写代码后自动跑相关测试 |
| `docs/loop/loop-workflow.md` | 本规范 |

## 4. 状态机

```
⬜ 待做 ──派发──► 🔄 进行中（进程在 sub-agent，主会话无正文）
                    │ 测试门 ✅ + 评审 ✅ ──► ✅ 通过 ──► 下一轮
                    │ 评审 CRITICAL/HIGH ──► ❌ 打回 ──重派──► 🔄（≤2 次）
                    └ 2 次仍失败 / 遇 Gate ──► ⚠️ 需人工 ──► 用户拍板后回 ⬜ 或 ✅
```

- 状态以 `.claude/loop-state.md` 为准；一个任务只有一个状态。
- 「需人工」是**暂停点**，不是失败：控制器停下汇报，用户拍板后继续。

## 5. 人工 Gate 边界（哪些必须人卡）

**可全自动**：实现明确、验收可断言、不触发外部资源的任务（扫描、解析、切块、检索、UI）。

**必须人卡**：
1. 任何**出网**动作（模型下载、云端 provider）——违反「默认零外发」，需显式 opt-in。
2. PRD 12.2 **待拍板项**的方案选择（识图本地 vs 云端、对话去重键规范、Dashboard 形态、开源许可）。
3. 涉及**设计决策**、需要用户判断方向的（如切块算法选型、对话边界定义）。
4. 用户主动叫停。

> 判断准则：**验收标准能否写成可执行断言？能 → 自动；不能 → 人卡。**
> 无人值守不等于无人负责：任何歧义即停，不猜。

## 6. 上下文卫生（防污染，强制）

1. **正文不回流**：sub-agent 只回传「结果摘要 + 测试关键行 + commit hash」。
2. **状态文件为准**：跨轮信息一律经 `.claude/loop-state.md`，不靠上下文记忆。
3. **prompt 自包含**：派发时把任务规格 + 验收标准 + 约束全量写进 prompt；sub-agent 是冷启动，不许让它"翻文件猜需求"。
4. **PreCompact 保护**：被压缩前先确认状态文件已更新。
5. **超长队列**：若一轮控制器上下文逼近上限，可拆为多个 `/loop-plan <范围>` 分片执行；状态文件保证续跑。

## 7. 验收标准书写规范

- 每条标准 = **可执行断言**：`pytest：<前置> → <断言>` 或 `Playwright：<操作> → <断言>`。
- 有数字就有阈值（如"块长 ≤ N 字""首 token <3s"），不许"正常运行"这类模糊表述。
- 失败模式要写清（"返回清晰错误而非崩溃"），避免 sub-agent 用异常糊弄过去。

## 8. 常见坑与规避

| 坑 | 规避 |
|---|---|
| sub-agent "close enough" 就交差 | 验收标准写成断言 + 双段评审，spec 评审没过不进下一任务 |
| 实现正文灌进主上下文 | 第 6 节强制规则；摘要只留一行 |
| 无人值守把方向带偏 | 设计决策任务标 Gate；歧义即停 |
| 测试门形同虚设 | 测试门跑过 + code-reviewer 双审 + 每轮必须 commit |
| 循环停不下来 | 结束条件显式化：队列清空 / 遇 Gate / 用户叫停 |

## 9. 扩展路径（后续里程碑）

- **模块并行**：任务间无依赖时，用 `isolation: worktree` 派多个 sub-agent 并行，或内置 `/batch`（5-30 隔离 worktree 各开 PR）。
- **纵向收敛**：启用官方 ralph-loop 插件（`/plugin`）处理"单测反复失败"的收敛。
- **确定性管线**：调研/评审扇出可用 Workflow 工具（pipeline/parallel/phase）。
- 这些扩展不改变第 3/4/6 节的核心模型：**状态在文件，正文在隔离环境，主会话只编排**。
