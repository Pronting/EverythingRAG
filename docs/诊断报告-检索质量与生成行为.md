# 诊断报告：检索质量差 + 生成"复读机/答不出常识" 根因分析

> 日期：2026-08-12 ｜ 环境：Windows，bge-m3 本地嵌入，deepseek-v4-flash 云端对话
> 方法：真实数据复现（向量库 777 块 / 62 文件 + 3 次真实对话调用 + chunker 全库跑分），非代码走读臆断。
> 本报告只做根因定位，不含修复实施；修复建议见 §4。

---

## 0. 三句话结论（三板斧）

1. **切块碎片化是检索质量的主根因** —— 全库 **49.6% 的块 <100 字**，最小 2 字。碎片嵌入信号弱，检索只能靠"关键词局部重叠"命中，召回的上下文是**残句**，LLM 无米下锅。
2. **检索无相关度门控** —— 无论相似度多低（0.34）都硬塞 top-5 进上下文。库外/常识问题被**垃圾上下文污染**，这就是"答不出常识"和"被无关上下文劫持"（模型去扮演 Cider 客服）的直接机制。
3. **提示词既过度约束又缺指引** —— 默认提示词"严格基于上下文、不得编造上下文之外"直接把常识问题变成拒答（已复现）；用户覆盖成裸提示词后又失去锚点，模型行为不稳定。**没有一条指令告诉模型"上下文不相关时怎么办"**。

### 1.3 真实对话生成实测（deepseek-v4-flash，当前 config）

**① 三国演义（当前裸提示词）**：检索 5 块全无关。模型思维链自己识破"上下文片段看起来无关，应基于常识回答"，才答对了《三国演义》。**纯靠模型自觉，无系统保障，且不稳定**——同一问题换默认提示词就变成拒答（见 ②）。

**② 三国演义（默认提示词 `_SYSTEM_PROMPT`）**：模型直接拒答——
> "根据提供的参考上下文，无法回答……上下文内容与《三国演义》无关，因此不能给出基于来源的答案。"

**这就是你遇到的"普通问题他也不知道"**。默认提示词"严格基于给定上下文作答，不要编造上下文之外的内容"把任何库外问题变成拒答。

**③ 自我介绍"你是我的私人知识助手"**（最致命）：检索到 sim 0.60 的 `chatgpt_客服需求.md`（内容是"You act as a professional customer service representative"），模型思维链写道：
> "参考上下文是Cider客服提示，要求以客服Amy身份回答……应该按照客服角色介绍自己"

**结果：模型无视用户"私人知识助手"的明确指令，扮演 Cider 客服 Amy。** 无关上下文（sim 仅 0.60）直接劫持了模型行为——这就是"回复完全根据召回的 chunk 来回答"的实锤。

### 1.4 chunker 全库跑分（复现碎片机制）

真实文档 `线上死循环导致MQ消息堆积问题排查.md`（2068 字，**无顶层标题**）：
> 22 个块，**19 个 <100 字**，中位数 **17 字**。碎片样例：
> `#5 "发现大量MQ消息堆积"`(10字)、`#13 "然后查看线程的堆栈"`(9字)、`#18 "则死循环了"`(5字)、`#17 "total = 0"`(9字)、`#8 "<font style=\"background-color:#f5f6f7;\">consume</font> 方法，里面有个线程池去执行任务"`(HTML 未清洗)

全库统计（documents/ 下 788 个有效文档）：**49.6% 块 <100 字，676/788 文档含碎片** —— 系统性问题，非个例。

## 2. 根因清单（按影响排序）

### 🔴 根因 1：切块碎片化 —— 无下限、无合并（检索质量主因）

**证据**：§1.4 全库 49.6% <100 字。

**代码定位**：
- `backend/app/ingestion/chunker.py:114-130` `_emit_headingless_region`：无标题文档**每个段落独立成块，从不合并**（"无标题文档按段落为最小单元切块"）。这是碎片的第一来源。
- `chunker.py:100-111` `_emit_heading_region`：有标题文档按标题区间合并成一块（≤2000 字），但**单段内容很小的标题区间就直接产出极短块**；且**没有"相邻短块合并"或"最小块长"约束**。
- `chunker.py:44-47` `max_chunk_chars=2000` 只设了上限，**没有 min_chunk_chars**。

**机制**：9-17 字的块嵌入后几乎无语义信号 → 检索退化为"词面重叠"匹配（所以 MQ 靠 0.92 的词面命中，语义查询全崩）→ 召回的是残句 → LLM 无法据此作答，只能拒答或复读残句关键词。

### 🔴 根因 2：检索无相关度门控 / 无置信阈值

**证据**：§1.2"三国演义" sim 0.34~0.38 的无关块全进上下文；§1.3③ sim 0.60 的无关客服 prompt 劫持模型。

**代码定位**：
- `backend/app/retrieval/vector_retriever.py:56-66,73-81`：`retrieve()` **无条件取 top-context_k（默认 5）**，从不检查 `similarity` 是否低于阈值；`_rank_and_map` 只排序裁剪。
- 相似度信号（`1 - distance`）**只用于排序，从不用于决策**（"无相关则不给上下文"分支不存在）。

**机制**：库外/常识/模糊问题永远被喂 5 块无关上下文，模型要么拒答，要么被无关内容带偏（Cider 客服案例）。**这正是"答不出常识"与"复读机"共享的放大环节。**

### 🔴 根因 3：系统提示词过度约束 + 缺"无关上下文处理"指引

**证据**：§1.3①②③ —— 默认提示词下"三国演义"拒答；裸提示词下模型被无关上下文劫持、行为不稳定。

**代码定位**：
- 默认提示词 `backend/app/generation/chat_service.py:24-28` 与 `backend/app/core/settings_store.py:24-28`（DEFAULT_SYSTEM_PROMPT）：**"请严格基于给定的参考上下文作答，不要编造上下文之外的内容；若上下文无法回答该问题，请如实说明"** —— 一条指令同时造成 ①常识问题拒答 ②鼓励"只复述上下文"（复读机）。
- 用户已在设置页覆盖为 `"你是 Everything RAG 个人知识助手。"`（config.json）→ 裸提示词无锚点：模型有时答对、有时拒答、有时被上下文劫持，**无任何"上下文相关/无关判定"与"何时可用常识"的指令**。

**机制**：提示词没有告诉模型"上下文不相关时：① 明确说'资料未覆盖' ② 可用通用知识补充 ③ 不要被无关上下文带偏"。这是生成行为不稳定的直接根因。

### 🟠 根因 4：噪音语料 + HTML 未清洗（污染检索候选池）

**证据**：`chatbot对话测试数据.md`（**90 块，占全库 11.6%**）+ `LiveChat_内容方案生成调研.md`(74) + `散点属性文档.md`(71)，**3 个文件占 235/777 ≈ 30% 块**；检索结果里反复出现 `<font style="color:rgb(...)">` HTML 与管道符原始数据。

**代码定位**：
- `backend/app/ingestion/markdown_parser.py` **不过滤 HTML**（`<font>` 内联标签原样保留，全文件无 sanitize/strip）。
- 无导入时的"文档重要性/质量分级"——原始聊天记录、测试数据 dump、API 参数表与高质量技术文档同等权重入库。

**机制**：噪音文档碎片在候选池（candidate_k=20）里挤占真文档位置；HTML 标签污染嵌入向量与 LLM 上下文（还可能导致前端渲染异常）。

### 🟠 根因 5（放大因素）：仅纯向量检索，无混合/重排，窗口太小

**证据**：语义型查询（客户流失/红人流程/双十一）召回偏移；能答好的全是词面重叠。

**代码定位**：
- `backend/app/retrieval/vector_retriever.py:49-50`：candidate_k=20 / context_top_k=5（`chat.py:47` 用默认值）。
- 全库仅 777 块，其中 30% 来自 3 个噪音文档 → 检索在**小而脏的候选池**上做纯向量 top-5，无 BM25 词面兜底、无重排、无 MMR 多样性。

## 4. 修复建议（按优先级，未实施）

### P0（不修则检索/生成质量无解）

1. **切块策略重做**（`chunker.py`）
   - 加 `min_chunk_chars`（建议 ~150-300），**相邻短块合并到语义完整**；headingless 文档不要每段一块，改按"相邻段落贪心合并到 min/max 之间"。
   - 块文本**剥离 HTML 标签**（`<font>`/`<br>` 等）再入库。
   - 对表格/属性 dump（如散点属性文档）按"行聚合到完整表语义"处理，不要每行一块。

2. **相关度门控**（`vector_retriever.py` + `chat_service.py`）
   - 加 `min_similarity` 阈值（用真实语料校准，实测 MQ 相关 0.60~0.92 / 无关 0.34~0.60 的分档，建议先 0.55~0.6 起步）。
   - 低于阈值 → **不灌上下文**，走"无相关资料"分支：允许模型用常识回答并明确标注"资料未覆盖"。
   - `meta` 帧暴露相似度已在做，前端可直接展示置信度。

3. **提示词重构**（`settings_store.py` DEFAULT_SYSTEM_PROMPT + 指引）
   - 三段式：**① 优先用上下文作答并引用来源 → ② 上下文不相关/缺失时，可基于通用知识回答但必须明说"这是常识补充、非资料内容" → ③ 禁止被无关上下文带偏角色与立场**。
   - 补"复读抑制"：要求用自己的话归纳，禁止整段照抄。
   - 这是用户当前裸提示词 workaround 的正规化替代。

### P1

4. **语料卫生**：导入时识别原始聊天记录/测试数据（如 `chatbot对话测试数据.md`）→ 降权或排除；大表/API 文档单独策略。
5. **检索升级**：BM25 混合召回（`base.py` 已预留接口）+ context_top_k 提到 8~10 + 候选池按文档多样性去重。

### P2

6. **检索可视化调试**：`/api/chat` 返回 top-N 相似度分布，前端展示，便于持续校准阈值。

## 5. 关于"答案带来源"的诚实定位

PRD 定位是"检索找回我的一切、答案永远带来源"，方向没错。**当前真正的病不在"要不要带来源"，而在"来源本身是残句 + 无门槛"** —— 不是 LLM 复读机，而是**把残句当上下文喂给 LLM，LLM 被逼成复读机/拒答/跑偏**。修好 P0 的切块 + 门控 + 提示词后，"带来源且可用常识补充"的定位才成立。
