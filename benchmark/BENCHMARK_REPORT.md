### 0.3 已落地到生产代码的修复

1. **短兄弟章节聚合**：只合并同父级、同深度、同类型的连续短叶子节，并在正文注入
   `【叶子标题】`；顶级标题、代码、图片和类型切换仍是硬边界。元数据保存全部原始标题
   alias，来源评测和引用不会因聚合失真。
2. **软边界切分**：超长正文依次优先换行、句末、分号、空白，再做字符兜底；代码块保持
   原子性，表格独立分块，正文不会混入表格结构。
3. **稳定语义切块**：已有 Markdown 标题的文档直接信任标题边界；只对无标题长文做相邻
   段落语义切分，避免重复云端调用和边界漂移。
4. **跨文件批量嵌入**：文档向量按 64 块一批、文件按 32 篇编排；单批失败自动降级为
   单文件隔离，不让一个坏文档拖垮整次同步。
5. **内容级同步去重**：生产扫描的 1354 个路径中，实际是 298 份唯一内容和 1056 个完全
   相同的历史路径副本；重建只嵌入唯一内容。原报告“402 个 UUID 独有内容缺失”的判断
   混淆了路径覆盖与内容覆盖，现已纠正，不再作为结论。
6. **检索去重保留章节语义**：历史副本仍按“正文 + 完整标题路径”折叠；相同公式若在
   “首页”和“购物车”等不同章节重复出现，两份 provenance 都保留，避免证据被错误转移。
7. **长口语词法救援收紧**：只有同时命中至少 3 个高稀有信息词和明确业务锚点时，才可
   覆盖偏低但不矛盾的 dense 分数；两词泛匹配、数字噪声和 dense 反证继续硬拒绝。
8. **索引版本与自修复**：切块规则升级触发 schema v6 重建；批量写入后执行全库 ANN
   自探针并补写不可达节点，避免“数据库里有记录、向量检索却找不到”。

### 🔴 P0-1 定义类查询存在"假拒答"（最伤产品信任）
`Q03「什么是 MVCC？」` → **0 块召回**，模型回答"当前本地知识库中没有关于 MVCC 的足够内容"。但库内《加字段？锁表？》明确写了"不得不说MVCC（多版本并发控制）"。
根因：`hybrid_retriever.py::_has_definition_evidence` 把"定义证据"做成了**硬否决**——要求原文出现 `X 是/指/即/属于` 句式，而 `MVCC（多版本并发控制）` 这种括号注释虽然匹配 `X（...）` 模式，但该块同时被 BM25 排序挤出了候选窗口。定义类是 9 类中表现最差的（hit@5 77.8%）。

### 🔴 P0-2 语料 83% 未入库，其中 402 个文件内容真正丢失
UUID 上传目录（历史导入产物）产生 1046 个重复副本 + 402 个独有内容文件从未入库。用户以为"知识库包含我的一切"，实际近 1/4 内容不在索引里——这与 PRD「检索找回我的一切」的定位直接冲突。

### 🔴 P0-3 近空图片块污染候选池
全语料重切出 9998 个 image 块，**中位长度 0 字**（无 alt 文本）。线上索引虽只收了 635 个识图完成的块，但管线仍会为无 alt 图片生成空块占位。空块嵌入后是纯噪声向量，挤占 candidate_k 窗口。

### 🟠 P1-1 上下文污染率 30.4%，语义类查询高达 39.7%
top-8 里平均 2.4 块来自与问题无关的文档。代码注释里记录的"cross-encoder 重排反而降分（84.6%→76.9%）"使系统放弃了重排，但**没有替代的上下文精选机制**。

### 🟠 P1-2 词法救援绕过相似度门控
N11（Redis 大 key）在 dense 相似度仅 0.377 时仍召回 8 块。`_is_lexical_rescue` 的 `lexical_override_min_similarity=0.35` 门槛过低，且 `accepted_lexical_only` 对 BM25-only 候选完全不设相似度上限约束。

### 🟠 P1-3 跨路径重复块未去重
`_logical_block_key` 以 `doc_id`（按路径派生）作为身份，同一内容从不同路径入库时 doc_id 不同 → 4616 块只去重掉 11 块。同一事实的多个副本同时进 top-K，既浪费窗口又推高污染率。

### 🟠 P1-4 表格块碎片化 + 分块参数失效
430 个 table 块，表格行以「；」拆分后无法跨标题合并，`min_chunk_chars` 对它们完全不生效（见 2.7 消融）。

### 🟡 P2-1 数字类查询排序偏后（hit@5 71.4%）
数字/指标类问题（如"ctr 从多少降到多少"）gold 块常排 3–5 名，embedding 对数字不敏感，BM25 对纯数字 token 权重不足。

### 🟡 P2-2 语义类问题证据利用率低
检索证据覆盖 95.5%，但答案证据串命中只有 52.3%——模型拿到素材后概括过粗，关键数字/结论偶有丢失。

### 🟡 P2-3 单文档过度倾斜
`doc-noise-03.md` 占索引 15.3%，任何与其词汇重叠的查询都会被它的块填满候选窗口。

## 四、改进建议

### P0（直接修复错误行为）

1. **定义门控从"硬否决"改为"软加分"**
   `_has_definition_evidence` 命中失败时不应直接 `rejected_missing_definition_evidence`，而应降低该候选的融合分（如 ×0.6）或仅在"候选数已够"时才淘汰。同时把 `X（...）` 括号注释视为强定义证据。验证方式：`什么是 MVCC？` 应召回《加字段？锁表？》对应块。

2. **清理 UUID 上传目录并重建索引**
   - 同步/导入时把 `source_file` 归一到规范路径（去除 32 位 hex 目录段），让 `doc_id` 按**内容哈希**而非路径生成；
   - 对 402 个独有内容文件补导一次；
   - 预期收益：候选池去重后 top-K 有效容量提升约 8%，且消除"同一事实占 3 席"的污染。

3. **空图片块不入库**
   无 alt 且识图未完成/失败的图片，跳过 upsert（或在识图完成后异步补写），而不是先写一个 0 字块。已在库的 635 个 image_description 块保留。

4. **表格块聚合策略**
   表格行不再逐「；」拆成独立块，改为"整表 ≤ 上限则整表一块；超限则按表头+行组切块，每块回填表头"。这能把 430 个表格块的平均长度提上来，也让 min_chunk_chars 重新生效。

### P1（显著提升检索质量）

5. **用轻量重排替代被弃用的 cross-encoder**
   之前 bge-reranker-base 降分大概率是模型太小 + 输入未带标题。建议：a) 换 `bge-reranker-v2-m3` 并把 `标题路径 + 正文` 一起喂入；b) 或做零成本版——对 top-20 候选按 `dense_sim` 与 BM25 覆盖率做二次线性打分，砍掉 dense_sim < 0.5 且词法覆盖 ≤2 的填充块。目标：污染率从 30% 降到 <15%。

6. **给词法救援加相似度下限**
   `accepted_lexical_only` 分支增加"dense 候选池中该块相似度 < 0.40 时视为矛盾证据"的 veto（当前只有 0.35），并要求 BM25 `informative_matched_terms ≥ 3` 才能对长查询救援。预期把 N10/N11 这类对抗性泄漏降到 1–2 块。

7. **内容哈希去重**
   在 `_logical_block_key` 中用 `sha1(text)` 替代/叠加 `doc_id`，同一文本不同路径只保留规范路径版本。注意保留 `source_file` 最短路径优先策略（`_canonical_block_priority` 已有）。

8. **答案层"关键事实保全"指令**
   在系统提示词中加入一条："引用的具体数字、版本号、阈值必须与来源一致，不得四舍五入或省略单位"。并考虑对 numeric 类问题把 context_top_k 临时放宽到 10。

9. **语料卫生分级**
   导入时按"内容密度"打标：块均长度、HTML 残留率、重复块比例。对 `doc-noise-03.md` 这类 700+ 块的超大文档做章节级拆分或在检索时限制单文档 top-K 占比 ≤3。

### P2（长期健康度）

10. **把 benchmark 纳入回归**：`benchmark/` 已可一键重跑（`run_retrieval_bench.py` → `summarize.py`）。建议评测集扩到 150+ 条并加入"阈值/参数变更必须重跑 benchmark"的门禁；当前 87 条中 colloquial 仅 2 条、numeric 仅 7 条，是置信区间最窄的两类，优先补样。
11. **上下文压缩**：top-8 × 2000 字最长可到 1.6 万字进 prompt，对 `context_text` 做 800 字截断或句级抽取，可降延迟与失焦。
12. **LLM 查询改写**：当前 `normalize_query` 只做确定性去口语化，对 semantic 类帮助有限（污染率仍最高）。可选做一次轻量 LLM 改写（同义扩展 + 子查询拆分），配合多路 RRF。
13. **评测集防泄漏机制**：本报告的 gold 由人工从抽样块中构造，天然规避了"用检索结果反推 gold"的循环论证；建议后续扩集时保持这个流程（抽样 → 人工读原文 → 写 query + 证据串 → 程序校验），不要用模型自动生成。
